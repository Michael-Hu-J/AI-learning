## 一、分数出来了，然后呢？

实战 3 跑完评测，你拿到了一堆分数。但分数本身没有意义，关键是怎么解读。

两个 Agent 都是 3.5 分，可能一个规划强对话弱，另一个对话强规划弱。选型时该选哪个？取决于你的业务。

这篇我不给你假数据，我带你逐维度拆解评测结果，看每个维度的得分意味着什么、失败模式是什么、怎么改进。

## 二、任务规划：Agent 会不会拆任务

**评测器**：`evaluators/task_planning_evaluator.py`

**评分逻辑**：
- 覆盖率（40%）：Agent 拆的子任务覆盖了多少必需步骤
- 精确度（30%）：拆得是否合理（不过度也不不足）
- 粒度（20%）：子任务大小是否合适（3-8 个最佳）
- 依赖识别（10%）：是否正确识别了子任务间的先后关系

### 典型得分模式

| 得分区间 | 意味着什么 | 常见失败模式 |
|---------|-----------|------------|
| 4.0-5.0 | 规划能力强 | 几乎没有 |
| 3.0-3.9 | 能拆但不够精细 | 漏掉关键步骤、依赖关系错误 |
| 2.0-2.9 | 规划能力不足 | 拆得太粗（2-3 个子任务搞定一切）、工具选错 |
| < 2.0 | 基本不会规划 | 不拆任务、直接单步执行、JSON 解析失败 |

### 失败案例分析

**失败案例 1：过度分解**

任务：「分析2024年6月销售数据并生成报告」

Agent 拆了 15 个子任务：
1. 连接数据库
2. 执行 SQL 查询
3. 获取结果
4. 解析结果
5. 清洗数据
6. ...（省略 9 个）

**问题**：Agent 把简单任务复杂化了。一次 **`search`（经营类）** 就能拿到摘要，Agent 却拆了 4 个子任务。

**改进方向**：在 Prompt 中明确"子任务数量控制在 3-8 个"。

**失败案例 2：依赖关系错误**

任务：「评估618大促效果」

Agent 的依赖图：
```
task_1: 查询6月数据
task_2: 查询5月数据
task_3: 对比分析 → 依赖 [task_1]   漏了 task_2
task_4: 生成报告 → 依赖 [task_3]
```

**问题**：对比分析需要 6 月和 5 月数据，Agent 只依赖了 task_1。执行时 task_3 只有 6 月数据，对比结果不完整。

**改进方向**：在 Prompt 中强调"每个子任务必须列出所有前置依赖"。

## 三、工具使用：Agent 会不会选工具

**评测器**：`evaluators/tool_use_evaluator.py`

**评分逻辑**：
- 工具选择准确率（50%）：选的工具是否在期望列表中
- 参数准确性（30%）：工具参数格式是否正确
- 错误恢复（20%）：工具调用失败后是否重试或换工具

### 典型得分模式

| 得分区间 | 意味着什么 | 常见失败模式 |
|---------|-----------|------------|
| 4.0-5.0 | 工具选择精准 | 几乎没有 |
| 3.0-3.9 | 基本能选对 | 偶尔选错相似工具、参数格式有小问题 |
| 2.0-2.9 | 工具选择不可靠 | 频繁选错、参数经常出错 |
| < 2.0 | 不会用工具 | 不调用工具、工具名写错 |

### 失败案例分析

**失败案例：工具名混淆**

任务：「使用 calculator 计算销售指标」

Agent 输出：
```json
{"tool": "calculate", "input": "1250000 / 3200"}
```

**问题**：工具名是 `calculator`，Agent 写成了 `calculate`。Agent 的工具注册中心里没有 `calculate`，所以调用失败。

**根因**：Agent 的 Prompt 中列出了所有可用工具，但 LLM 记住了近似名而非精确名。

**改进方向**：在 Prompt 中用表格列出工具名，而不是纯文本描述。

## 四、多轮对话：Agent 能不能记住前面的话

**评测器**：`evaluators/dialogue_evaluator.py`

**评分逻辑**：
- 上下文保持（40%）：是否记住了前面轮次的信息
- 指代消解（30%）：是否正确理解了"它"、"那个"等指代
- 回复相关性（20%）：回复是否与用户问题相关
- 情绪识别（10%）：是否能识别用户情绪

### 典型得分模式

| 得分区间 | 意味着什么 | 常见失败模式 |
|---------|-----------|------------|
| 4.0-5.0 | 对话能力强 | 几乎不忘信息、能处理复杂指代 |
| 3.0-3.9 | 基本可靠 | 偶尔忘记早期信息、简单指代能处理 |
| 2.0-2.9 | 记忆不可靠 | 3 轮以后开始忘、指代经常出错 |
| < 2.0 | 没有记忆 | 每轮当新对话处理 |

### 失败案例分析

**失败案例：指代消解失败**

对话：
```
用户：我的订单到哪了？
Agent：正在为您查询物流信息...
用户：那个能改地址吗？
```

Agent 回答：「请问您想改哪个订单的地址？」

**问题**：「那个」指代的是上一轮的"订单"，Agent 没有记住上下文，又问了一遍。

**根因**：Agent 的 `_build_context_text()` 方法把历史对话拼接到 Prompt 中，但 LLM 在长上下文中容易忽略早期信息（Lost in the Middle 现象）。

**改进方向**：
1. 减少无关上下文，只保留最近 5 轮
2. 在 Prompt 中明确标注"对话历史"部分

## 五、代码能力：Agent 写的代码对不对

**评测器**：`evaluators/coding_evaluator.py`

**评分逻辑**：
- 可执行性（40%）：代码能不能跑（不报错）
- 输出正确性（40%）：输出结果是否正确
- 代码质量（20%）：代码风格、注释、边界处理

### 典型得分模式

| 得分区间 | 意味着什么 | 常见失败模式 |
|---------|-----------|------------|
| 4.0-5.0 | 代码能力强 | 能处理边界情况、代码规范 |
| 3.0-3.9 | 能写但不够好 | 能跑但结果偶尔错、缺少边界处理 |
| 2.0-2.9 | 代码能力弱 | 经常报错、逻辑错误 |
| < 2.0 | 不会写代码 | 语法错误、不会用库 |

### 失败案例分析

**失败案例：逻辑错误**

任务：「计算各月的同比和环比增长率」

Agent 生成的代码：
```python
# 同比增长率 = (今年-去年)/去年
growth = (this_month - last_month) / last_month  #  这是环比，不是同比
```

**问题**：Agent 混淆了同比和环比的概念。同比是和去年同期比，环比是和上个月比。

**根因**：这不是代码问题，是知识问题。Agent 不懂"同比"和"环比"的业务含义。

**改进方向**：加强知识应用维度的训练，尤其是业务概念。

## 六、知识应用：Agent 懂不懂业务

**评测器**：`evaluators/knowledge_evaluator.py`

**评分逻辑**：
- 选择题准确率（70%）：标准选择题，对错分明
- 解释合理性（30%）：Agent 附加的解释是否合理

### 典型得分模式

| 得分区间 | 意味着什么 | 常见失败模式 |
|---------|-----------|------------|
| 4.0-5.0 | 业务知识扎实 | 概念清晰、不会混淆 |
| 3.0-3.9 | 基础知识 OK | 简单概念懂、复杂概念模糊 |
| 2.0-2.9 | 知识薄弱 | 基本概念都搞错 |
| < 2.0 | 缺乏领域知识 | 需要大量领域训练 |

### 失败案例分析

**失败案例：概念混淆**

题目：「客单价的计算公式是？」

Agent 回答：「总利润 / 订单数」

**问题**：客单价 = 总销售额 / 订单数，不是总利润。Agent 混淆了"销售额"和"利润"。

**根因**：LLM 的通用训练数据中，"客单价"的定义不够突出，被其他电商指标干扰。

## 七、综合解读：怎么看雷达图

5 个维度跑完，你会看到一个雷达图。怎么解读？

### 解读原则 1：看形状，不看面积

两个 Agent 雷达图面积相同，形状可能完全不同：

```
Agent A（均衡型）：        Agent B（偏科型）：
规划 3.5                  规划 4.8
工具 3.4                  工具 4.5
对话 3.6                  对话 2.1
代码 3.3                  代码 4.2
知识 3.5                  知识 2.8
```

如果你的业务是客服场景（对话重要），选 Agent A。如果你的业务是数据分析（规划+代码重要），选 Agent B。

### 解读原则 2：看短板，不看长板

短板效应：任何一个维度低于 2.0，综合分打折扣。

```
综合分 = 加权平均分 × 短板系数

短板系数：
- 所有维度 ≥ 3.0：系数 1.0
- 任一维度 2.0-2.9：系数 0.8
- 任一维度 < 2.0：系数 0.6
- 安全维度 < 2.0：直接标记"不建议上线"
```

### 解读原则 3：看趋势，不看单次

跑 3 次评测，看每个维度的标准差：

| 标准差 | 意味着什么 |
|--------|-----------|
| < 0.3 | Agent 稳定，分数可信 |
| 0.3-0.5 | 有一定波动，需要关注 |
| > 0.5 | Agent 不稳定，分数参考价值低 |

## 八、改进建议：分数低怎么办

评测不是目的，改进才是。根据得分给出改进方向：

| 低分维度 | 改进方向 | 具体操作 |
|---------|---------|---------|
| 任务规划 | 优化规划 Prompt | 增加示例、明确子任务数量限制、强调依赖关系 |
| 工具使用 | 优化工具描述 | 用表格列出工具、增加工具使用示例 |
| 多轮对话 | 优化上下文管理 | 减少无关上下文、关键信息前置、增加对话历史标记 |
| 代码能力 | 增加代码训练数据 | 提供业务代码示例、加强边界处理训练 |
| 知识应用 | 补充业务知识 | 在业务背景中增加概念定义、提供术语表 |

---

## 九、这一篇要带走的东西

1. **分数本身没有意义，解读才有意义。** 看形状、看短板、看趋势。
2. **每个维度的失败模式不同。** 规划是拆不对，工具是选错，对话是忘了，代码是写错，知识是搞混。
3. **改进方向要对症下药。** 不是"提升 Agent能力"这种空话，而是"优化 Prompt 中的工具描述格式"这种具体操作。

## 面试题模块

### Q1：5 维评测结果中，哪个维度的得分最低？为什么？

A：知识维度和安全维度一般得分相对较低。知识维度低的原因是 LLM 存在幻觉——让 Agent 回答"2024年6月华东区销售额"时可能胡编数字。安全维度低的原因是通用模型的安全防护相对较弱——容易被注入攻击绕过。

### Q2：评测结果中得分最高的维度是什么？说明什么问题？

A：任务规划得分最高（通常 4.0+/5）。说明 LLM 做任务拆分是比较擅长的——给定一个目标，LLM 能合理规划步骤。但高分不代表没有问题——漏掉中间步骤是常见但不易被发现的缺陷。

### Q3：评测报告中，Top 3 改进建议通常是什么？

A：1) 工具调用失败后的错误处理需要加强（当前 agent 倾向于直接报告失败而非重试）；2) 多轮对话中 30 轮后信息召回率下降明显（需要显式记忆机制）；3) 温度超过 0.5 时规划路径不稳定（建议生产环境使用 0.1-0.3）。
