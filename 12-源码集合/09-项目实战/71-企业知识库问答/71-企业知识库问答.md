## 工程实践（代码与一键运行）

### 项目简介

这是一个企业级知识库问答系统，覆盖文档解析、文本切片、混合检索、问答生成等完整流程。

**核心特性：**
- ✅ 文档解析：支持 Markdown、纯文本、HTML 等多种格式
- ✅ 文本切片：段落分割 + 句子边界 + 重叠保留上下文
- ✅ 混合检索：向量检索 + 关键词检索 + RRF 融合 + 重排序
- ✅ 时效性管理：过期文档降权，优先返回最新版本
- ✅ 安全校验：数值一致性检查，防止安全内容"自由发挥"
- ✅ 一键启动：无需配置即可运行，支持交互/演示/测试三种模式

## 测试方案与踩坑实录

## 一、概念讲解：为什么企业知识库比你想的难测得多

### 1.1 先说个真实故事

2024年2月，我们给一家中型企业部署了内部知识库问答系统。公司有3000多名员工，分布在HR、财务、IT、行政等多个部门。员工经常问一些重复性问题——"差旅费报销标准是多少"、"请假流程是什么"、"怎么申请办公用品"。

以前这些问题都找各部门的人问，效率很低。老板说："用RAG做一个知识库，员工自己查。"

我们花了两个月开发。知识库包含了公司的员工手册、报销制度、请假流程、IT支持指南等文档。上线前测试，员工问"差旅费报销标准"，系统回答"住宿费300元/天，餐饮费100元/天"。看起来没问题，老板也很满意。

上线第一周，问题来了。

**场景一：旧文档没有被下架**

员工问："差旅费报销标准是多少？"

系统回答："差旅费报销标准为：住宿费300元/天，餐饮费100元/天。"

财务部门的人看到后直接炸了："这个标准是2022年的！2023年已经更新了——住宿费500元/天，餐饮费150元/天。旧文档没有被下架！"

我当时听到这个消息，后背一凉。这不是一个小bug，这是一个系统性问题——我们的知识库同时存着新旧两个版本的文档，而且系统优先检索到了旧的那个。

> **踩坑实录1**：我们上线前只测了"能不能回答"，没有测"回答的是不是最新版本"。这是企业知识库测试最容易忽略的盲区。

**场景二：权限隔离不彻底**

IT部门的员工问："HR部门的绩效考核标准是什么？"

系统回答了一大段HR部门的内部考核标准，连每个职级的薪资范围都列出来了。

HR部门的人看到后很生气："这是内部文档，不应该被其他部门的人看到！你们这个系统有严重的安全漏洞！"

> **踩坑实录2**：权限过滤只在检索层做了，但文档上传时没有设置权限标签。结果所有文档的默认权限都是"public"，等于所有人都能看到所有东西。

**场景三：文档格式混乱**

行政部的文档是Word格式，财务部的文档是PDF格式，IT部的文档是Wiki页面。解析器对Word和Wiki支持好，但对PDF支持差——很多PDF文档解析后变成了乱码。

财务部的老王拿着解析结果来找我："周周，你看看这个，我花了一周做的报销制度，解析出来全是乱码，这怎么用？"

> **踩坑实录3**：我们测试时用的都是UTF-8编码的文档，但财务部的PDF是GBK编码的。国内企业大量使用GBK编码，这一点我们在测试计划里完全没考虑到。

**场景四：知识更新不及时**

公司5月份更新了"加班补贴政策"，但知识库直到7月份还没有更新。员工问"加班补贴是多少"，系统回答的还是旧标准。

员工去财务部领补贴，财务说新标准已经执行了两个月了，但知识库告诉员工的还是旧标准。两边说法不一致，员工直接投诉到HR。

> **踩坑实录4**：没有建立文档更新流程。业务部门更新了文档，但没有人通知知识库管理员。知识库成了"僵尸库"——只管建，不管维护。

这一篇，我把企业知识库问答的完整测试方案讲清楚——从概念到方法论，从实战到代码，从踩坑到总结。你看完之后，至少能避开我们踩过的这些坑。

### 1.2 企业知识库 vs 公开知识库：本质区别

企业知识库和公开知识库有本质区别。公开知识库（如维基百科）面向所有人，内容公开，不需要权限控制。企业知识库面向内部员工或特定客户，内容可能涉及商业机密，需要严格的权限控制。

| 维度 | 公开知识库 | 企业知识库 |
|------|-----------|-----------|
| 文档来源 | 互联网（公开） | 企业内部（私有） |
| 文档质量 | 参差不齐 | 相对规范（有审核流程） |
| 更新频率 | 不固定 | 定期更新（有更新流程） |
| 权限控制 | 无 | 必须按部门/角色隔离 |
| 合规要求 | 低 | 高（金融/医疗/法律） |
| 审计要求 | 无 | 必须有（谁在什么时候查了什么） |
| 容错率 | 较高（用户可自行判断） | 极低（错误回答可能导致法律风险） |
| 数据敏感度 | 低 | 高（可能涉及薪酬、客户信息） |

> **踩坑实录5**：我们最初用测试公开知识库的方法来测试企业知识库，结果上线后被安全团队打了脸。企业知识库的测试维度比公开知识库多了至少三个：权限、合规、审计。

### 1.3 企业知识库的5大核心挑战

**挑战一：文档格式混乱**

企业内部的文档格式五花八门：PDF、Word、Excel、扫描件、手写笔记、邮件、聊天记录。每种格式都需要不同的解析方法。

比如财务部门的文档是Excel，HR部门的文档是Word，法务部门的文档是PDF扫描件，业务部门的文档是邮件截图。解析器需要支持所有这些格式，而且要保证信息不丢失。

> **踩坑实录6**：我们遇到的最离谱的文档是一个销售总监用语音备忘录录的"客户拜访注意事项"，转成文字后全是口语化表达，切片后语义完全断裂。

**挑战二：知识更新不及时**

企业知识库的文档需要定期更新。旧文档没有及时下架，新文档没有及时上传，导致系统回答过时信息。

比如理财产品的收益率从8%-12%更新到了6%-10%，但旧文档没有被下架，系统仍然回答8%-12%。员工按照旧标准去理财，亏了钱谁负责？

> **踩坑实录7**：有一家银行的知识点库，回答的贷款利率还是2022年的LPR基准，实际上2024年已经调整了两次。客户拿着知识库的回答去贷款，发现利率对不上，直接投诉到银保监会。

**挑战三：权限隔离**

不同部门的人只能看到自己的文档。A部门的员工不能看到B部门的文档，普通员工不能看到管理层文档。

比如信贷审批的内部标准只有管理层能看到，普通员工看到就是违规。薪酬数据只有HR和当事人能看到，其他人看到就是泄露隐私。

> **踩坑实录8**：我们曾经发现一个严重问题——新员工入职培训用的文档里，包含了公司组织架构和各部门负责人信息。这些信息本身不敏感，但结合权限系统的漏洞，新员工可以查询到所有部门的内部文档。

**挑战四：合规风险**

金融、医疗、法律等强监管行业，知识库回答必须符合行业法规。错误回答可能导致法律风险。

比如理财产品不能承诺"保本保息"，医疗建议不能替代医生诊断，法律咨询不能替代律师意见。知识库的回答必须加上免责声明，而且回答内容本身不能违反监管规定。

> **踩坑实录9**：一家保险公司的知识库回答"这款重疾险保证赔付"，实际上条款里有免责条款。客户买了保险后出险，发现不在赔付范围内，投诉到监管部门。公司被罚款50万。

**挑战五：审计要求**

企业知识库必须有审计日志——谁在什么时候查了什么，系统回答了什么。这是合规要求。

比如监管检查时，需要调取某个员工在某段时间内的查询记录。或者出了纠纷时，需要证明系统当时回答的是什么。

> **踩坑实录10**：我们上线初期没有做审计日志功能，结果安全审计时被开了一个严重不符合项。补做这个功能花了整整两周，而且还要把之前的查询记录补录进去——实际上根本补不了，因为没记录。

### 1.4 为什么知识库测试容易被忽视？

说句大实话，很多团队对知识库测试的重视程度远远不够。原因有几个：

第一，老板觉得"大模型这么聪明，应该没问题"。他们不知道大模型会 hallucination（幻觉），会一本正经地胡说八道。

第二，开发觉得"检索到了相关文档，答案应该没问题"。他们不知道检索到的文档可能是旧的、可能是错的、可能权限不对。

第三，测试觉得"这不是传统软件，不知道怎么测"。传统软件测试有明确的输入输出，知识库测试的答案是生成的，每次可能不一样。

> **踩坑实录11**：我们第一次做知识库测试的时候，测试用例只有5条——"问一个简单问题，看看回答对不对"。结果上线后翻车翻得亲妈都不认识。后来我们总结了上百条测试用例，覆盖各种边界场景。

### 2.2 文档解析测试：信息保留率是核心指标

文档解析是知识库的第一道关卡。解析不好，后面全完蛋。

**测试维度一：格式兼容性**

你需要准备一个测试文档集，覆盖企业里常见的所有格式：

- PDF（文字版）：正常PDF，包含文字、图片、表格
- PDF（扫描版）：扫描件，需要OCR识别
- Word（.docx）：包含标题、列表、表格、脚注
- Word（.doc）：老格式，兼容性更差
- Excel（.xlsx）：包含多sheet、合并单元格、公式
- HTML：网页导出，包含样式和链接
- 图片：JPG/PNG，需要OCR
- TXT：纯文本，但可能有各种编码

> **踩坑实录13**：我们准备测试文档集的时候，只准备了每种格式的一个样本。结果上线后发现，同一种格式也有天差地别——有的PDF是Acrobat生成的，有的是WPS生成的，有的是在线转换的，解析效果完全不同。后来我们把每种格式的样本扩展到了至少5个，覆盖了不同来源、不同版本、不同复杂度的文档。

**测试维度二：信息保留率**

信息保留率 = 解析后保留的字符数 / 原文档总字符数

一般来说，文字版PDF的信息保留率应该在95%以上，扫描版PDF（OCR）应该在85%以上。如果低于这个标准，说明解析器有问题。

但光看保留率不够，你还要看关键信息是否保留。比如一份报销制度，关键信息包括：报销标准、报销流程、审批人。这些信息一个都不能少。

> **踩坑实录14**：我们曾经有一份Excel文档，解析后信息保留率98%，看起来很好。但仔细看发现，合并单元格的内容只保留了一个单元格，其他单元格的内容全丢了。而丢失的那个单元格正好是"审批人"字段。员工按照解析后的文档去报销，找不到审批人，整个流程卡住了。

**测试维度三：表格解析**

表格是企业文档中最常见的结构，也是解析器最容易翻车的地方。

你需要重点测试：
- 简单表格（无合并单元格）
- 复杂表格（有合并单元格、跨页表格）
- 嵌套表格（表格套表格）
- 图片中的表格（需要OCR+表格识别）

> **踩坑实录15**：财务部的差旅费报销标准是一个跨页表格，第一页是"国内出差"，第二页是"国际出差"。解析器把两页的内容混在一起了，国内和国际的标准全乱了。员工按照解析后的标准去报销，国内出差按国际标准报，多报了钱；国际出差按国内标准报，少报了钱。财务部差点跟我们急。

### 2.3 文本切片测试：粒度决定检索质量

切片是把长文档切成小块，方便向量检索。切得太粗，检索不精确；切得太细，语义不完整。

**切片策略对比**

| 切片策略 | 适用场景 | 优点 | 缺点 |
|---------|---------|------|------|
| 固定字符数切片 | 通用文档 | 简单、均匀 | 可能切断语义 |
| 按章节切片 | 有标题结构的文档 | 语义完整 | 章节大小不一 |
| 按条款切片 | 政策/法规文档 | 精确 | 需要理解文档结构 |
| 按问答对切片 | FAQ文档 | 直接可用 | 只适用于FAQ |
| 语义切片 | 复杂文档 | 最准确 | 计算成本高 |

> **踩坑实录16**：我们一开始用固定字符数切片，每500字切一刀。结果一份请假流程文档，第499字是"请假需要"，第500字切到了下一块，变成了"提交申请"。两块单独拿出来都没法理解。后来我们改用按章节切片，问题解决了。

**切片质量评估指标**

- 语义完整性：每个切片是否包含完整的语义单元
- 检索命中率：用测试问题检索，能否命中正确的切片
- 冗余度：不同切片之间是否有大量重复内容
- 覆盖率：所有重要内容是否都被切到了

> **踩坑实录17**：我们评估切片质量的时候，只看了检索命中率，忽略了语义完整性。结果系统能检索到相关切片，但切片内容不完整，生成的答案断章取义。比如一份安全操作规程，切片只包含了"操作步骤"，没包含"注意事项"，员工按照答案操作出了安全事故。

### 2.4 权限隔离测试：纵深防御策略

权限隔离是企业知识库最核心的安全机制。我们的策略是纵深防御——在三个层面都做权限控制：

**第一层：文档上传时设置权限标签**

上传文档时必须设置：
- 部门标签（哪个部门的文档）
- 访问级别（public / department / management / confidential）
- 有效期（文档的有效期限）

**第二层：检索时按权限过滤**

检索时根据用户的角色和部门，过滤掉无权访问的文档。

**第三层：答案生成时二次检查**

即使检索通过了权限过滤，在生成答案时还要再检查一遍——确保答案中没有泄露敏感信息。

> **踩坑实录18**：我们只做了第一层和第二层，没做第三层。结果大模型在生成答案时，把检索到的多个切片拼在一起，其中某个切片虽然权限通过了，但内容里包含了其他部门的敏感信息（因为原始文档引用了其他部门的数据）。第三层检查就是用来拦截这种"间接泄露"的。

**权限测试矩阵**

你需要构建一个权限测试矩阵，覆盖所有用户角色和文档权限的组合：

| 用户角色 | 用户部门 | 文档权限 | 预期结果 |
|---------|---------|---------|---------|
| 普通员工 | 销售部 | public | ✅ 可访问 |
| 普通员工 | 销售部 | department(销售部) | ✅ 可访问 |
| 普通员工 | 销售部 | department(HR部) | ❌ 不可访问 |
| 普通员工 | 销售部 | management | ❌ 不可访问 |
| 普通员工 | 销售部 | confidential | ❌ 不可访问 |
| 经理 | 销售部 | public | ✅ 可访问 |
| 经理 | 销售部 | department(销售部) | ✅ 可访问 |
| 经理 | 销售部 | management | ✅ 可访问 |
| 经理 | 销售部 | department(HR部) | ❌ 不可访问 |
| CEO | 管理层 | 所有 | ✅ 全部可访问 |

> **踩坑实录19**：我们构建权限测试矩阵的时候，漏了一个场景——"跨部门协作文档"。有些文档需要多个部门的人都能访问，但我们的权限模型只支持单一部门。结果市场部和合作方共享的文档，合作方的人看不到。后来我们在权限模型里加了"共享部门列表"字段，才解决这个问题。

### 2.5 知识时效性测试：过期文档自动下架

知识时效性是企业知识库最容易翻车的点。我们的策略是三层防护：

**第一层：文档版本管理**

每次更新文档时，自动标记旧版本为"expired"，新版本为"active"。检索时只检索"active"文档。

**第二层：文档过期检查**

文档超过180天（可配置）未更新，自动标记为"auto_expired"。标记后仍然可以检索到，但会在答案中标注"此信息可能已过时，请以最新文档为准"。

**第三层：定期人工审核**

每月跑一次知识时效性报告，列出所有接近过期和已过期的文档，通知文档负责人确认是否需要更新。

> **踩坑实录20**：我们设置过期时间是180天，但有些文档的有效期只有30天——比如月度促销活动。这些文档过期后还在被检索到，员工按照过期的促销信息去参加活动，活动早就结束了。后来我们加了"文档有效期"字段，不同类型的文档有不同的过期时间。

### 2.6 合规性测试：强监管行业的生命线

金融、医疗、法律等强监管行业，知识库回答必须符合行业法规。我们的合规测试框架包括：

**禁止词汇表**

维护一个禁止词汇表，覆盖所有违规场景。比如金融行业的"保本保息"、"稳赚不赔"，医疗行业的"保证治愈"、"无副作用"。

**免责声明自动添加**

在特定场景下自动添加免责声明。比如金融问答加上"投资有风险，入市需谨慎"，医疗问答加上"本回答仅供参考，不能替代专业医疗建议"。

**答案合规检查**

在答案生成后，用合规检查器扫描答案，确保没有违规内容。合规检查器可以用规则引擎，也可以用另一个大模型。

> **踩坑实录21**：我们一开始只用规则引擎做合规检查，结果大模型生成的答案用了同义词替换——把"保本"说成了"本金安全"，规则引擎没识别出来。后来我们加了一个大模型做二次检查，识别率提高了很多。但大模型检查也有问题——它自己也会犯错，有时候把正常的回答标记为违规。所以最好的方案是规则引擎+大模型+人工抽检，三层防护。

## 三、实战案例：完整测试流程

### 3.1 案例背景

我们给一家金融公司测试知识库问答系统。公司有2000多名员工，知识库包含：
- 产品手册（理财产品、保险产品、贷款产品）
- 业务流程（开户流程、审批流程、理赔流程）
- 合规文档（监管要求、内部制度、操作规范）
- FAQ（常见问题解答）

总共约500份文档，覆盖PDF、Word、Excel三种主要格式。

### 3.2 测试计划制定

我们花了三天时间制定测试计划，覆盖以下测试类型：

| 测试类型 | 测试内容 | 用例数量 | 优先级 |
|---------|---------|---------|-------|
| 文档解析测试 | 格式兼容性、信息保留率、表格解析 | 80 | P0 |
| 切片质量测试 | 语义完整性、检索命中率 | 50 | P0 |
| 权限隔离测试 | 角色-权限矩阵、边界场景 | 60 | P0 |
| 知识时效性测试 | 版本管理、过期检查 | 30 | P1 |
| 答案准确性测试 | 事实准确性、完整性、合规性 | 100 | P0 |
| 合规性测试 | 禁止词汇、免责声明、合规检查 | 40 | P0 |
| 性能测试 | 响应时间、并发能力 | 20 | P1 |
| 审计日志测试 | 日志完整性、可查询性 | 15 | P1 |

> **踩坑实录22**：我们制定测试计划的时候，性能测试只安排了20个用例。后来上线后发现并发量远超预期——早上9点员工集中查询，系统响应时间从2秒飙升到30秒。后来我们把性能测试用例扩展到了80个，覆盖了不同并发级别、不同查询复杂度、不同文档大小。

### 3.3 文档解析测试实战

**步骤一：准备测试文档集**

我们准备了80份测试文档，覆盖以下维度：

- 格式：PDF(30份)、Word(25份)、Excel(15份)、HTML(5份)、图片(5份)
- 大小：小(10KB以下)、中(10-100KB)、大(100KB-10MB)、超大(10MB以上)
- 复杂度：简单(纯文字)、中等(含表格)、复杂(含表格+图片+公式)
- 编码：UTF-8、GBK、GB2312、Big5

> **踩坑实录23**：我们准备测试文档集的时候，Big5编码的文档只准备了一份。后来发现繁体中文文档的解析问题特别多——有些字识别成了简体字，有些字直接变成了乱码。后来我们把繁体中文文档扩展到了10份，覆盖了不同来源、不同字体。

**步骤二：执行解析测试**

对每份文档执行解析，记录以下指标：
- 解析是否成功
- 信息保留率
- 关键信息是否保留
- 表格是否正确解析
- 特殊字符是否正确处理

**步骤三：分析结果**

80份文档的解析结果如下：

- 成功解析：72份（90%）
- 解析失败：8份（10%）
  - PDF扫描版OCR失败：3份
  - Excel合并单元格解析错误：2份
  - GBK编码识别错误：2份
  - 超大文件超时：1份

> **踩坑实录24**：GBK编码识别错误的那两份文档，后来发现不是解析器的问题，是文件本身的问题——文件头声明是UTF-8，但实际内容是GBK。这种情况叫"编码声明错误"，解析器按声明的UTF-8读取，自然读出来是乱码。后来我们加了编码检测逻辑（用chardet库），先检测实际编码，再按检测到的编码读取，问题解决了。

### 3.4 权限隔离测试实战

**步骤一：构建测试用户集**

我们构建了10个测试用户，覆盖不同角色和部门：

| 用户 | 角色 | 部门 | 预期权限 |
|-----|------|------|---------|
| user_emp_sales | 普通员工 | 销售部 | public + 销售部文档 |
| user_emp_hr | 普通员工 | HR部 | public + HR部文档 |
| user_mgr_sales | 经理 | 销售部 | public + 销售部文档 + 管理层文档 |
| user_mgr_hr | 经理 | HR部 | public + HR部文档 + 管理层文档 |
| user_ceo | CEO | 管理层 | 所有文档 |
| user_emp_it | 普通员工 | IT部 | public + IT部文档 |
| user_emp_finance | 普通员工 | 财务部 | public + 财务部文档 |
| user_mgr_finance | 经理 | 财务部 | public + 财务部文档 + 管理层文档 |
| user_newbie | 新员工 | 未分配 | public 文档 |
| user_external | 外部用户 | 无 | 仅公开文档 |

> **踩坑实录25**：我们漏了一个场景——"员工调岗"。员工从销售部调到了HR部，权限应该自动切换。但我们测试的时候没有覆盖这个场景，结果上线后有一个员工调岗了，但他还能看到销售部的文档。后来我们加了"权限变更测试"，覆盖调岗、晋升、离职等场景。

**步骤二：执行权限测试**

对每个用户，执行以下测试：
1. 查询本部门的文档——应该能访问
2. 查询其他部门的文档——应该被拦截
3. 查询管理层文档（普通员工）——应该被拦截
4. 查询公开文档——应该能访问
5. 查询机密文档（非CEO）——应该被拦截

**步骤三：边界测试**

除了正常场景，还要测试边界场景：
- 用户角色为空
- 用户部门为空
- 文档权限标签缺失
- 文档权限标签不合法
- 用户角色和部门不匹配

> **踩坑实录26**：边界测试的时候我们发现，当用户角色为空时，权限过滤器直接抛异常了，整个系统崩溃。原因是权限过滤器没有处理空值。后来我们加了空值处理——角色为空时默认按"普通员工"处理。

### 3.5 答案准确性测试实战

**步骤一：构建标准问答对**

我们构建了100个标准问答对，覆盖以下类型：

| 问题类型 | 数量 | 示例 |
|---------|------|------|
| 事实型问题 | 40 | "差旅费报销标准是多少？" |
| 流程型问题 | 25 | "请假流程是什么？" |
| 政策型问题 | 20 | "加班补贴政策是什么？" |
| 比较型问题 | 10 | "A理财产品和B理财产品有什么区别？" |
| 模糊型问题 | 5 | "我想理财，有什么推荐？" |

> **踩坑实录27**：我们构建标准问答对的时候，所有问题都是"完美问题"——表述清晰、关键词准确。结果上线后发现，员工问的问题千奇百怪——有打错字的、有用口语表达的、有省略关键词的。比如标准问题是"差旅费报销标准是多少"，员工问的是"出差住酒店能报多少钱"。后来我们把问题集扩展到了200个，覆盖了各种非标准问法。

**步骤二：执行准确性测试**

对每个问题，评估答案的：
- 事实准确性：答案中的事实是否正确
- 完整性：答案是否覆盖了问题的所有方面
- 相关性：答案是否与问题相关
- 合规性：答案是否包含违规内容

**步骤三：分析结果**

100个问题的测试结果：

- 完全正确：65个（65%）
- 部分正确：20个（20%）——答案有部分正确信息，但有关键遗漏
- 错误：10个（10%）——答案完全错误
- 无法回答：5个（5%）——系统说"不知道"

> **踩坑实录28**：那10个完全错误的答案里，有3个是因为检索到了旧文档（知识时效性问题），有4个是因为切片不完整导致语义断裂，有2个是大模型幻觉（编造了不存在的政策），有1个是因为文档本身写错了（文档源头问题）。你看，答案错误的原因有很多种，你不能只怪大模型。

### 3.6 性能测试实战

**测试场景**

| 场景 | 并发用户数 | 预期响应时间 | 实际响应时间 |
|------|----------|------------|------------|
| 正常负载 | 10 | < 3秒 | 2.1秒 ✅ |
| 中等负载 | 50 | < 5秒 | 4.8秒 ✅ |
| 高峰负载 | 100 | < 10秒 | 12.3秒 ❌ |
| 极端负载 | 200 | < 20秒 | 45.6秒 ❌ |

> **踩坑实录29**：高峰负载测试的时候，我们发现向量数据库成了瓶颈。100个并发查询同时打过来，向量数据库的查询队列排满了，响应时间直接飙升。后来我们做了两件事：一是加了查询缓存（相同问题30秒内不重复检索），二是把向量数据库从单机换成了集群。改完之后，100并发的响应时间降到了6秒。

## 四、代码示例：测试工具集

### 4.1 权限隔离测试框架

```python
class PermissionFilter:
    """权限过滤器"""
    
    def __init__(self, vector_db):
        self.vector_db = vector_db
    
    def get_allowed_docs(self, user_role: str, user_dept: str) -> list:
        """获取用户有权限查看的文档"""
        allowed = []
        
        # 公开文档
        public_docs = self.vector_db.filter({"access_level": "public"})
        allowed.extend(public_docs)
        
        # 部门文档
        if user_dept:
            dept_docs = self.vector_db.filter({
                "access_level": "department",
                "department": user_dept
            })
            allowed.extend(dept_docs)
        
        # 管理层文档
        if user_role in ["manager", "director", "ceo"]:
            mgmt_docs = self.vector_db.filter({"access_level": "management"})
            allowed.extend(mgmt_docs)
        
        # 机密文档（需要额外检查）
        if user_role == "ceo":
            confidential_docs = self.vector_db.filter({"access_level": "confidential"})
            allowed.extend(confidential_docs)
        
        return allowed
    
    def retrieve_with_permission(self, query: str, user_role: str, user_dept: str, top_k: int = 5) -> list:
        """带权限过滤的检索"""
        allowed_docs = self.get_allowed_docs(user_role, user_dept)
        results = self.vector_db.search(query, docs=allowed_docs, top_k=top_k)
        return results


def test_permission_isolation():
    """权限隔离测试"""
    filter = PermissionFilter(vector_db)
    
    # 测试1：普通员工不能看到管理层文档
    results = filter.retrieve_with_permission(
        query="信贷审批内部标准",
        user_role="employee",
        user_dept="sales",
        top_k=5
    )
    assert len(results) == 0, "普通员工不应该看到管理层文档"
    
    # 测试2：管理层可以看到管理层文档
    results = filter.retrieve_with_permission(
        query="信贷审批内部标准",
        user_role="manager",
        user_dept="credit",
        top_k=5
    )
    assert len(results) > 0, "管理层应该看到管理层文档"
    
    # 测试3：A部门员工不能看到B部门文档
    results = filter.retrieve_with_permission(
        query="HR部门内部政策",
        user_role="manager",
        user_dept="sales",
        top_k=5
    )
    assert len(results) == 0, "销售部不应该看到HR部门文档"
    
    print("✅ 权限隔离测试通过")
```

这个权限过滤器的核心思路很简单：先拿到用户有权限的文档列表，然后只在这个列表里做检索。但实际用的时候有几个坑要注意：

第一，`get_allowed_docs` 这个方法如果文档量大会很慢。我们一开始每次检索都调用一次，后来改成了缓存——用户权限不变的情况下，缓存结果5分钟。

第二，权限过滤是在向量检索之前做的（pre-filtering），但也有另一种做法是在检索之后做（post-filtering）。pre-filtering性能好但可能漏掉一些相关文档（因为被权限过滤掉了），post-filtering准确但性能差。我们用的是pre-filtering，因为安全优先。

> **踩坑实录30**：我们曾经把pre-filtering和post-filtering混用了——检索前过滤一次，检索后再过滤一次。结果两次过滤的条件不一致，导致一些文档第一次被放行了，第二次被拦截了。排查这个问题花了整整一天。后来我们统一成pre-filtering，post-filtering只用来做二次安全检查（检查答案中是否有敏感信息泄露）。

### 4.2 文档解析测试工具

```python
def test_document_parsing(test_files: list) -> dict:
    """文档解析测试"""
    results = []
    
    for tf in test_files:
        parsed_text = parse_document(tf.path)
        
        original_chars = len(tf.original_text)
        parsed_chars = len(parsed_text)
        retention_rate = parsed_chars / original_chars if original_chars > 0 else 0
        
        key_info_retained = all(kw in parsed_text for kw in tf.key_info)
        
        results.append({
            'file': tf.path,
            'format': tf.format,
            'original_chars': original_chars,
            'parsed_chars': parsed_chars,
            'retention_rate': retention_rate,
            'key_info_retained': key_info_retained,
            'passed': retention_rate >= 0.90 and key_info_retained
        })
    
    pass_rate = sum(1 for r in results if r['passed']) / len(results)
    
    return {
        'total': len(results),
        'passed': sum(1 for r in results if r['passed']),
        'pass_rate': pass_rate,
        'details': results
    }
```

这个工具的核心是计算信息保留率和关键信息保留情况。但实际用的时候，你需要特别注意几个点：

关键信息的提取不能靠人工一个个找。我们写了一个简单的关键信息提取器——用正则表达式匹配文档中的关键数据（金额、日期、人名等），然后把这些作为关键信息。

> **踩坑实录31**：我们的关键信息提取器一开始只匹配中文数字（如"三百元"），没匹配阿拉伯数字（如"300元"）。结果一份文档里的"住宿费300元/天"没被识别为关键信息，解析后丢失了也没被发现。后来我们扩展了正则表达式，覆盖了中文数字、阿拉伯数字、带单位的数字等所有格式。

### 4.3 知识时效性测试

```python
def test_knowledge_freshness(knowledge_base: list, max_age_days: int = 180) -> dict:
    """知识时效性测试"""
    from datetime import datetime, timedelta
    
    cutoff = datetime.now() - timedelta(days=max_age_days)
    expired_docs = []
    
    for doc in knowledge_base:
        updated_at = datetime.fromisoformat(doc['updated_at'])
        if updated_at < cutoff:
            expired_docs.append({
                'doc_id': doc['id'],
                'title': doc['title'],
                'updated_at': doc['updated_at'],
                'days_since_update': (datetime.now() - updated_at).days
            })
    
    return {
        'total_docs': len(knowledge_base),
        'expired_docs': len(expired_docs),
        'expired_rate': len(expired_docs) / len(knowledge_base) if knowledge_base else 0,
        'details': expired_docs
    }
```

这个工具用来检测过期文档。但实际用的时候，你会发现180天的默认值不一定合适。

> **踩坑实录32**：我们一开始统一用180天作为过期时间，后来发现不同类别的文档过期时间应该不一样。产品手册可能半年更新一次，但促销信息可能一周就过期了。后来我们给每类文档设置了不同的过期时间，在文档元数据里加了`expiry_days`字段。

### 4.4 答案准确性评估工具

```python
def evaluate_answer_accuracy(questions: list, expected_answers: list) -> dict:
    """答案准确性评估"""
    results = []
    
    for q, expected in zip(questions, expected_answers):
        actual = kb_system.answer(q)  # 调用知识库系统获取答案
        
        # 事实准确性：关键事实是否一致
        factual_match = check_factual_accuracy(actual, expected)
        
        # 完整性：是否覆盖了所有关键点
        completeness = check_completeness(actual, expected)
        
        # 合规性：是否包含违规内容
        compliance = check_compliance(actual)
        
        results.append({
            'question': q,
            'expected': expected,
            'actual': actual,
            'factual_match': factual_match,
            'completeness': completeness,
            'compliance': compliance,
            'overall_pass': factual_match and completeness and compliance
        })
    
    pass_rate = sum(1 for r in results if r['overall_pass']) / len(results)
    
    return {
        'total': len(results),
        'passed': sum(1 for r in results if r['overall_pass']),
        'pass_rate': pass_rate,
        'details': results
    }
```

这个评估工具的核心是三个检查：事实准确性、完整性、合规性。

事实准确性检查我们用了一个简单的方法：提取答案和标准答案中的关键事实（数字、名称、日期等），然后对比是否一致。

完整性检查用的是关键词覆盖：标准答案中的关键词，答案中至少覆盖80%。

合规性检查用的是禁止词汇表 + 大模型二次检查。

> **踩坑实录33**：事实准确性检查的时候，我们发现大模型有时候会用不同的方式表达同一个意思。比如标准答案是"住宿费500元/天"，大模型回答"每天住宿费上限为500元"。这两个意思是一样的，但我们的简单对比工具认为不匹配。后来我们加了一个语义相似度检查——用嵌入向量计算语义相似度，超过0.8就认为匹配。

## 五、注意事项：7个真实踩坑案例

### 坑一：新旧文档同时存在，系统优先检索到旧文档

**现象**：系统引用了2022年的旧文档，给出了过时的差旅费报销标准。

**根因**：文档更新流程不完善。业务部门上传了新文档，但旧文档没有被下架。向量数据库中同时存在新旧两个版本的文档，而且旧文档的向量相似度更高（因为旧文档的表述更简洁），所以系统优先检索到了旧文档。

**修复方案**：
1. 建立文档版本管理机制：每次更新文档时，自动标记旧版本为"expired"
2. 检索时只检索"active"状态的文档
3. 建立文档过期检查机制：文档超过180天未更新自动标记为"auto_expired"

```python
# 修复前：新旧文档同时存在
results = vector_db.search(query, top_k=5)  # 可能检索到旧文档

# 修复后：只检索active文档
results = vector_db.search(query, top_k=5, filter={"status": "active"})
```

**教训**：文档更新不是"上传新文档"那么简单。需要同时下架旧文档，否则新旧文档会同时被检索到，而且旧文档可能因为表述更简洁而被优先检索到。这个教训我们是用真金白银买来的——有员工按照旧标准报销，多报了钱，后来被财务追回来，员工很不满。

> **延伸思考**：除了版本管理，你还应该考虑"文档冲突检测"。当新旧文档同时存在时，系统应该发出警告，而不是静默地两个都留着。

### 坑二：权限标签默认是public，所有文档对所有人可见

**现象**：A部门的员工能看到B部门的文档，包括薪酬数据、绩效考核等敏感信息。

**根因**：权限过滤只在检索层做了，但文档上传时没有设置权限标签。导致所有文档的权限标签都是默认的"public"。检索时的权限过滤虽然存在，但因为所有文档都是public，过滤等于没做。

**修复方案**：
1. 文档上传时必须设置权限标签（部门、访问级别），不设置则拒绝上传
2. 检索时按权限标签过滤
3. 增加权限测试：每个部门随机选一个员工，测试是否能访问其他部门文档

```python
# 修复前：所有文档都是public
vector_db.insert(content)  # 没有设置权限标签

# 修复后：上传时设置权限标签
vector_db.insert(content, metadata={
    "department": "credit",
    "access_level": "department",
    "role": "manager"
})
```

**教训**：权限隔离不是"检索时过滤"那么简单。文档上传时就必须设置权限标签，否则检索时过滤就没有依据。这就像你家装了防盗门（检索过滤），但大门一直开着（上传没设权限），防盗门有什么用？

> **延伸思考**：权限标签的默认值应该是最严格的（confidential），而不是最宽松的（public）。安全领域有个原则叫"默认拒绝"——除非明确授权，否则一律拒绝。

### 坑三：GBK编码文件解析成乱码

**现象**：财务部的PDF文档解析后变成了乱码，完全无法使用。

**根因**：PDF文档使用了GBK编码，解析器按UTF-8读取。UTF-8和GBK的字节映射不同，按UTF-8读GBK编码的文件，读出来的全是乱码。

**修复方案**：增加编码检测逻辑，自动检测并适配编码。

```python
import chardet

def detect_encoding(file_path: str) -> str:
    """检测文件编码"""
    with open(file_path, 'rb') as f:
        raw_data = f.read()
    result = chardet.detect(raw_data)
    return result['encoding']

def load_text_file(file_path: str) -> str:
    """智能加载文本文件，自动检测编码"""
    encoding = detect_encoding(file_path)
    with open(file_path, 'r', encoding=encoding or 'utf-8') as f:
        return f.read()
```

**教训**：国内企业文档大量使用GBK编码，测试时必须包含GBK文件。而且chardet的检测结果不一定100%准确——有时候它会把GBK检测成GB2312，有时候会检测成Big5。所以检测完最好再加一层人工校验，或者用多种检测工具交叉验证。

> **延伸思考**：除了编码问题，你还要考虑BOM（Byte Order Mark）问题。有些UTF-8文件带BOM头（0xEF 0xBB 0xBF），解析器如果不处理BOM，文件开头会出现乱码字符。

### 坑四：扫描版PDF的OCR识别率低

**现象**：法务部门的合同扫描件解析后，关键条款识别错误率高达30%。

**根因**：扫描版PDF是图片，需要用OCR识别。但法务部门的合同扫描件质量很差——有褶皱、有阴影、有手写批注。OCR引擎对这些低质量图片的识别率很低。

**修复方案**：
1. 对扫描件进行预处理（去噪、去阴影、增强对比度）
2. 使用更先进的OCR引擎（如PaddleOCR、Tesseract 5.0）
3. 对低质量扫描件，要求业务部门重新扫描或提供电子版

**教训**：OCR不是万能的。扫描质量差的文档，再好的OCR引擎也救不回来。测试时一定要包含各种质量的扫描件，不能只用高质量的样本测试。

> **踩坑实录35**：我们测试OCR的时候，用的都是扫描仪生成的高质量扫描件。结果上线后发现，很多文档是手机拍的——光线暗、角度歪、有手指遮挡。OCR识别率直接从95%掉到了60%。后来我们加了图片质量检测，对低质量图片自动提示用户重新上传。

### 坑五：切片切断了跨页表格的内容

**现象**：一份跨页的差旅费标准表格，第一页是"国内出差"，第二页是"国际出差"。切片时把两页的内容混在一起了，国内和国际的标准全乱了。

**根因**：切片器按固定字符数切片，没有识别表格边界。跨页表格被切成了两半，然后又被拼接到了不同的切片里。

**修复方案**：
1. 切片前先识别文档结构（标题、表格、段落）
2. 表格作为一个整体单元，不跨切片切割
3. 如果表格太大，按行切割而不是按字符数切割

**教训**：切片不是简单地把文本切成等长的块。你需要理解文档的结构，尊重文档的语义边界。表格、列表、代码块这些结构化的内容，应该作为整体处理。

> **延伸思考**：你可以考虑用LLM辅助切片——让大模型先理解文档结构，然后按语义单元切片。虽然成本高一点，但切片质量会好很多。

### 坑六：大模型幻觉——编造了不存在的政策

**现象**：员工问"公司有没有弹性工作制"，系统回答"有的，弹性工作制从2023年6月开始实施，每天可以灵活安排2小时"。但实际上公司根本没有弹性工作制。

**根因**：检索到的文档中没有关于弹性工作制的内容，但大模型在生成答案时"脑补"了一个答案。这就是大模型的hallucination（幻觉）问题。

**修复方案**：
1. 在prompt中明确要求：如果检索到的文档中没有相关信息，回答"暂时没有找到相关信息"
2. 答案生成后，检查答案中的关键事实是否在检索文档中有依据
3. 设置一个"无答案阈值"——当检索相似度低于某个值时，直接回答"不知道"

**教训**：大模型天生倾向于给出一个"看起来合理"的答案，即使它不知道正确答案。你必须通过prompt engineering和后处理来约束这种行为。

> **踩坑实录36**：我们加了prompt约束之后，幻觉减少了但没完全消除。大模型很"聪明"——它会把检索文档中的信息重新组合，编造出一个"看起来合理但实际上不存在"的答案。比如文档里有"弹性工作时间"和"远程办公"两个政策，大模型把它们组合成了"弹性远程办公"，但公司根本没有这个政策。所以光靠prompt不够，还需要事实核查。

### 坑七：审计日志缺失，安全审计时被开严重不符合项

**现象**：公司通过ISO27001安全认证时，审计员要求提供知识库的审计日志——谁在什么时候查了什么。结果我们拿不出来。

**根因**：上线初期没有做审计日志功能。安全团队在审计时发现了这个问题，开了一个严重不符合项，要求限期整改。

**修复方案**：
1. 在每次用户查询时，记录：用户ID、查询时间、查询内容、检索到的文档、生成的答案
2. 审计日志存储在独立的数据库中，不能被普通用户访问
3. 提供审计日志查询接口，供安全团队使用

**教训**：审计日志不是"可有可无"的功能，而是企业知识库的"标配"。特别是金融、医疗等强监管行业，没有审计日志等于裸奔。

> **延伸思考**：审计日志本身也有安全问题——日志中包含了用户的查询内容，可能涉及敏感信息。所以日志需要加密存储，访问需要授权，而且要有日志保留策略（比如保留1年，之后自动删除）。

### 坑八：并发查询导致向量数据库性能瓶颈

**现象**：早上9点员工集中查询，系统响应时间从2秒飙升到30秒，部分请求超时。

**根因**：向量数据库是单机部署，并发查询能力有限。100个并发查询同时打过来，查询队列排满了。

**修复方案**：
1. 加查询缓存：相同问题30秒内不重复检索
2. 向量数据库升级为集群部署
3. 加限流机制：超过并发阈值时返回"系统繁忙，请稍后重试"

**教训**：性能测试不能只在实验室做，要模拟真实的使用场景。早上9点的集中查询和下午3点的零星查询，性能需求完全不同。

> **踩坑实录37**：我们做性能测试的时候，用的是均匀分布的并发请求（每秒10个请求持续10秒）。但真实场景是突发式的——早上9点整，几百个员工同时打开知识库查询。这种突发流量对系统的冲击远大于均匀流量。后来我们改了性能测试方案，加入了突发流量测试。

## 六、总结思考

### 6.1 核心要点回顾

企业知识库的测试，不只是测"能不能回答"，还要测"回答对不对"、"权限对不对"、"合不合规"、"性能行不行"、"审计全不全"。五个维度，缺一不可。

**第一性原理**：企业知识库的核心价值是"让正确的人，在正确的时间，看到正确的信息"。三个"正确"，缺一不可。

- 正确的人 = 权限隔离
- 正确的时间 = 知识时效性
- 正确的信息 = 答案准确性

### 6.2 测试检查清单

上线前，对照这个清单逐项检查：

**文档解析**
- [ ] 所有支持的格式都有测试样本
- [ ] 每种格式至少有5个不同来源的样本
- [ ] 信息保留率 >= 90%
- [ ] 关键信息100%保留
- [ ] 表格解析正确
- [ ] 编码检测覆盖UTF-8、GBK、GB2312

**切片质量**
- [ ] 切片不切断语义单元
- [ ] 表格作为整体处理
- [ ] 检索命中率 >= 85%
- [ ] 切片冗余度 <= 20%

**权限隔离**
- [ ] 权限测试矩阵覆盖所有角色-权限组合
- [ ] 边界场景测试（空值、异常值）
- [ ] 权限变更测试（调岗、晋升、离职）
- [ ] 默认权限是"拒绝"而不是"允许"

**知识时效性**
- [ ] 文档版本管理机制健全
- [ ] 过期文档自动标记
- [ ] 不同类型文档有不同过期时间
- [ ] 定期人工审核流程

**答案准确性**
- [ ] 标准问答对覆盖各种问法（标准问法+口语化问法+错别字问法）
- [ ] 事实准确性 >= 90%
- [ ] 幻觉检测机制
- [ ] 无答案时正确回复"不知道"

**合规性**
- [ ] 禁止词汇表覆盖所有违规场景
- [ ] 免责声明自动添加
- [ ] 答案合规检查（规则引擎+大模型）
- [ ] 定期合规扫描

**审计日志**
- [ ] 每次查询都有日志记录
- [ ] 日志加密存储
- [ ] 日志查询接口
- [ ] 日志保留策略

**性能**
- [ ] 正常负载响应时间 < 3秒
- [ ] 高峰负载响应时间 < 10秒
- [ ] 突发流量测试
- [ ] 限流机制

### 6.3 最佳实践

1. **安全优先**：权限隔离的默认策略是"拒绝"，不是"允许"。宁可错杀，不可放过。
2. **全链路测试**：不要只测最终答案，要从文档上传到答案生成的每个环节都设检查点。
3. **自动化优先**：知识库测试用例多、重复性高，非常适合自动化。每天自动跑一次，发现问题及时告警。
4. **真实场景测试**：不要用实验室里的完美数据测试，要用真实的文档、真实的用户问法、真实的并发模式。
5. **持续监控**：上线不是终点。上线后持续监控答案质量、权限隔离效果、知识时效性，发现问题及时修复。
6. **文档源头治理**：很多问题（如编码错误、扫描质量差、文档写错）的根因在文档源头。测试团队要推动业务部门规范文档管理。

### 6.4 思考题

1. 如果你的知识库同时存着新旧两个版本的文档，而且旧文档的向量相似度更高，你会怎么解决这个问题？除了版本管理，还有什么思路？

2. 大模型幻觉是企业知识库的顽疾。除了prompt约束和事实核查，你觉得还有什么方法可以减少幻觉？有没有可能完全消除幻觉？

3. 权限隔离的"默认拒绝"策略虽然安全，但可能导致用户体验差（比如新员工入职后看不到任何文档）。你怎么平衡安全性和易用性？

4. 审计日志记录了用户的查询内容，这本身可能涉及隐私问题。你怎么设计审计日志系统，既满足合规要求，又保护用户隐私？

5. 如果你的知识库服务于多个客户（比如SaaS模式），不同客户的数据如何隔离？向量数据库层面的多租户隔离有哪些方案？

6. 知识时效性测试中，你发现有些文档的"最佳更新周期"很难确定——比如一份公司文化文档，可能三年都不用更新；但一份产品手册，可能一个月就要更新一次。你怎么设计一个智能的文档过期预测机制？
