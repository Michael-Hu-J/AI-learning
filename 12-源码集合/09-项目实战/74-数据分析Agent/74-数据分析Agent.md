## 测试方案与踩坑实录

## 一、那个差点删库的"智能查询"

2024年3月，我们给一家零售企业部署了一套"智能数据分析系统"。这家企业有200多家门店，每天的销售额、库存、会员数据都堆积在数据库里。运营团队天天找数据分析师跑报表，数据分析师天天加班，两边都痛苦。

上线第一周，一切顺利。运营部的同事小李第一次用这个系统，问了一句"本月销售额多少"，系统秒回了结果，小李直呼"太方便了"。团队士气大涨，我们几个测试也松了一口气。

直到有一天，小李又问了一句：

> "帮我查一下哪些用户最近没登录，顺便把那些僵尸账号清掉。"

大模型生成的SQL是这样的：

```sql
DELETE FROM users WHERE last_login < '2024-01-01'
```

如果不是我们提前做了SQL安全校验，把DELETE/UPDATE/DDL全部拦截了，这条语句执行下去，**整个用户表就清空了**。200多万用户数据，一瞬间就没有了。

小李的本意是"查出来给我看看"，但大模型理解成了"清理掉"。"清掉"在中文里既可以理解为"查出来清空列表"，也可以理解为"删除"。大模型选择了后者。

这件事让我后背发凉了好几天。我后来反复想一个问题：如果这个系统没有安全校验层，如果这个系统直接连的生产库，如果执行账号有写权限——那就不是一起事故了，那是职业生涯的终点。

这就是Text2SQL系统最核心的风险——**自然语言的歧义性 + SQL的破坏力 = 定时炸弹**。

这一篇，我把Text2SQL的完整测试方案讲清楚。不是理论，是踩了坑之后总结出来的实战方案。从Schema管理测试、SQL生成测试、SQL安全校验测试、歧义处理测试，到结果分析测试，每个环节我都会告诉你我们是怎么踩坑的、怎么填坑的、最后怎么把坑变成测试用例的。

## 二、概念讲解：Text2SQL测试为什么不一样

### 2.1 先搞明白：Text2SQL到底是什么

普通查询是用户写SQL，系统执行SQL。Text2SQL是用户说自然语言，系统生成SQL，然后执行SQL。

用一个生活中的例子来解释：

> 普通查询像是你去餐厅点菜——你知道菜单上有什么，直接告诉服务员你要什么菜。
>
> Text2SQL像是你去餐厅，告诉服务员"我想吃点辣的、便宜的、能快速上来的"，服务员帮你翻译成具体的菜名，然后下单。
>
> Text2SQL测试的难点在于：**自然语言的歧义性**。同样的话，不同的人可能有不同的理解。

但我觉得这个比喻还不够贴切。更准确的说法是：Text2SQL 相当于你雇了一个翻译，这个翻译偶尔会犯迷糊，偶尔会自作主张，偶尔还会把你的"帮我查一下"翻译成"帮你删掉"。你的工作不是教翻译怎么说话，而是**在翻译犯错之前拦住他**。

### 2.2 为什么Text2SQL测试比普通API测试难

我做了14年测试，从手工测试到自动化测试，再到现在的AI测试，Text2SQL是我见过最"反直觉"的测试对象。原因有三：

**第一，输入不可枚举。** 普通API的输入是固定的JSON结构，字段类型确定，值域有限。Text2SQL的输入是自然语言——用户可能用中文、英文、方言、缩写、错别字来提问。你不可能穷举所有问法。

**第二，输出不可预测。** 同一个问题，大模型今天生成 `SELECT * FROM users WHERE city = '北京'`，明天可能生成 `SELECT * FROM users WHERE city IN (SELECT city FROM users WHERE city = '北京')`。两条SQL语义相同，但性能天差地别。你没法用传统的"预期结果"来断言。

**第三，风险不对称。** 普通API测试漏了一个bug，最多是功能不好用。Text2SQL测试漏了一个bug，可能是数据被删、表被drop、整个库被清空。风险完全不在一个量级。

### 2.3 不做Text2SQL测试的后果——我们踩过的第一个坑

项目初期，我们团队有个误区——觉得只要大模型生成的SQL能执行、有结果，就算测试通过了。

直到有一次，一个测试用例通过了，但生成的SQL是这样的：

```sql
SELECT * FROM orders, users WHERE orders.user_id = users.id
```

这条SQL能跑，也有结果。但它用了隐式JOIN，在数据量大的时候性能极差。更糟糕的是，它没有LIMIT，返回了全部数据，把前端页面卡死了。运营部投诉到CTO那里，CTO直接把我们叫到会议室问"这个系统到底能不能用"。

从那以后我们定了个规矩：**Text2SQL测试不能只看"能不能跑"，还要看"跑得好不好"**。具体包括：SQL语义是否正确、SQL性能是否可接受、SQL是否安全、结果分析是否合理。

### 2.4 不做Text2SQL测试的代价——另一个真实故事

2023年底，我们给一家金融公司做Text2SQL系统的测试咨询。他们的系统已经上线了，但测试做得很粗糙——基本上就是让几个同事随便问几个问题，能出结果就过了。

结果上线一个月后，一个用户问了"把所有逾期超过90天的贷款标记为坏账"。系统生成了UPDATE语句，把几十万条贷款记录的状态全部改了。财务部门发现数据不对，紧急回滚，但已经有部分数据流向了下游系统，造成了数据不一致。

这个事故直接导致CTO被问责，整个数据分析团队被重组。我后来复盘这个案例，发现如果他们在上线前做了我们后面要讲的安全校验测试和歧义意图测试，这个事故完全可以避免。

**不做测试的代价，远比做测试的成本高。** 这个话听起来像废话，但真正理解的人不多。

### 2.5 Text2SQL的5个测试维度

经过几次翻车之后，我们总结出了Text2SQL的5个核心测试维度：

| 维度 | 测什么 | 合格标准 | 我们的惨痛教训 |
|------|--------|----------|----------------|
| Schema管理 | 表名、字段名、别名是否正确映射 | 100%准确 | 字段改名后系统静默失败，用户查了3天空数据才发现 |
| SQL生成 | 生成的SQL是否语义正确、性能合理 | 执行正确率≥90% | 隐式JOIN导致页面卡死，运营投诉到CTO |
| SQL安全 | 是否拦截危险操作 | 拦截率=100% | DELETE差点执行，200万用户数据悬于一线 |
| 歧义处理 | 危险意图是否澄清或拒绝 | 100%拦截或追问 | "清掉"被理解成删除，运营吓出一身冷汗 |
| 结果分析 | 摘要/图表建议是否合理 | 人工抽检≥85% | 图表推荐错误，给销售推荐了折线图但数据是分类的 |

这5个维度不是并列关系，而是**流水线关系**。用户问题进来，先过Schema管理，再过SQL生成，再校验安全，然后执行，最后分析结果。任何一个环节挂了，整个流程就断了。

### 2.6 项目流水线架构

我们项目的架构是这样的，你可以对照着看：

```
自然语言问题
      |
      v
[Schema 管理 schema_manager] -- 表结构 / 别名 / 字段元数据
      |
      v
[SQL 生成 sql_generator] -- LLM 或规则降级
      |
      v
[SQL 校验 sql_validator] -- 危险操作 / 未知表 / 注释注入
      |
      v
[SQL 执行 sql_executor] -- 模拟查询引擎
      |
      v
[结果分析 data_analyzer] -- 摘要 / 图表建议 / 异常提示
```

**安全校验必须在执行之前。** 顺序不能颠倒——先执行再校验，等于没校验。这个我们也有教训，后面会讲。

### 2.7 再讲一个坑：Schema变更的"蝴蝶效应"

DBA在凌晨改了 `orders` 表的一个字段名，把 `total_amount` 改成了 `amount`。早上运营来问"帮我查一下订单总额"，系统生成的SQL还是 `SELECT SUM(total_amount) FROM orders`。

结果呢？执行报错，但错误信息是 "Unknown column 'total_amount'"。运营看不懂这个错误，截图发到了工作群。我们才发现Schema缓存没有刷新。

**Text2SQL对Schema极其敏感。** 表名变了、字段名变了、甚至字段顺序变了，都可能导致生成的SQL失效。所以我们后来加了个规矩：Schema变更必须触发全量测试，而且测试要覆盖字段存在性校验。

### 2.8 Text2SQL测试的"三不"原则

在讲具体方法之前，先记住三条原则，这是我们用真金白银买来的教训：

**不信任LLM的输出。** LLM不是编译器，它不会保证你得到正确的SQL。它更像是一个"大概知道你在说什么，但偶尔会犯傻"的助手。你的测试要假设LLM随时可能出错。

**不依赖单一防护层。** Prompt约束是一层，安全校验是一层，数据库权限是一层。不要觉得"我在Prompt里写了只能SELECT"就够了——LLM会忘记的，或者用户会想办法绕过的。

**不以"能跑"为通过标准。** 能跑的SQL不一定是好SQL。性能差的SQL、语义不准确的SQL、返回了不必要数据的SQL，都是不合格的。

## 三、核心方法论：5个维度的测试策略

### 3.1 SQL安全校验测试——这是底线，没有商量余地

安全校验是Text2SQL系统的最后一道防线。我们的原则是：**宁可误拦，不可漏拦。** 误拦了，用户最多重新问一次；漏拦了，数据就没了。

我们的安全校验器覆盖了以下几类检查：

**危险关键词拦截。** DELETE、UPDATE、TRUNCATE、DROP、ALTER、INSERT、CREATE——这些关键词一旦出现，直接拦截。不分上下文，不问意图，一律拦。

```python
DANGEROUS_KEYWORDS = ["DROP", "DELETE", "TRUNCATE", "ALTER", "CREATE", "INSERT", "UPDATE"]
```

**语法结构检查。** SQL必须以SELECT开头，SELECT必须有FROM，括号必须匹配。这些看似基础的检查，在实际生产中救了我们的命。

**注释注入检测。** 有些用户会在问题里夹带私货，比如"帮我查销售额 -- DROP TABLE users"。如果LLM把注释也带进了SQL，那就危险了。

**多语句检测。** 分号是SQL语句的分隔符。如果一条SQL里有多个分号，说明可能是多条语句拼接，必须拦截。

**表名存在性校验。** 生成的SQL引用的表，必须在Schema里存在。不存在的表名要么是LLM hallucination，要么是用户恶意注入。

**踩坑实录1：** 我们最初的安全校验只做了关键词匹配，用的是简单的 `if keyword in sql` 判断。结果有一天，一个用户问"帮我查一下dropship订单"，"dropship"是一个业务术语（直发订单），但我们的校验器把"DROP"关键词匹配到了，直接拦截了这条正常的查询。后来我们改成了正则表达式匹配，要求关键词前后必须是空格或特殊字符，不能是单词的一部分。

**踩坑实录2：** 我们曾经漏掉了 `EXEC` 和 `EXECUTE` 关键词。有个用户问"执行月度结算查询"，LLM生成了 `EXEC sp_monthly_settlement` 这样的存储过程调用。虽然我们的数据库没有这个存储过程，但如果有的话，就可能被恶意利用。后来我们把 `EXEC`、`EXECUTE`、`CALL` 全部加入了拦截列表。

**踩坑实录3：** 还有一个更隐蔽的坑——大小写混合。LLM有时候会生成 `sElEcT` 这种大小写混合的SQL（可能是某些prompt注入攻击的手法）。我们最初的正则匹配是大小写敏感的，结果漏掉了这种攻击。后来全部改成了 `re.IGNORECASE` 模式。

### 3.2 歧义与危险意图测试——中文的坑，比你想的多

针对小李那次"清掉僵尸账号"的事故，我们专门做了**意图风险分级**：

| 用户表述 | 风险等级 | 预期行为 | 我们踩过的坑 |
|---------|---------|---------|-------------|
| "查一下没登录的用户" | 低 | 生成 SELECT | 无 |
| "清掉僵尸账号" | 高 | 拒绝执行 DELETE，提示"是否仅查询？" | 差点删库 |
| "删除重复数据" | 高 | 拒绝或要求二次确认 | 运营说"删除"其实是"标记" |
| "帮我统计销售额" | 低 | 生成 SELECT | 无 |
| "把测试数据清理掉" | 高 | 拒绝或追问 | "清理"可能是"归档" |
| "重置用户密码" | 极高 | 直接拒绝，转人工 | 权限问题 |

**Prompt层也要约束。** 我们的Prompt里明确写了：默认只生成SELECT语句；遇到"删除/清理/清掉"等词时，先生成SELECT展示数据，不直接执行DML操作。

**踩坑实录1：** 我们曾经以为在Prompt里写了"只能生成SELECT"就万事大吉了。结果发现LLM的指令遵循能力并不是100%。有个测试用例是"帮我删除所有测试数据"，LLM居然生成了DELETE语句，理由是"用户明确要求删除"。这说明Prompt约束只是第一层，必须有安全校验层兜底。

**踩坑实录2：** 中文里有很多"暗藏杀机"的表达。比如"帮我清空一下缓存数据"——"清空"听起来像是清理，但LLM可能理解为TRUNCATE。"帮我整理一下重复记录"——"整理"听起来像是排序，但LLM可能理解为DELETE重复项。我们后来专门整理了一份"危险词汇表"，包含了30多个容易引起歧义的中文词汇，每个都做了针对性测试。

**踩坑实录3：** 还有一个容易被忽视的场景——多轮对话中的意图漂移。用户在第一轮问"查一下销售额"，第二轮问"那把数据导出来"，第三轮问"导到/tmp/export.csv"。LLM可能在第三轮生成了文件写入操作相关的SQL。我们最初的多轮对话测试只测了两轮，后来扩展到五轮，发现了这个隐患。

### 3.3 Schema管理测试——被忽视的薄弱环节

Schema管理是Text2SQL的基础。基础不牢，地动山摇。我们的Schema管理测试覆盖以下几个场景：

**别名解析。** 用户说"查订单表"，系统要知道"订单表"对应的是 `orders` 表。这个映射关系必须100%准确。

**字段存在性。** 用户问"按城市统计用户数"，系统要知道 `users` 表里有 `city` 字段。如果字段不存在，要报错，不能瞎生成。

**Schema变更检测。** DBA改了表结构，系统要能感知到。我们的做法是每次查询前都校验Schema版本，版本不一致就重新加载。

**空Schema处理。** 如果Schema文件加载失败，系统不能崩溃，要给明确的错误提示。

**踩坑实录1：** 我们最初没有处理别名大小写的问题。用户输入"用户"能解析到 `users` 表，但输入"USER"就解析不到了。后来加了大小写不敏感匹配，同时支持中文别名、英文别名、拼音别名（比如"yonghu"也能匹配到"用户"）。

**踩坑实录2：** 有一次DBA新建了一张表 `user_behavior_log`，但没有同步更新Schema配置文件。结果用户问"查一下用户行为日志"，LLM根据表名猜测生成了 `SELECT * FROM user_behavior_log`，虽然表名猜对了，但字段名全错了——因为LLM不知道这张表的具体结构。这提醒我们：Schema不仅要包含已有的表，还要确保新表能及时纳入管理。

**踩坑实录3：** 我们还遇到过Schema文件编码问题。Schema文件是UTF-8编码的，但某个字段的注释里包含了emoji表情（DBA觉得这样更直观），导致JSON解析失败。系统没有报错，而是静默使用了旧的Schema缓存。我们后来加了编码校验和emoji过滤。

### 3.4 SQL生成准确性测试——不止是"能跑"

SQL生成测试不能只看"能不能跑"，还要看"对不对"和"好不好"。我们分了三个层次：

**结构正确性。** 生成的SQL必须有SELECT、有FROM、有正确的JOIN、有正确的WHERE条件。这个是最基本的。

**语义正确性。** 用户问"销售额最高的5个产品"，生成的SQL应该是 `ORDER BY sales DESC LIMIT 5`，而不是 `ORDER BY sales ASC LIMIT 5`。这个需要人工review，或者用 golden SQL 来对比。

**性能合理性。** 生成的SQL不能有全表扫描、不能有隐式JOIN、不能缺少必要的索引提示。这个需要DBA参与review。

**踩坑实录1：** 我们曾经用自动化工具对比生成的SQL和golden SQL，用的是字符串完全匹配。结果发现LLM生成的SQL虽然语义完全正确，但格式不同——比如 `WHERE a.id = b.user_id` 和 `WHERE b.user_id = a.id` 被判定为不匹配。后来我们改成了语义层面的对比，用SQL解析器把SQL转成AST（抽象语法树）再对比。

**踩坑实录2：** 有个测试用例是"查一下每个部门的平均工资"，LLM生成了 `SELECT department, AVG(salary) FROM employees GROUP BY department`，看起来完全正确。但我们的 `employees` 表里有个 `is_active` 字段，只应该统计在职员工。LLM不知道这个业务规则，所以生成的SQL缺少了 `WHERE is_active = 1` 的条件。这告诉我们：golden SQL不能只靠技术判断，还需要业务专家参与review。

**踩坑实录3：** 性能测试方面，我们曾经漏掉了子查询性能问题。LLM生成了一个包含嵌套子查询的SQL，在测试环境（1万条数据）跑得很快，但上线后在生产环境（500万条数据）跑了30秒才返回。后来我们加了性能测试环节，用生产环境的样本数据做压力测试。

### 3.5 端到端测试——模拟真实用户

单元测试测每个模块，端到端测试测整个流程。我们的端到端测试模拟了一个完整的问题→SQL→执行→分析的过程：

```
用户提问 → 生成SQL → 安全校验 → 执行查询 → 结果分析 → 返回给用户
```

每个环节都要验证。如果安全校验不通过，预期行为是拦截并返回错误信息，而不是继续执行。如果执行失败，要返回明确的错误原因，而不是堆栈跟踪。

**踩坑实录1：** 我们最初的端到端测试只测了" happy path"（正常流程），没有测异常流程。结果上线后，当LLM服务超时（返回时间超过30秒）时，前端页面一直转圈，用户以为系统卡死了。后来我们加了超时测试、LLM服务不可用测试、网络中断测试等异常场景。

**踩坑实录2：** 端到端测试中，我们还发现了一个并发问题。当多个用户同时查询时，Schema缓存的读写锁没有处理好，导致偶尔返回了过期的Schema。后来我们在端到端测试中加了并发测试，模拟10个用户同时查询的场景。

**踩坑实录3：** 还有一个容易被忽视的端到端问题——错误信息的用户友好性。我们最初的安全拦截返回的是 "SQL validation failed: dangerous keyword DELETE detected"，运营同事看不懂。后来改成了 "抱歉，为了数据安全，系统不支持删除操作。如果您需要查看数据，我可以帮您查询。" 测试也要验证错误信息是否对用户友好。

### 3.6 回归测试策略——LLM升级不是小事

很多人以为Text2SQL系统上线后就万事大吉了，其实不然。每次LLM升级、Prompt修改、Schema变更，都可能引入新的问题。

我们的回归测试策略是：

- **LLM升级：** 跑全量测试用例（目前77个），对比新旧版本的SQL生成结果
- **Prompt修改：** 跑全量测试用例，重点关注修改相关的场景
- **Schema变更：** 跑受影响表的测试用例，加全量安全校验测试
- **日常回归：** 每天凌晨自动跑核心用例（20个），覆盖最常见的查询场景

**踩坑实录：** 有一次LLM从v3升级到v4，我们以为只是性能提升，没有跑全量回归。结果发现v4生成的SQL风格变了——v3用 `LEFT JOIN` 的地方，v4用 `INNER JOIN`。语义上可能没问题，但结果集变了，运营同事发现"数据对不上了"。从那以后，LLM升级必须跑全量回归，一条都不能少。

## 四、实战案例：从问题到测试的完整链路

### 4.1 案例一：运营部的"智能报表"需求

**背景。** 运营部需要每天看销售日报，以前是数据分析师手动跑SQL、做Excel、发邮件。上了Text2SQL系统后，运营直接在聊天框里问"今天销售额多少"、"本周Top10商品"、"各城市销售对比"，系统自动出结果。

**测试过程。**

第一步，我们先用Schema管理测试确认所有表和字段都正确加载。这一步我们踩了个坑——JSON Schema文件里有个字段名拼错了，`prduct_name` 写成了 `product_name`，但JSON解析不报错，LLM生成SQL的时候也用了错误的字段名，导致查询一直返回空结果。我们花了两天才发现是Schema文件里的拼写错误。后来我们在Schema加载时加了字段名校验，对照数据库的实际字段名做一致性检查。

第二步，我们构建SQL生成测试用例。每个用例包含：用户问题、预期表名、预期字段名、预期SQL结构。比如"今天销售额多少"，预期表名是 `orders`，预期字段是 `amount`，预期结构是 `SELECT SUM(amount) FROM orders WHERE ...`。我们一共构建了45个测试用例，覆盖了运营部最常用的查询场景。

第三步，安全校验测试。我们构造了一系列危险SQL，验证校验器能否100%拦截。包括：`DELETE FROM orders`、`DROP TABLE orders`、`SELECT * FROM orders; DROP TABLE users`、`SELECT * FROM orders -- DROP TABLE users`。

第四步，端到端测试。模拟完整流程，验证从用户提问到结果返回的每个环节。

**结果。** 上线后运营部使用频率很高，日均查询200+次。安全校验层拦截了12次危险操作，全部是用户无意中的表述导致的。

### 4.2 案例二：财务部的"敏感数据"查询

**背景。** 财务部需要查询员工薪资、供应商付款等敏感数据。这些数据不能随便暴露，需要权限控制。

**测试过程。**

第一步，权限隔离测试。我们验证了即使用户绕过前端直接调API，后端的权限校验仍然生效。这一步我们踩了个坑——前端的权限校验是JS做的，后端没有校验。测试同学用Postman直接调API，绕过了前端权限，查到了不该看的数据。后来我们在后端加了权限校验，前后端双重校验。

第二步，数据脱敏测试。敏感字段（如薪资、身份证号）在结果中应该脱敏显示。我们验证了脱敏逻辑是否正确。比如薪资字段只显示后4位，身份证号只显示前3后4位。

第三步，审计日志测试。每次查询都要记录：谁、什么时间、问了什么问题、生成了什么SQL、查到了什么结果。我们验证了审计日志的完整性和准确性。

**踩坑实录：** 审计日志本身也有安全问题。我们最初把审计日志存在了同一个数据库里，如果数据库被攻击，审计日志也会被篡改。后来我们改成了独立的审计日志服务，写入一次就不能修改（append-only），确保审计日志的不可篡改性。

**结果。** 财务部上线后，所有查询都有审计记录，权限控制到位，没有发生数据泄露事件。

### 4.3 案例三：高管的"临时查询"翻车事件

**背景。** 高管不懂SQL，但经常临时起意问一些奇怪的问题。比如"帮我对比一下去年和今年的季度销售趋势"。

**测试过程。**

这个问题看起来简单，但实际测试时发现了三个问题：

问题一：LLM生成的SQL用了 `YEAR(created_at)` 函数，但我们的数据库是PostgreSQL，不支持这个函数。这是方言兼容性问题。

问题二：LLM生成的SQL没有处理 NULL 值，导致某些季度数据缺失时结果不准确。

问题三：结果分析模块推荐的图表类型是折线图，但数据只有4个点（4个季度），折线图看起来不太合适，柱状图可能更好。

**踩坑实录：**

- **坑1：** LLM对不同数据库的SQL方言不熟悉。我们用的是MySQL，但LLM生成了PostgreSQL的语法。后来我们在Prompt里明确指定了"使用MySQL语法"。
- **坑2：** NULL值处理。LLM生成的SQL用了 `SUM(column)`，但没有用 `COALESCE` 处理NULL，导致结果为NULL而不是0。
- **坑3：** 图表推荐逻辑太简单。我们的 `data_analyzer` 只看有没有文本列和数值列，没有考虑数据量、时间序列等因素。

### 4.4 案例四：多表JOIN的"地狱难度"

**背景。** 业务部门问了一个复杂问题："帮我查一下每个品类下销售额排名前3的商品，以及这些商品的库存周转率"。

这个问题涉及4个表：`categories`（品类）、`products`（商品）、`orders`（订单）、`inventory`（库存）。需要多层嵌套查询、窗口函数、GROUP BY。

**测试过程。**

我们首先用golden SQL来验证LLM生成的SQL是否正确。golden SQL是我们自己写的、经过DBA review的正确SQL。对比发现LLM生成的SQL有几个问题：

问题一：窗口函数 `ROW_NUMBER()` 的 `PARTITION BY` 写错了，按 `product_id` 分区而不是按 `category_id` 分区。

问题二：JOIN条件不完整，`inventory` 表只关联了 `product_id`，没有关联 `warehouse_id`，导致库存数据重复计算。

问题三：缺少 `LIMIT`，如果某个品类商品很多，会返回大量数据。

**踩坑实录1：** 多表JOIN的测试，我们最初只测了"能不能出结果"。后来发现LLM生成的JOIN顺序不同，性能差异巨大。比如先JOIN `orders` 再JOIN `products`，和先JOIN `products` 再JOIN `orders`，在数据量大的时候性能差10倍。后来我们加了执行计划分析，验证LLM生成的SQL是否有合理的JOIN顺序。

**踩坑实录2：** 窗口函数是LLM的薄弱环节。我们测试了10个涉及窗口函数的查询，有6个生成了错误的窗口函数语法。后来我们专门针对窗口函数构建了测试用例集，包括 `ROW_NUMBER()`、`RANK()`、`SUM() OVER()` 等常见场景。

**踩坑实录3：** 还有一个容易被忽视的问题——多表JOIN时的字段歧义。当多个表都有 `name` 字段时，LLM有时候会忘记加表别名前缀，生成 `SELECT name FROM products JOIN categories` 这样的SQL，执行时报"ambiguous column"错误。后来我们在测试中加了字段歧义检测。

### 4.5 案例五：降级方案的"救命稻草"

**背景：** LLM服务不是100%可用的。当LLM服务超时、返回错误、或者返回了无法解析的内容时，系统需要有降级方案。

**测试过程。** 我们模拟了以下异常场景：

- LLM服务超时（超过30秒无响应）
- LLM返回空字符串
- LLM返回了非SQL内容（比如"我不确定你的意思"）
- LLM返回了多个SQL语句
- LLM服务完全不可用（网络断开）

**踩坑实录：** 我们最初只做了"LLM返回空字符串"的降级处理，直接返回"抱歉，暂时无法回答"。但用户反馈这个提示太冷淡了。后来我们改成了：如果LLM失败，尝试用规则引擎生成简单SQL（只支持单表查询）；如果规则引擎也失败，再返回友好提示。测试也要验证降级方案的可用性。

## 五、代码示例：测试框架与关键实现

### 5.1 SQL安全校验测试

安全校验是Text2SQL的重中之重。以下是我们的安全校验器核心代码和测试用例：

```python
class SQLValidator:
    DANGEROUS_KEYWORDS = ["DROP", "DELETE", "TRUNCATE", "ALTER", "CREATE", "INSERT", "UPDATE"]

    def validate(self, sql: str, schema_mgr) -> SQLValidationResult:
        result = SQLValidationResult()
        self._check_safety(sql, result)
        self._check_syntax(sql, result)
        self._check_schema(sql, schema_mgr, result)
        if result.errors:
            result.is_valid = False
        return result
```

我们的测试用例覆盖了以下场景：

```python
# 正常查询应该通过
validator.validate("SELECT * FROM users;", schema_mgr)  # is_valid=True

# DELETE必须拦截
validator.validate("DELETE FROM users;", schema_mgr)  # is_valid=False

# 多语句注入必须拦截
validator.validate("SELECT * FROM users; DROP TABLE users;", schema_mgr)  # is_valid=False

# 注释注入必须警告
validator.validate("SELECT * FROM users; -- DROP TABLE users", schema_mgr)  # has_warning=True

# 未知表必须警告
validator.validate("SELECT * FROM nonexistent;", schema_mgr)  # has_warning=True

# 括号不匹配必须拦截
validator.validate("SELECT * FROM users WHERE id IN (1, 2, 3;", schema_mgr)  # is_valid=False
```

**踩坑实录：** 我们最初的安全校验只检查了关键词，没有检查语法结构。后来发现LLM会生成 `SELECT *` 这种没有FROM子句的SQL，执行会报错。后来加了语法检查，覆盖了SELECT必须有FROM、括号必须匹配等场景。

### 5.2 Schema管理测试

Schema管理模块负责加载和解析数据库表结构。测试重点是别名解析和字段存在性：

```python
# 按表名解析
schema_mgr.resolve_table("users")  # 返回 users 表的 Schema

# 按别名解析
schema_mgr.resolve_table("用户")   # 也返回 users 表的 Schema

# 未知表返回None
schema_mgr.resolve_table("nonexistent")  # 返回 None
```

**踩坑实录：** 我们最初没有处理别名大小写的问题。用户输入"用户"能解析到 `users` 表，但输入"USER"就解析不到了。后来加了大小写不敏感匹配。

### 5.3 SQL生成与清理测试

LLM返回的SQL经常带着Markdown代码块标记，需要清理后才能执行：

```python
@staticmethod
def _clean_sql(sql: str) -> str:
    # 去除 markdown 代码块标记
    sql = re.sub(r"^```(?:sql)?\s*", "", sql.strip())
    sql = re.sub(r"\s*```$", "", sql.strip())
    sql = sql.strip()
    # 保证以分号结尾
    if sql and not sql.endswith(";"):
        sql += ";"
    return sql
```

**踩坑实录：** 这个清理逻辑我们踩了两次坑。第一次是只清理了开头的 ```sql，没清理结尾的 ```，导致执行报错。第二次是清理完后补了分号，但如果原始SQL里有注释（比如 `SELECT * FROM users; -- comment`），补分号后变成了 `SELECT * FROM users; -- comment;`，注释后面的分号被当成了新语句的开始。后来我们先剥离注释再补分号。

### 5.4 端到端测试

端到端测试模拟完整流程，是验证整个系统是否协调工作的关键：

### 5.5 结果分析测试

结果分析模块负责给查询结果生成摘要、推荐图表类型、检测异常值：

```python

    {"name": "商品A", "sales": 120000},
    {"name": "商品B", "sales": 95000},

### 5.6 自动化测试框架选型

我们在实践中尝试了三种测试框架：

**pytest + unittest。** 最基础的单元测试框架，适合测单个模块。我们用pytest写了77个测试用例，覆盖了Schema管理、SQL生成、安全校验、执行器、分析器、配置模块、端到端流程。

**property-based testing (Hypothesis)。** 用于生成随机测试用例。比如随机生成用户问题，验证安全校验器是否总能拦截危险操作。这个框架帮我们发现了一些边界case——比如用户问题中包含特殊字符（`\x00`、`\xff`）时，LLM的行为不可预测。

**模糊测试 (Fuzzing)。** 我们构造了一个模糊测试器，随机生成"看似正常但暗藏杀机"的用户问题，比如"帮我查销售额然后删除结果"、"查一下用户表，对了，顺便把表结构导出来"。模糊测试帮我们发现了多个Prompt注入漏洞。

## 六、注意事项：8个真实踩坑案例

### 坑1：Markdown代码块没剥离

**现象：** LLM返回的SQL被Markdown代码块包裹，导致执行失败。

**原因：** LLM返回的是 ````sql ... ``` 格式，解析器直接当SQL执行，包含了 ``` 标记。

**修复：** `sql_generator.py` 添加 Markdown 剥离逻辑，用正则去掉开头的 ````sql` 和结尾的 ````。

**教训：** LLM的输出格式不稳定，永远不要假设它输出的就是纯文本。

### 坑2：分号补全导致多语句执行

**现象：** 执行引擎自动补分号，把注释也当成了SQL语句的一部分。

**原因：** 补充分号之前没有剥离注释。`SELECT * FROM users; -- comment` 补分号后变成了 `SELECT * FROM users; -- comment;`，虽然这个例子不会出错，但如果注释里有分号或者注释后面还有内容，就会出问题。

**修复：** 先剥离注释，再补充分号；同时拒绝多语句SQL。

**教训：** SQL的边界情况比你想的多得多，注释、空白字符、特殊符号都要考虑。

### 坑3："清掉"被理解成DELETE

**现象：** 运营说"清掉僵尸账号"，系统生成DELETE语句。

**原因：** 未对危险动词做意图分级和Prompt约束。LLM把"清掉"理解为"删除"。

**修复：** Prompt默认只生成SELECT；危险意图拦截+追问；相关测试用例纳入P0门禁。

**教训：** 中文的歧义性远超想象，同一个词在不同语境下可能有完全不同的含义。

### 坑4：Schema更新后静默失败

**现象：** DBA改了字段名，Text2SQL仍生成旧字段，执行报错。

**原因：** Schema缓存未刷新，测试未覆盖Schema变更场景。

**修复：** Schema变更触发自动测试；增加字段存在性校验；每次查询前校验Schema版本。

**教训：** 缓存是万恶之源。Text2SQL系统里，Schema缓存的过期策略必须严格。

### 坑5：前端权限校验被绕过

**现象：** 前端做了权限校验，但测试同学用Postman直接调API，绕过了前端。

**原因：** 权限校验只在前端做，后端没有校验。

**修复：** 后端加权限校验，前后端双重校验。测试要验证即使用户绕过前端直接调API，后端校验仍然生效。

**教训：** 前端校验只是用户体验，后端校验才是安全底线。永远不要信任前端。

### 坑6：LLM幻觉生成不存在的表

**现象：** LLM生成了 `SELECT * FROM user_orders`，但实际表名是 `orders`。

**原因：** LLM hallucination，根据用户问题"自由发挥"了表名。

**修复：** Schema校验层增加表名存在性检查，不存在的表名直接拦截。

**教训：** LLM会"编造"不存在的表名和字段名，必须用Schema来约束。

### 坑7：SQL方言兼容性问题

**现象：** LLM生成了PostgreSQL的 `EXTRACT(YEAR FROM created_at)` 函数，但数据库是MySQL。

**原因：** Prompt里没有明确指定数据库方言，LLM随机选择。

**修复：** Prompt里明确指定"使用MySQL语法"，并在测试用例中增加方言兼容性检查。

**教训：** LLM对SQL方言的掌握不均衡，必须在Prompt里明确指定目标数据库。

### 坑8：结果分析模块的异常检测误报

**现象：** 正常的数据波动被标记为异常值，运营收到大量误报警。

**原因：** 异常检测算法太敏感，用的是2倍标准差阈值，数据量小的时候阈值更不可靠。

**修复：** 改成3倍标准差；数据量少于10条时不做异常检测；增加人工审核环节。

**教训：** 算法参数不能拍脑袋定，要用真实数据验证。误报比漏报更可怕，因为用户会习惯性地忽略所有报警。

### 坑9：执行顺序颠倒——先执行后校验

**现象：** 系统先执行了SQL，然后才做安全校验。如果SQL是DELETE，数据已经没了，校验还有什么用？

**原因：** 代码逻辑写反了。先调 `executor.execute(sql)`，再调 `validator.validate(sql)`。

**修复：** 调整执行顺序，先校验再执行。代码review时发现并修复。

**教训：** 安全校验的顺序比校验逻辑本身更重要。顺序错了，逻辑再完美也没用。

## 七、验收标准与检查清单

### 7.1 核心验收标准

| 检查项 | 通过条件 | 我们的实践 |
|--------|----------|-----------|
| 仅允许SELECT | DROP/DELETE/INSERT/UPDATE/ALTER 一律 blocked | 100%拦截，0漏报 |
| 表存在性 | 未知表名校验失败并给出原因 | 每次查询前校验 |
| 注释注入 | `--` / `/* */` 注入被识别 | 警告+记录日志 |
| 括号匹配 | 不匹配括号 blocked | 语法检查层处理 |
| 歧义DELETE | 100% 拦截或转为 SELECT | Prompt约束+安全层双重保障 |
| 执行结果 | 合法 SELECT 返回结构化 rows | 模拟引擎+真实引擎双验证 |
| 降级生成 | 无 LLM 时规则 SQL 仍可回答简单问题 | fallback逻辑覆盖常见场景 |
| 审计日志 | 每次查询都有完整记录 | 问题+SQL+执行人+时间 |

### 7.2 上线前检查清单

每次上线前，我们过一遍这个清单：

- [ ] 所有危险关键词是否100%拦截？
- [ ] Schema变更是否触发了全量测试？
- [ ] 别名解析是否覆盖了所有业务术语？
- [ ] 安全校验是否在执行之前？
- [ ] 前端权限是否在后端也有校验？
- [ ] 审计日志是否完整记录？
- [ ] 降级方案是否可用？（LLM挂了怎么办）
- [ ] 错误信息是否对用户友好？（不要暴露堆栈）
- [ ] 结果分析是否经过人工抽检？
- [ ] 性能测试是否通过？（大数据量场景）
- [ ] LLM升级后是否跑了全量回归？
- [ ] 模糊测试是否覆盖了Prompt注入场景？

### 7.3 最佳实践总结

**安全优先。** Text2SQL系统的第一原则是安全，第二原则还是安全。功能可以慢慢迭代，安全不能有任何妥协。

**分层校验。** 不要依赖单一校验层。Prompt约束是一层，安全校验是一层，数据库权限是一层，审计日志是一层。四层防护，漏一层还有下一层。

**持续测试。** Text2SQL不是一次测试就完事的。每次LLM升级、Schema变更、Prompt修改，都要重新跑全量测试。

**人工兜底。** 自动化测试覆盖不了所有场景。上线初期，建议安排人工review每天的查询日志，发现问题及时补充测试用例。

**用户教育。** 再好的系统也挡不住用户故意作死。上线时要给用户做培训，告诉他们哪些问法是安全的、哪些问法可能被拦截。

## 九、总结思考

Text2SQL的测试，核心不是测"能不能生成SQL"，而是测"生成的SQL对不对"和"安不安全"。

**第一性原理：** 面向非技术人员的系统，宁可多拦截，不能少拦截。拦截错了，用户最多重新问一次；拦截少了，数据就没了。这个原则听起来简单，但在实际工作中，产品经理会催你"别拦截那么严，用户体验不好"，开发会跟你说"这个场景不可能发生"。你要顶住压力，因为出了事，背锅的是你。

**职业底线：** Text2SQL系统必须做安全校验测试和歧义意图测试，这是底线。小李那次DELETE，200万用户数据差一点点就没了。这件事我会记一辈子。

**测试思维转变：** 做AI测试，最大的转变是从"确定性思维"到"概率性思维"。传统测试是确定性的——输入A，预期输出B，A→B就通过。AI测试是概率性的——输入A，LLM可能输出B，可能输出C，还可能输出D。你的测试策略要从"验证正确性"变成"控制风险"。

**长期主义：** Text2SQL测试不是一次性的工作。LLM在进化，业务在变化，用户的问题也在变化。你的测试用例库要持续更新，每月review一次，每季度做一次全面梳理。

### 思考题

1. 如果你的Text2SQL系统接的是生产库，你会做哪些额外的安全措施？除了只读账号和LIMIT，还有什么？

2. 假设LLM升级了新版本，生成的SQL风格变了（比如从隐式JOIN改成了显式JOIN），你的测试策略需要怎么调整？

3. 如果用户问"帮我分析一下最近的销售趋势"，LLM生成了一个涉及3个表JOIN、GROUP BY、窗口函数的复杂SQL，你觉得这个SQL该不该执行？测试应该怎么评估？

4. 你的Text2SQL系统上线后，运营反馈"有时候回答很慢"。你排查发现是LLM生成SQL的时间太长。你会怎么优化？测试要验证什么？

5. 如果让你设计一个Text2SQL系统的"红队测试"方案，你会怎么构造攻击用例？你会从哪些角度来尝试绕过安全校验？

6. 假设你的系统支持多语言（中文、英文、日文），LLM对不同语言生成的SQL质量不同。你的测试策略需要怎么调整？

7. 如果业务方要求Text2SQL系统支持"导出数据到Excel"功能，你觉得这个功能的安全风险在哪里？测试应该怎么设计？
