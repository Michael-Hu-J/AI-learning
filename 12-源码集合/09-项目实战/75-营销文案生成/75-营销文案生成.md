## 常见问题

### 坑一：合规词库更新不及时

**现象**：系统上线后，广告法新增了"国家级"作为禁用词，但我们的词库没有同步更新，导致一条使用了"国家级原料"的文案通过了检查。

**排查**：合规词库是项目启动时一次性导入的，之后没有维护机制。法规更新了，系统不知道。

**教训**：合规词库必须有定期更新机制。我们后来接入了法规变更的 RSS 订阅，每次法规更新自动触发词库同步，并重新跑一遍回归测试。

### 坑二：不同平台的合规标准不一样

**现象**：同一条文案在朋友圈发布没问题，但在电商平台却被平台审核拒绝了。原因是电商平台的审核标准比广告法更严格。

**排查**：我们的合规检查只做了广告法层面的通用检查，没有考虑各平台的特殊规则。

**教训**：合规检查要分层。第一层是法律法规的通用检查，第二层是各平台的特殊规则检查。我们在平台适配层增加了平台规则校验。

### 坑三：多样性评估形同虚设

**现象**：系统生成了三个版本的文案，多样性分数显示 0.8，但人工一看，三个版本只是换了几个同义词，内容结构完全一样。

**排查**：我们的多样性计算用的是字符级 n-gram 相似度，模型学会了用同义词替换来"欺骗"相似度计算，但实际内容没有变化。

**教训**：字符级相似度不够，后来我们加上了语义层面的多样性评估，用嵌入向量计算语义距离，同时保留人工抽检。

## 测试方案与踩坑实录

## 一、概念讲解：为什么营销文案生成值得专门讲测试

### 1.1 从一条差点让我们被请去喝茶的文案说起

去年我们给一个保健品客户做营销文案生成系统。产品经理觉得这个场景简单，不就是把产品信息填进去让模型生成文案嘛。测试团队也觉得简单，跑了十几条用例就上线了。

上线第一周，系统生成了这样一条文案："本产品经临床验证，有效率高达 98%，三天见效，无效退款。"

客户那边直接用了。结果第二天，市场监管局就找上门了。广告法明确规定，保健品广告不能含有有效率、治愈率等表述，更不能承诺退款。那条文案里三条红线全踩了。

那次事件之后，我在复盘会上拍了桌子：**文案生成系统的合规检查不是锦上添花，是保命符。** 模型可不管什么广告法，你让它写它就敢写。大模型的本质是"续写"，它不知道什么叫违法，什么叫虚假宣传，它只知道你让它写得有吸引力，它就把所有能想到的词全堆上去。

这也是为什么营销文案生成的测试，跟其他 AI 应用的测试完全不一样。聊天机器人回答错了，用户关掉就行；但文案一旦发布出去，那就是公共事件，工商局找上门来，罚款是小事，品牌声誉受损是大事。

### 1.2 营销文案生成到底在做什么

简单说，就是让大模型扮演一个"营销文案撰稿人"的角色。你给它产品信息（名称、卖点、价格、目标人群），它给你输出可以直接投放的广告文案。

但这里面有几个关键点，很多团队一开始都没想清楚：

**第一，文案不是随机出稿。** 好的营销文案是有策略的——针对什么人群、用什么语气、在什么平台发布、希望用户看完之后做什么动作。这些策略都要通过 Prompt 传递给模型。你 Prompt 写得模糊，模型输出的文案就模糊。

**第二，一次生成多个版本是刚需。** 为什么？因为没有人能提前知道哪个文案效果好。行业内通行的做法是同时生成 3-5 个版本，通过 A/B 测试来验证哪个转化率高。如果你的系统一次只出一个文案，那等于把命交给运气。

**第三，合规检查是独立环节，不能依赖模型的"自觉"。** 很多团队觉得，我在 Prompt 里写一句"请遵守广告法"就行了。我告诉你，没用。模型在生成文案的时候，注意力全在"写得有吸引力"上，你那句合规提醒它可能直接忽略。合规检查必须是一个独立的、强制执行的模块。

### 1.3 系统的完整流水线

我们的文案生成系统不是简单的 Prompt 调用，而是一个多阶段流水线：

```
产品信息输入 → 受众画像分析 → 风格策略选择 → 多版本生成 → 合规检查 → 质量评估 → A/B测试分发 → 效果回收
```

每个环节都有各自的测试重点：

- **产品信息输入**：测试输入边界——信息不全怎么办？信息矛盾怎么办？
- **受众画像分析**：测试画像匹配度——给老年人推的产品用了年轻人的语气，这就是事故
- **风格策略选择**：测试风格一致性——选了"幽默"风格，结果文案一本正经
- **多版本生成**：测试版本差异度——三个版本长得一样，等于没生成
- **合规检查**：这是最关键的，后文会详细讲
- **质量评估**：测试评分准确性——评分高的文案真的比评分低的好吗？
- **A/B 测试分发**：测试流量分配公平性
- **效果回收**：测试数据准确性

**踩坑实录 1**：我们一开始只测了"正常输入"的场景，后来发现用户经常只填产品名称不填卖点。模型遇到这种情况，就会自己编卖点。有一次它给一款普通茶叶编了"降血压、降血脂"的功效，直接违反广告法。后来我们加了一个输入校验环节，卖点为空时拒绝生成，强制用户补全。

**踩坑实录 2**：受众画像分析这个环节，我们最开始觉得是多余的——产品类别不就够了吗？后来发现同一个产品在不同人群中的表达方式差异巨大。比如一款护肝片，给中年男性推要强调"应酬必备"，给年轻女性推要强调"熬夜救星"。画像不准，文案就白写。

**踩坑实录 3**：风格策略选择这块，我们定义了 5 种风格（正式、幽默、情感、促销、科普），但测试时发现模型对"幽默"的理解跟我们不一样。我们想要的幽默是"俏皮但不低俗"，模型输出的幽默是"段子手附体"，把产品本身都忘了。后来我们在 Prompt 里加了负面示例——"不要写成纯段子，必须包含产品信息"，这才好点。

## 二、核心方法论：营销文案生成的测试框架

### 2.1 三层测试体系

营销文案生成的测试，我把它分成三层：合规层、质量层、效果层。这三层缺一不可，而且顺序不能乱。

**第一层：合规层——能不能发？**

这是底线。不管文案写得再好，不合规就是零分。合规检查要覆盖三个维度：

- **法律法规**：广告法、消费者权益保护法、行业特定法规（比如保健品的《保健食品管理办法》、金融的《广告法》金融条款）
- **平台规则**：微信朋友圈、微博、抖音、淘宝各有各的审核标准，平台规则往往比法律更细更严
- **品牌调性**：有些词不违法，但不符合品牌形象。比如一个高端品牌用了网络流行语，合规但不调性

**踩坑实录 4**：我们曾经用了一个第三方合规检查 API，结果它只检查了广告法的通用条款，没有覆盖行业特定条款。保健品客户用这个 API 检查完的文案，照样被市场监管局罚了。后来我们干脆自己维护词库，虽然麻烦，但可控。

**踩坑实录 5**：平台规则这块，我们踩的坑是"抖音和朋友圈的规则混为一谈"。抖音对"引导关注"类表述特别敏感，比如"关注我了解更多"这种话在朋友圈没事，在抖音可能被限流。我们后来给每个平台单独建了一套规则。

**踩坑实录 6**：品牌调性检查最难自动化。我们试过让模型自己判断"这条文案是否符合高端品牌调性"，结果模型对自己的输出总是打高分。后来我们换了一个模型专门做调性评估，相当于让"裁判"和"运动员"分开，这才靠谱。

### 2.2 质量评估的五个维度

合规通过了，接下来评估质量。我们用了五个维度：

| 维度 | 说明 | 自动化程度 |
|------|------|-----------|
| 信息完整度 | 产品名称、卖点、价格是否都包含了 | 高，可以自动检查 |
| 卖点覆盖 | 所有卖点是否都有体现，不是只提了一两个 | 中，部分可以自动 |
| 行动号召 | 有没有引导用户行动的表述（购买、扫码、了解等） | 高，关键词匹配 |
| 平台适配 | 字数、格式是否符合平台要求 | 高，规则明确 |
| 风格一致性 | 生成的文案是否符合指定的风格 | 低，需要人工或模型评估 |

前四个维度自动化程度高，第五个风格一致性是最头疼的。

**踩坑实录 7**：我们之前用模型自己评估自己的输出，相当于学生自己批改自己的考卷。模型给自己的文案打了 95 分，人工一看，那文案平淡得像说明书。后来我们引入了交叉评估——用另一个独立的模型来打分，分数立刻就真实了。

### 2.3 多样性评估：不只是"不一样"

多样性评估的目的是确保生成的多个版本之间有实质性的差异，而不是简单的同义词替换。

我们试过三种方法：

- **字符级 n-gram 相似度**：计算最便宜最快，但最容易被"骗"。模型把"非常好"换成"特别棒"，字符相似度就降了，但内容没变。
- **词向量余弦相似度**：好一些，能识别同义词，但对句式变化不敏感。
- **语义嵌入向量相似度**：目前最好的方案，用 Sentence-BERT 之类的模型把文案转成向量，然后算距离。但成本高、速度慢。

我们的实际做法是：先用字符级 n-gram 做快速初筛，把明显重复的过滤掉；然后用语义嵌入向量做精筛；最后人工抽检 10%。

**踩坑实录 8**：多样性分数和人工感受经常不一致。系统显示多样性 0.8（很高），但人工一看三个版本结构完全一样，只是开头换了个词。后来我们加了结构多样性检查——比较文案的段落结构、论点顺序、修辞手法，这才跟人工判断对齐了。

### 2.4 A/B 测试的设计原则

A/B 测试是验证文案效果的最终环节。设计上有几个要点：

- **样本量要够**：每个版本至少 500 次展示，否则数据没有统计意义。我们一开始每个版本只给了 100 次展示，结果两个版本的转化率分别是 2.0% 和 2.5%，看着差了不少，但统计检验发现 p 值 0.35，完全不显著。
- **流量分配要公平**：每个版本的展示量应该大致相等。我们遇到过流量分配不均的情况——版本 A 展示了 800 次，版本 B 只展示了 200 次，原因是分发算法有 bug，偏向了新版本。
- **测试周期要合理**：太短看不出趋势，太长浪费流量。一般 3-7 天比较合适。我们有一次测试只跑了 1 天就下结论，后来发现那天的流量结构跟平时不一样（周末 vs 工作日），结论完全不准。

**踩坑实录 9**：A/B 测试的"新奇效应"——新文案刚上线时点击率会偏高，因为用户没见过。我们有一次把一个新文案的初期高点击率当成了"效果好"，全量推送了，结果一周后点击率跌回正常水平。后来我们加了"观察期"，至少跑 3 天再看数据。

## 三、实战案例：从保健品到金融产品的跨行业测试

### 3.1 案例一：保健品文案生成

这是我们的第一个客户，也是踩坑最多的。

**背景**：客户是一家保健品公司，主要产品是维生素C泡腾片、鱼油、益生菌等。需要在微信朋友圈、抖音、电商平台三个渠道自动生成营销文案。

**测试策略**：

第一步，我们建立了一个覆盖保健品行业的禁用词库。广告法里的通用禁用词（最、第一、绝对等）只是基础，更重要的是保健品特有的禁用词：

- 有效率、治愈率、根治、永不复发
- 三天见效、七天改善、一周有效
- 纯天然无副作用、包治百病
- 临床验证（需要标注研究机构和结论）
- 专家推荐（需要标注专家姓名和资质）

第二步，我们设计了覆盖各个禁用词类别的测试用例，每个词至少 3 个变体。比如"最有效"、"效果最好"、"最好的选择"都要能检测出来。

第三步，我们做了跨平台适配测试。同一条文案，在微信朋友圈能通过，在抖音可能被拒，在电商平台可能又被拒。我们建了一个矩阵来管理这些差异：

| 文案类型 | 微信朋友圈 | 抖音 | 电商平台 |
|---------|----------|------|---------|
| 含"有效率" | 拒绝 | 拒绝 | 拒绝 |
| 含"天然" | 通过 | 需标注来源 | 需标注来源 |
| 含"专家推荐" | 需标注资质 | 拒绝 | 需标注资质 |
| 含"限时优惠" | 通过 | 通过 | 需标注时限 |

**踩坑实录 10**：保健品文案最容易踩的坑是"暗示疗效"。模型不会直接写"治疗XX病"，但它会写"改善睡眠质量"、"增强免疫力"——这些看起来没问题，但在保健品的语境下，就是暗示疗效。我们一开始的词库没覆盖这些"软性疗效表述"，后来加了几十个类似的词组。

**踩坑实录 11**：价格表述也是个坑。模型喜欢写"原价 299，现价 99"，但广告法要求"原价"必须是本次促销前七日内在本交易场所成交的有交易票据的最低交易价格。我们后来在合规检查里加了价格表述的规则——如果用了"原价"，必须同时标注原价的依据。

**踩坑实录 12**：还有一个很隐蔽的坑——"用户评价"。模型生成的文案里经常出现"用户反馈效果很好"这种话。广告法要求用户评价必须真实可查，不能虚构。我们后来要求所有包含用户评价的文案，必须标注评价者的真实身份（如"来自北京的张先生"），否则一律拒绝。

### 3.2 案例二：金融产品文案生成

金融产品的合规要求比保健品更严，而且更复杂。

**背景**：客户是一家互联网金融公司，主要产品是理财产品、消费贷、信用卡。需要生成适合微博、微信朋友圈、APP 内推送的文案。

**金融行业的特殊禁用词**：

- 稳赚不赔、保本保息、零风险
- 年化收益固定、 guaranteed（中英文都要查）
- 绝对安全、内部渠道
- 日息低至 X%（需要标注年化利率）

**踩坑实录 13**：金融文案最容易出问题的是利率表述。模型会写"日息仅 0.05%"，看起来很低的数字，但折合年化利率是 18.25%。监管要求必须同时展示年化利率。我们后来在合规检查里加了利率换算和校验的逻辑。

**踩坑实录 14**：金融产品的风险提示是强制要求的。模型生成的文案经常忘记加风险提示。我们后来在 Prompt 里强制要求每条文案末尾加上风险提示语，并在合规检查里验证是否包含。

**踩坑实录 15**：还有一个坑是"对比竞品"。模型有时候会写"比 XX 银行利率更低"，这种对比性表述在金融广告里是严格限制的。我们后来在词库里加了竞品对比检测。

### 3.3 案例三：教育产品文案生成

教育产品的核心问题是"承诺效果"。

**背景**：客户是一家在线教育机构，主要产品是考研培训、英语培训、职业证书培训。

**教育行业的特殊禁用词**：

- 保过、包过、不过退款
- 内部渠道、命题专家
- 百分百通过、一次过关
- 名师授课（需要标注教师资质）

**踩坑实录 16**：教育文案特别喜欢用"名师"这个词。但广告法要求"名师"必须有官方认证或行业公认的头衔，不能自己说自己是名师就是名师。我们后来要求所有包含"名师"的文案，必须同时标注教师的具体资质（如"清华大学博士、10 年教学经验"）。

**踩坑实录 17**：通过率表述是教育行业的高频违规点。模型会写"学员通过率高达 95%"，但这种数据必须有第三方统计报告支撑。我们后来要求所有通过率数据必须标注来源。

### 3.4 跨行业对比总结

| 行业 | 核心风险 | 高频违规词 | 特殊要求 |
|------|---------|-----------|---------|
| 保健品 | 暗示疗效 | 有效率、三天见效、根治 | 不能承诺效果，需标注批准文号 |
| 金融 | 承诺收益 | 稳赚不赔、零风险、保本 | 需展示年化利率，需风险提示 |
| 教育 | 承诺效果 | 保过、包过、命题专家 | 需标注教师资质，不能承诺通过率 |
| 食品 | 虚假功效 | 减肥、美容、保健 | 普通食品不能暗示保健功能 |
| 化妆品 | 虚假功效 | 祛斑、美白、抗皱 | 特殊用途化妆品需标注批准文号 |

## 四、代码示例：从生成到评估的完整工具链

### 4.1 文案生成引擎

文案生成不是随机出稿，而是基于风格策略和受众画像的结构化生成。核心思路是：把营销策略编码成 Prompt，让模型按照策略来写。

```python
import re
import json
import random
import time
from typing import List, Dict, Optional, Tuple
from dataclasses import dataclass, field


@dataclass
class ProductInfo:
    """产品信息"""
    name: str
    category: str
    selling_points: List[str]
    price: str
    target_audience: str
    platform: str  # 发布平台：朋友圈/微博/抖音/电商


@dataclass
class CopyVersion:
    """文案版本"""
    content: str
    style: str
    version_id: str
    compliance_passed: bool = True
    quality_score: float = 0.0
    compliance_issues: List[str] = field(default_factory=list)
    metrics: Optional[Dict] = None


class CopyGenerator:
    """文案生成引擎"""

    STYLE_TEMPLATES = {
        "正式": "请以正式、专业的口吻撰写，适合企业官方渠道发布。",
        "幽默": "请以轻松幽默的口吻撰写，使用网络流行语和俏皮话。",
        "情感": "请以情感共鸣的方式撰写，触动用户内心需求。",
        "促销": "请以紧迫感推动的方式撰写，强调限时优惠和稀缺性。",
        "科普": "请以知识科普的方式撰写，先讲道理再推产品。",
    }

    PLATFORM_FORMATS = {
        "朋友圈": "字数控制在 100 字以内，适合配图发布。",
        "微博": "字数控制在 200 字以内，可以带话题标签。",
        "抖音": "口语化表达，适合口播，控制在 150 字以内。",
        "电商": "详细的产品描述，突出卖点，控制在 300 字以内。",
    }

    def __init__(self, llm_call_func):
        self.llm = llm_call_func

    def generate(self, product: ProductInfo, style: str, count: int = 3) -> List[CopyVersion]:
        """生成多个版本的文案"""
        if style not in self.STYLE_TEMPLATES:
            raise ValueError(f"不支持的风格：{style}，可选：{list(self.STYLE_TEMPLATES.keys())}")

        style_instruction = self.STYLE_TEMPLATES[style]
        platform_instruction = self.PLATFORM_FORMATS.get(product.platform, "")

        selling_points_text = "\n".join([f"- {sp}" for sp in product.selling_points])

        prompt = (
            f"你是一名资深营销文案撰稿人，擅长为不同平台撰写高转化率的营销文案。\n\n"
            f"产品信息：\n"
            f"- 产品名称：{product.name}\n"
            f"- 产品类别：{product.category}\n"
            f"- 核心卖点：\n{selling_points_text}\n"
            f"- 价格：{product.price}\n"
            f"- 目标受众：{product.target_audience}\n"
            f"- 发布平台：{product.platform}\n\n"
            f"风格要求：{style_instruction}\n"
            f"平台要求：{platform_instruction}\n\n"
            f"请生成 {count} 个不同版本的文案，每个版本包含：\n"
            f"1. 标题（吸引眼球）\n"
            f"2. 正文（突出卖点）\n"
            f"3. 行动号召（引导购买）\n\n"
            f"每个版本之间要有明显差异，不要重复。\n"
            f"输出格式：每个版本用 --- 分隔。\n"
        )

        response = self.llm(prompt)
        versions = self._parse_response(response, style, count)
        return versions

    def _parse_response(self, response: str, style: str, expected_count: int) -> List[CopyVersion]:
        """解析模型返回的多个文案版本"""
        parts = response.split("---")
        versions = []

        for i, part in enumerate(parts[:expected_count]):
            content = part.strip()
            if content:
                versions.append(CopyVersion(
                    content=content,
                    style=style,
                    version_id=f"{style}_{i + 1}",
                ))

        return versions if versions else [CopyVersion(
            content=response.strip(),
            style=style,
            version_id=f"{style}_1",
        )]
```

这段代码的核心是 Prompt 设计。我重点讲几个设计要点：

**要点一：结构化输入。** 产品信息用 bullet point 列出，模型更容易理解。不要把所有信息堆成一段话，模型会漏掉关键信息。

**要点二：风格和平台要求分开。** 风格决定语气，平台决定格式。这两个维度是独立的，分开写更清晰。

**要点三：明确要求输出格式。** 用 `---` 分隔版本，方便后续解析。如果不指定格式，模型输出的格式每次都不一样，解析代码会写得很痛苦。

### 4.2 合规检查模块

这是整个系统最重要的模块，没有之一。合规检查分两层：规则层和模型层。

```python
class ComplianceChecker:
    """合规检查器"""

    # 广告法禁用词库（部分示例）
    ABSOLUTE_BANNED_WORDS = [
        "最", "第一", "唯一", "绝对", "国家级", "全球领先",
        "顶级", "极致", "史无前例", "空前绝后",
    ]

    # 行业特定禁用词
    CATEGORY_BANNED_WORDS = {
        "保健品": [
            "有效率", "治愈率", "三天见效", "无效退款",
            "根治", "永不复发", "纯天然无副作用", "包治百病",
        ],
        "金融": [
            "稳赚不赔", "保本保息", "零风险", "guaranteed",
            "年化收益固定", "绝对安全",
        ],
        "教育": [
            "保过", "包过", "内部渠道", "命题专家",
            "百分百通过", "不过退款",
        ],
    }

    # 需要资质声明的表述
    CLAIM_PATTERNS = [
        (r'(\d+)%', "数据需要标注来源"),
        (r'临床验证|实验证明|科学研究', "需要标注研究机构和结论"),
        (r'专家推荐|权威认证', "需要标注专家姓名和认证机构"),
        (r'用户评价|用户反馈', "需要保证评价真实可查"),
    ]

    def __init__(self, category: str = ""):
        self.category = category

    def check(self, content: str) -> Tuple[bool, List[str]]:
        """执行合规检查，返回 (是否通过, 问题列表)"""
        issues = []

        # 检查绝对化用语
        for word in self.ABSOLUTE_BANNED_WORDS:
            if word in content:
                issues.append(f"包含绝对化用语：{word}")

        # 检查行业特定禁用词
        if self.category in self.CATEGORY_BANNED_WORDS:
            for word in self.CATEGORY_BANNED_WORDS[self.category]:
                if word in content:
                    issues.append(f"包含行业禁用词：{word}")

        # 检查需要资质声明的表述
        for pattern, message in self.CLAIM_PATTERNS:
            if re.search(pattern, content):
                issues.append(message)

        # 检查夸大表述
        exaggeration_patterns = [
            (r'(\d+)\s*天\s*见\s*效', "承诺见效时间，涉嫌虚假宣传"),
            (r'无效\s*退款', "承诺退款，可能涉嫌误导"),
            (r'包\w+过|包\w+会', "承诺效果，涉嫌虚假宣传"),
        ]
        for pattern, message in exaggeration_patterns:
            if re.search(pattern, content):
                issues.append(message)

        passed = len(issues) == 0
        return passed, issues
```

关于合规检查模块，我想多说几句实战经验：

**经验一：词库要分层管理。** 通用禁用词（所有行业都不能用）和行业特定禁用词（只有特定行业不能用）要分开管理。这样添加新行业时，只需要加行业词库，不用动通用词库。

**经验二：正则表达式比简单字符串匹配更可靠。** 比如"三天见效"，如果只用字符串匹配，模型写成"3 天见效"就漏了。用正则 `(\d+)\s*天\s*见\s*效` 就能覆盖数字和中文数字两种写法。

**经验三：合规检查的结果要可解释。** 返回的 issues 列表要清楚地告诉用户"哪里有问题、为什么有问题"。不能只返回一个"不通过"，那样用户不知道怎么改。

### 4.3 质量评估与 A/B 测试

```python
class QualityEvaluator:
    """文案质量评估器"""

    def evaluate(self, content: str, product: ProductInfo, llm_call_func=None) -> Dict:
        """综合质量评估"""
        score = 100.0
        details = {}

        # 长度评估
        length = len(content)
        if product.platform == "朋友圈" and length > 150:
            score -= 10
            details["length"] = f"过长（{length}字），朋友圈建议100字以内"
        elif length < 20:
            score -= 15
            details["length"] = f"过短（{length}字），信息量不足"
        else:
            details["length"] = f"适中（{length}字）"

        # 卖点覆盖评估
        covered_points = 0
        for point in product.selling_points:
            if point in content:
                covered_points += 1
        coverage = covered_points / len(product.selling_points) if product.selling_points else 0
        if coverage < 0.5:
            score -= 15
        details["selling_point_coverage"] = f"{covered_points}/{len(product.selling_points)}"

        # 行动号召评估
        has_cta = bool(re.search(r'立即|点击|购买|扫码|了解|咨询|限时|抢购', content))
        if not has_cta:
            score -= 10
        details["has_call_to_action"] = has_cta

        # 重复度评估（用于多版本对比）
        details["quality_score"] = round(max(0, score), 1)
        return details

    def calculate_diversity(self, versions: List[CopyVersion]) -> float:
        """计算多个版本之间的多样性分数"""
        if len(versions) < 2:
            return 1.0

        total_similarity = 0
        pair_count = 0

        for i in range(len(versions)):
            for j in range(i + 1, len(versions)):
                similarity = self._text_similarity(versions[i].content, versions[j].content)
                total_similarity += similarity
                pair_count += 1

        avg_similarity = total_similarity / pair_count if pair_count > 0 else 0
        return round(1.0 - avg_similarity, 2)

    def _text_similarity(self, text1: str, text2: str) -> float:
        """简单的文本相似度计算（基于字符级 n-gram）"""
        n = 3
        set1 = set(text1[i:i + n] for i in range(len(text1) - n + 1))
        set2 = set(text2[i:i + n] for i in range(len(text2) - n + 1))

        if not set1 or not set2:
            return 0.0

        intersection = len(set1 & set2)
        union = len(set1 | set2)
        return intersection / union if union > 0 else 0.0


class ABTestManager:
    """A/B 测试管理器"""

    def __init__(self):
        self.experiments: Dict[str, Dict] = {}

    def create_experiment(self, experiment_id: str, versions: List[CopyVersion],
                          total_impressions: int = 1000) -> Dict:
        """创建 A/B 测试实验"""
        self.experiments[experiment_id] = {
            "versions": versions,
            "total_impressions": total_impressions,
            "impressions": {v.version_id: 0 for v in versions},
            "clicks": {v.version_id: 0 for v in versions},
            "conversions": {v.version_id: 0 for v in versions},
            "start_time": time.time(),
        }
        return self.experiments[experiment_id]

    def record_impression(self, experiment_id: str, version_id: str):
        """记录一次展示"""
        if experiment_id in self.experiments:
            self.experiments[experiment_id]["impressions"][version_id] += 1

    def record_click(self, experiment_id: str, version_id: str):
        """记录一次点击"""
        if experiment_id in self.experiments:
            self.experiments[experiment_id]["clicks"][version_id] += 1

    def record_conversion(self, experiment_id: str, version_id: str):
        """记录一次转化"""
        if experiment_id in self.experiments:
            self.experiments[experiment_id]["conversions"][version_id] += 1

    def get_results(self, experiment_id: str) -> List[Dict]:
        """获取测试结果"""
        if experiment_id not in self.experiments:
            return []

        exp = self.experiments[experiment_id]
        results = []

        for version_id in exp["impressions"]:
            impressions = exp["impressions"][version_id]
            clicks = exp["clicks"][version_id]
            conversions = exp["conversions"][version_id]

            ctr = clicks / impressions if impressions > 0 else 0
            cvr = conversions / impressions if impressions > 0 else 0

            results.append({
                "version_id": version_id,
                "impressions": impressions,
                "clicks": clicks,
                "conversions": conversions,
                "ctr": round(ctr, 4),
                "cvr": round(cvr, 4),
            })

        results.sort(key=lambda x: x["cvr"], reverse=True)
        return results
```

质量评估这块，我想强调的是：**自动化评分只是初筛，不是终审。** 我们的评分体系能过滤掉明显不合格的文案（比如太短的、没有卖点的、没有行动号召的），但它判断不了"这条文案是否真的打动人"。那个必须靠人工。

A/B 测试的代码比较简单，但实战中有几个要点：

- **随机性要真正随机**。不要用简单的轮询分配流量，要用随机数。我们之前用轮询，结果某个时间段的流量特征恰好跟某个文案匹配，导致数据偏差。
- **数据要能回溯**。每次记录都要带时间戳，这样后期分析时可以按时间段切片。
- **结果要看统计显著性**。不能光看转化率数字大小，要做卡方检验或 Fisher 精确检验，确认差异是真实的而不是随机波动。

### 4.4 完整流程串联

```python
class CopywritingPipeline:
    """营销文案生成完整流程"""

    def __init__(self, llm_call_func):
        self.generator = CopyGenerator(llm_call_func)
        self.compliance_checker = ComplianceChecker()
        self.quality_evaluator = QualityEvaluator()
        self.ab_manager = ABTestManager()

    def set_category(self, category: str):
        """设置产品类别以启用对应合规规则"""
        self.compliance_checker = ComplianceChecker(category)

    def process(self, product: ProductInfo, styles: List[str],
                versions_per_style: int = 2) -> List[CopyVersion]:
        """执行完整的文案生成流程"""
        all_versions = []

        for style in styles:
            # 第一步：生成文案
            versions = self.generator.generate(product, style, versions_per_style)

            for version in versions:
                # 第二步：合规检查
                passed, issues = self.compliance_checker.check(version.content)
                version.compliance_passed = passed
                version.compliance_issues = issues

                if not passed:
                    continue

                # 第三步：质量评估
                quality = self.quality_evaluator.evaluate(version.content, product)
                version.quality_score = quality.get("quality_score", 0)

                all_versions.append(version)

        # 第四步：多样性检查
        if len(all_versions) >= 2:
            diversity = self.quality_evaluator.calculate_diversity(all_versions)
            if diversity < 0.3:
                print(f"警告：版本间多样性不足（{diversity}），建议调整 temperature")

        return all_versions
```

这个流程的核心思想是**"漏斗模型"**：生成 → 合规过滤 → 质量过滤 → 多样性检查 → 输出。每一层都过滤掉不合格的文案，最后输出的就是可用的版本。

## 五、注意事项：7 个真实踩坑案例

### 坑一：合规词库更新不及时——法规变了系统不知道

**现象**：系统上线后，广告法新增了"国家级"作为禁用词，但我们的词库没有同步更新，导致一条使用了"国家级原料"的文案通过了检查。

**排查**：合规词库是项目启动时一次性导入的，之后没有维护机制。法规更新了，系统不知道。

**教训**：合规词库必须有定期更新机制。我们后来接入了法规变更的 RSS 订阅，每次法规更新自动触发词库同步，并重新跑一遍回归测试。同时，我们每季度做一次人工复核，确保词库没有遗漏。

### 坑二：不同平台的合规标准不一样——此平台通过彼平台拒绝

**现象**：同一条文案在朋友圈发布没问题，但在电商平台却被平台审核拒绝了。原因是电商平台的审核标准比广告法更严格。

**排查**：我们的合规检查只做了广告法层面的通用检查，没有考虑各平台的特殊规则。

**教训**：合规检查要分层。第一层是法律法规的通用检查，第二层是各平台的特殊规则检查。我们在平台适配层增加了平台规则校验，每个平台一套独立的规则文件。

### 坑三：多样性评估形同虚设——分数很高内容一样

**现象**：系统生成了三个版本的文案，多样性分数显示 0.8，但人工一看，三个版本只是换了几个同义词，内容结构完全一样。

**排查**：我们的多样性计算用的是字符级 n-gram 相似度，模型学会了用同义词替换来"欺骗"相似度计算，但实际内容没有变化。

**教训**：字符级相似度不够，后来我们加上了语义层面的多样性评估，用嵌入向量计算语义距离，同时保留人工抽检。现在我们的多样性评估是三层：字符级初筛 → 语义级精筛 → 人工抽检。

### 坑四：temperature 参数调不好——要么太死板要么太随机

**现象**：temperature 设低了（0.1），三个版本长得几乎一样；设高了（0.9），文案里开始出现胡言乱语，甚至编造不存在的卖点。

**排查**：temperature 控制的是模型输出的随机性。太低则输出趋同，太高则输出不可控。

**教训**：营销文案的 temperature 建议在 0.5-0.8 之间。这个范围既能保证版本之间有差异，又不会偏离产品信息太远。我们还发现，不同模型的最优 temperature 不一样——同一个值在 GPT-4 上合适，在 Claude 上可能就偏高了。每次换模型都要重新调。

### 坑五：Prompt 太长模型"遗忘"——前面的要求后面忘了

**现象**：我们在 Prompt 里写了十几条要求，结果模型生成的文案经常忽略排在后面的要求。比如我们要求"必须包含价格"，但经常生成的文案里没有价格。

**排查**：大模型对长 Prompt 的处理能力有限，排在中间和后面的要求容易被忽略。这在 NLP 领域叫"lost in the middle"现象。

**教训**：Prompt 要精简，最重要的要求放在开头和结尾。我们把 Prompt 从原来的 500 字压缩到 200 字以内，核心要求（产品信息、风格、平台）放在最前面，格式要求放在最后面。中间那些"注意事项"能删就删。

### 坑六：模型幻觉编造卖点——模型自己给自己加戏

**现象**：有一款普通茶叶，模型生成的文案里出现了"降血压、降血脂"的功效描述。但这款产品根本没有这些功效，也没有相关认证。

**排查**：模型在训练数据中见过很多茶叶产品的营销文案，那些文案里经常有功效描述。模型"记住"了这些模式，生成时自动套用了。

**教训**：必须在 Prompt 里明确禁止模型编造信息。我们加了一条："只能使用提供的产品信息，不得添加任何未提供的功效或特性描述。"同时，在合规检查之外，额外加了一个"信息一致性检查"——对比生成文案和原始产品信息，确保没有编造的内容。

### 坑七：合规检查的"误杀"——正常表述被当成违规

**现象**：一条文案里写了"这是我们最受欢迎的产品"，被合规检查拒绝了，因为包含了"最"字。但"最受欢迎"在日常表达中很常见，不一定违反广告法。

**排查**：我们的合规检查是简单的关键词匹配，没有考虑上下文。"最"字在"最好的产品"里是违规的，但在"这是我们最受欢迎的产品"里，如果是基于真实销售数据，可能并不违规。

**教训**：关键词匹配太粗糙了。我们后来做了改进：第一，把一些常见但不一定违规的表述从"绝对拒绝"改成"人工复核"；第二，引入了上下文感知的检查——如果"最"字后面跟的是客观数据（如"销量最高"），提示人工确认而不是直接拒绝；第三，设置了"白名单"——某些在特定语境下安全的表述可以放行。

### 坑八：A/B 测试的数据污染——外部因素干扰了结果

**现象**：一次 A/B 测试中，版本 A 的转化率是 3.2%，版本 B 是 1.8%。我们以为版本 A 赢了，但后来发现测试期间版本 A 恰好碰上了一个节假日，整体流量和转化率都偏高。

**排查**：A/B 测试期间遇到了外部事件（节假日、热点事件、竞品活动），这些因素影响了测试结果，而不是文案本身的差异。

**教训**：A/B 测试要避开节假日和重大事件。如果无法避开，要在分析时标注这些干扰因素。另外，测试周期至少要覆盖一个完整的用户行为周期（通常是一周），这样才能平均掉日间的波动。

## 六、总结思考：从测试视角看营销文案生成

### 6.1 三个核心认知

营销文案生成系统的测试，我总结了三个核心认知：

**第一，合规是底线，不是加分项。** 文案生成系统和其他生成类应用最大的不同在于，文案是直接面向公众发布的，一旦出问题就是公共事件。合规检查必须做到万无一失，宁可错杀不可放过。你想想，一条违规文案被发出去，轻则被平台删除，重则被工商局罚款，品牌声誉受损。这个风险成本太高了，测试阶段多花一倍的时间做合规检查，都比上线后出事故划算。

**第二，质量评估不能只看模型打分。** 模型自己评估自己生成的文案质量，就像学生自己批改自己的考卷。自动化评分可以过滤明显不合格的文案，但最终的质量判断必须有人工参与。我们的做法是自动化评分做初筛，人工评分做终审。人工评分不需要每个人都评——我们要求每个风格至少评 5 条，覆盖好中差三个等级，这样就能快速建立对系统输出质量的感知。

**第三，A/B 测试是验证文案效果的唯一可靠方式。** 不管测试阶段评分多高，实际投放后的点击率和转化率才是最终答案。我们现在的流程是：测试阶段过滤不合格文案，上线后通过 A/B 测试验证效果，效果数据再反哺模型优化。形成了一个闭环。

### 6.2 测试检查清单

每次上线前，对照这个清单过一遍：

**合规检查**：
- [ ] 通用禁用词库是否最新？
- [ ] 行业特定禁用词库是否覆盖当前行业？
- [ ] 各平台规则是否已配置？
- [ ] 是否做了边界用例测试（极端表述、变体写法）？
- [ ] 是否有误杀率监控？（正常文案被误判的比例）

**质量检查**：
- [ ] 信息完整度是否达标？（产品名称、卖点、价格）
- [ ] 卖点覆盖率是否大于 50%？
- [ ] 行动号召是否包含？
- [ ] 平台格式是否适配？（字数、排版）
- [ ] 风格一致性是否通过人工抽检？

**多样性检查**：
- [ ] 同风格多版本多样性分数是否大于 0.3？
- [ ] 不同风格之间是否可明显区分？
- [ ] 是否有重复文案？

**A/B 测试检查**：
- [ ] 流量分配是否均衡？（偏差不超过 5%）
- [ ] 样本量是否足够？（每个版本至少 500 次展示）
- [ ] 测试周期是否合理？（至少 3 天）
- [ ] 是否避开了节假日和重大事件？

### 6.3 最佳实践总结

1. **合规先行**：合规检查必须在质量评估之前。不合规的文案，质量再高也不能用。
2. **分层检查**：通用规则 → 行业规则 → 平台规则 → 品牌规则，四层检查层层递进。
3. **人工兜底**：自动化检查覆盖 90% 的场景，剩下 10% 靠人工复核。不要追求 100% 自动化。
4. **持续迭代**：合规词库、质量评分标准、A/B 测试策略，都要根据实际数据持续优化。
5. **数据驱动**：效果数据是最好的老师。哪个文案转化率高、为什么高，这些数据要反哺到 Prompt 设计和测试用例中。

### 6.4 思考题

最后留几个问题给你思考，这些都是我们在实战中反复纠结的问题：

1. **合规检查的"误杀率"和"漏杀率"之间如何平衡？** 误杀太多，用户体验差，好文案被拦住了；漏杀太多，违规文案发出去，法律风险大。你的系统倾向于哪一边？为什么？

2. **当模型升级了（比如从 GPT-3.5 换到 GPT-4），之前的测试用例还需要重新跑吗？** 你觉得哪些测试维度受模型影响大，哪些影响小？

3. **A/B 测试发现某个文案转化率高，但人工评估觉得质量一般。这时候该用哪个？** 数据说话还是人工判断？你有没有遇到过数据和人工判断矛盾的情况？

4. **多语言场景下的合规检查怎么做？** 如果你的系统要支持英文、日文等多语言文案，合规词库和检查逻辑要怎么适配？

5. **如果让你设计一个"合规检查"的测试用例生成器，你会怎么设计？** 怎么自动生成覆盖各种违规场景的测试用例，而不是靠人工一条条写？

6. **Prompt 工程和质量保证之间的关系是什么？** 我们花了很多精力优化 Prompt，但 Prompt 本身的质量怎么保证？你有没有想过给 Prompt 也写测试用例？

7. **当你的系统同时服务多个行业客户时，测试策略要怎么调整？** 每个行业一套独立的测试用例，还是用一套通用的测试框架加上行业插件？

8. **文案生成系统的"回归测试"怎么做？** 模型升级了、词库更新了、Prompt 改了，哪些东西需要重新测？全量回归太慢，选择性回归又怕漏，你怎么选？

### 6.5 写在最后

做 AI测试这几年，我最大的感受是：**测试人员的价值不是在发现 bug，而是在预防 bug。** 营销文案生成系统如果只靠测试阶段找问题，那已经晚了——因为真正严重的问题（合规违规）一旦发生就是不可逆的。

所以我们的测试思路是"左移"：在需求阶段就介入，跟产品经理一起定义什么是"好的文案"、什么是"不可接受的文案"；在设计阶段就参与，帮开发团队设计合规检查的架构；在编码阶段就做 review，确保 Prompt 的设计是合理的。

测试不是质量的守门员，测试应该是质量的建筑师。
