# 一句话需求，先判断该走哪条线

> 完整短语表在包内 `intent-router/mapping.yaml`；本篇为常用对照。

「帮我们做一下自动化。」

这句话在工位上出现频率很高，但对 AI 来说信息不够：可能是接口、可能是页面、也可能只是想要一份测试点清单。

专业版在包里有 **意图路由**（`intent-router`）：作用不是替你写脚本，而是**先派活**——把请求送到对的技能目录，减少跑偏。

---

## 它解决什么问题

| 没有路由时 | 有路由意识时 |
|------------|----------------|
| AI 直接写 Playwright，其实你要的是 POST 登录 | 先确认「接口线」再 @ `api-skills` |
| 用例还没评审就生成 pytest | 先 `testcase-skills/生成` 再执行 |
| 失败日志丢进聊天，格式每次不同 | 走 `bug-reporter` 统一字段 |

路由**不负责**写用例、跑测试、改代码，只负责「往哪送」。

---

## 用户常说法 → 建议技能线

下面不是穷举，是实际使用中**最高频**的对照表。听不清时，宁可多问一句。

| 用户大概在说什么 | 一般会落到 |
|------------------|------------|
| 写用例、铺场景、需求追溯到案例 | `testcase-skills`，多数先进 **生成** |
| 测试范围、迭代怎么排、上线前要卡什么 | `testcase-skills/规划` |
| 用例评审、质量把关 | `testcase-skills/评审` |
| 造数据、铺底数据 | `testcase-data-generator` |
| 接口、Swagger、OpenAPI、REST | `api-skills`，默认 **执行** |
| 接口脚本红了想修 | `api-skills/自我修复` |
| 页面、浏览器、E2E、Playwright | `UI-skills`，默认 **执行** |
| App、手机、真机、Appium | `mobile-skills` |
| 页面脚本失败、定位飘了 | `UI-skills/自我修复` |
| 记缺陷、缺陷统计 | `bug-reporter` |
| 进度、还剩多少、周报材料 | `progress-reporter` |
| 需求很粗、测什么不测什么 | `requirement-modeling` |
| 压测、Locust、性能专项 | `special-testing` |

## 在 Cursor 里怎么用

**方式 A：你自己判断**  
根据上表 @ 对应 `SKILL.md`，不必每次 @ 路由。

**方式 B：让 AI 先路由**  
任务很模糊时，可以先发：

```text
@intent-router/SKILL.md

用户原话：「我们要做秒杀活动的自动化。」
请先判断 intent，告诉该 @ 哪些 SKILL，不要直接写代码。
```

AI 应给出「建议走 api / UI / testcase 哪条线」和默认入口；你再开新对话 @ 执行 SKILL。

包内 `intent-router/mapping.yaml` 维护了更细的短语匹配。你只需知道：规则是**从上到下**匹配，**先命中先生效**。

## 两句澄清话术（可直接复制）

**澄清 1：**

```text
你是更关心「接口返回对不对」，还是「页面上能不能点通」？
```

**澄清 2：**

```text
这次是要「测试点/用例文档」，还是「能跑的 pytest 脚本」？
```

## 和三条推荐流水线

专业版 `START_HERE.md` 里概括了三条常路线：

```
粗需求 → requirement-modeling → testcase 分析（可选）→ 生成 → 评审

接口回归 → generate.sh + seckill/api 模板 → run_pytest.sh

页面冒烟 → generate.sh + ui 模板
```

意图路由是这些流水线的**入口导航**；具体步骤在 06～08 篇展开。
