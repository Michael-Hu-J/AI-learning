# 跑红了之后：缺陷单和进度表不要手写第二遍

自动化跑起来之后，真正的成本往往在**失败之后**：

- 同一段失败日志，三个人写出三种缺陷描述  
- 周报里的「还剩多少」和 Jira 对不上  

专业版用 **`bug-reporter`** 和 **`progress-reporter`** 统一口径，并配合 `run_pytest.sh` 减少复制粘贴。

---

## 术语（全包统一）

| 类型 | 用词 |
|------|------|
| 问题单 | **缺陷**（不叫 Bug 模块） |
| 能力包 | **技能**（不叫模块） |
| 严重度 | Critical / High / Medium / Low |
| 优先级 | P0 / P1 / P2 / P3 |

写对外文档、缺陷标题时也保持一致，方便评审。

---

## pytest 失败 → 缺陷草稿

包根目录（示例）：

```bash
./run_pytest.sh output/api_smoke.py -v
```

失败时，脚本会把摘要写入 **`output/bugs/`**，文件名通常带日期与用例名。  
你可在此基础上 @ `bug-reporter` 补全复现步骤、期望与实际。

AI 话术：

```text
@bug-reporter/SKILL.md

根据以下 pytest 失败输出写缺陷 Markdown，严重度你先估一版：

（粘贴终端 -v 片段）
```

包内 `examples/bug_sample_*.md` 可作结构参考（打码后对内培训）。

---

## 缺陷里建议有什么

不写模板全文（完整字段见 `@bug-reporter/SKILL.md`），只列**字段意识**：

- 标题：现象 + 范围（如「登录接口 401」）  
- 环境：URL、版本、账号类型（脱敏）  
- 复现：步骤编号、数据  
- 期望 / 实际  
- 严重度、优先级及理由  
- 附件：日志片段、截图路径  

**专业版不自动建 Jira/禅道单**——产出是 Markdown，由你们粘贴或二次开发对接 API。

---

## 缺陷列表汇总

多次失败后，`output/bugs/bug_list.md` 类文件可当作**本轮迭代缺陷索引**（以你包内实际文件为准）。  
适合站会投影：不翻十个聊天窗口。

---

## 进度汇报：progress-reporter

适合问 AI：

```text
@progress-reporter/SKILL.md

本轮目标：秒杀接口冒烟 + 登录 UI。
已完成：output/api_smoke.py 全绿；UI 还差支付页。
阻塞：测试环境 502。
请按 SKILL 输出进度摘要（表格或列表）。
```

输出给项目经理 / 周报时，字段与缺陷单同源，减少「测试说做完了、开发说没测」的歧义。

---

## 和「自我修复」的分工

| 情况 | 走 |
|------|-----|
| 脚本是错的（路径、断言、选择器） | 先 api/UI **自我修复** SKILL |
| 产品行为与需求不符 | **bug-reporter** 记缺陷 |
| 环境挂了 | 缺陷或环境问题单，别硬改断言通过 |

第 12 篇专讲自我修复流程（怎么演示、怎么区分脚本问题和产品问题）。
