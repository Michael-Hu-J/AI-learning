# 脚本挂了能不能救？专业版里「修」和「报缺陷」是两件事

> 修复策略全文在 `api-skills/自我修复`、`UI-skills/自我修复` 的 **SKILL.md** 内。

失败之后，团队常分两派：

- 「改断言让它绿」  
- 「啥都不改先报 bug」  

专业版把 **自我修复** 和 **缺陷记录** 分开：前者针对**脚本/ spec 与现状不符**；后者针对**产品不符合需求**。

---

## 自我修复解决哪类问题

典型包括（举例，非完整策略表）：

- spec 里 `path` 写错一字  
- 响应 JSON 字段改名，断言还停在旧字段  
- 页面按钮文案变了，选择器还停在旧 text  
- 环境变量漏配导致 401，实际应补 header  

**不解决**：业务规则错了、后端真返回 500、安全漏洞——这些应走 **bug-reporter**。

自我修复的**具体步骤、改几轮、能否改 spec**，写在 `api-skills/自我修复` 与 `UI-skills/自我修复`（及 mobile）的 SKILL 里。

---

## 怎么演示自我修复流程

拿你已有的任意一条 spec，故意改错一个字段，走一遍修复流程：

```bash
# 1. 用现有模板生成脚本（以 api_smoke.md 为例）
./generate.sh templates/api_smoke.md

# 2. 打开 output/api_smoke.py，故意改错一个 path（比如把 /api/login 改成 /api/loginn）

# 3. 跑 pytest，预期失败
cd output && python3 -m pytest api_smoke.py -v
```

然后在 Chat 里：

```text
@api-skills/自我修复/SKILL.md

失败用例：output/api_smoke.py
spec：templates/api_smoke.md
请按 SKILL 收敛，优先改 spec 再 generate。
```

AI 会按 SKILL 里的策略逐轮修复：先改 path → 重新 generate → 再跑 pytest。修到绿为止，或者判断是产品 bug 转缺陷单。

> **关键动作**：修复过程中注意观察 AI 改了什么——是改 spec（路径拼写错误）还是改断言（产品行为变了）。前者是自我修复，后者应该走 bug-reporter。

## 演示与生产的区别

| | 学习演示 | 生产仓库 |
|--|----------|----------|
| 目的 | 学会流程 | 保回归稳定 |
| 失败 | 预期 | 要归因 |
| 修改 | 可反复试 | 要 Code Review |
| 记录 | 自己记笔记 | bugs/ + 版本库 |

不要在生产上为了「演示自愈」故意留错 spec。

---

## UI 自愈同样存在

UI 线的自我修复流程与接口线一致：失败 → @ `UI-skills/自我修复` → 改 spec / 定位 → 再 generate → 再 pytest。

拿你已有的 UI spec 故意改错一个选择器，就能演示同样的流程。

---

## 和 run_pytest、bugs 目录的配合

1. `pytest` 红  
2. 判断：产品问题？→ 缺陷单  
3. 判断：脚本问题？→ 自我修复  
4. 修完仍红且确认是产品 → 再缺陷单  

避免「自愈把真实 bug 盖掉」。
