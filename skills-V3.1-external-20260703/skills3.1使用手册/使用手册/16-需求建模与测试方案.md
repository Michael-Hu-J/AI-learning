# 需求建模与测试方案：动手之前先画边界

很多团队拿到需求文档的第一反应是"开始写用例"。专业版建议先停一下：

**「测什么、不测什么、谁来做、什么时候做完」——这四件事想清楚，后面省很多返工。**

这条线走两个模块：`requirement-modeling`（需求建模）和 `test-plan`（测试方案与计划）。

---

## 需求建模（requirement-modeling）

**什么时候用**：需求文档写得不细、功能名模糊、团队对"测什么"有分歧。

**它不干什么**：不写具体用例，不做测试执行。只回答"范围在哪"。

### 典型流程

在 AI编辑器 Chat 中：

```text
@requirement-modeling/SKILL.md

这是产品需求文档：
---
@examples/prd_mini_seckill_auth.md
---

帮我拆解测试需求，列出测试范围和优先级。
```

AI 会输出结构化的需求拆解：

```markdown
# 需求拆解结果

## 业务模块
1. 用户认证 → 注册 / 登录 / Profile
2. （本轮不测）商品管理、秒杀下单

## 测试范围

### 功能测试（P0）
- 注册：合法 username+password、重复用户名拒绝
- 登录：admin/customer 成功拿 JWT；错误密码 401
- Profile：带 Token 200；无 Token 401

### 边界测试（P1）
- 密码长度 5 / 6 / 7 位
- username 空、超长

### 不测的范围
- 秒杀下单、Redis 预热（下迭代）
- 采购/销售/财务报表

## 测试顺序建议
1. 登录冒烟（admin）
2. 注册与 Profile
3. 权限：customer 不得 POST /api/products
```

### 核心规则

| 规则 | 说明 |
|------|------|
| 实体提取 | 从需求文本提取功能点、约束条件、业务规则、前置/后置条件 |
| 优先级判定 | P0=核心功能、P1=重要功能/边界、P2=次要功能、P3=体验细节 |
| 测试边界 | 明确标注"测什么"、"不测什么"、"待确认" |

### 和 testcase-skills 的衔接

需求建模完成后，直接把结果喂给 testcase-skills 生成用例：

```text
基于上面的需求拆解，生成测试用例 spec 文件。
kind 用 api_pytest，base_url 用 http://127.0.0.1:5001。
```

**不需要每次都用**。需求写得很死（前置、步骤、期望都齐）时，直接进入生成环节更快。

## 测试方案与计划（test-plan）

**什么时候用**：项目启动时、版本发布前、多团队协作时，需要一份完整的测试方案和计划。

**它不干什么**：不写具体测试用例，不做测试执行。只做"测什么、怎么测、谁来做、何时做完"。

### 测试方案（Test Plan）

在 AI编辑器 Chat 中：

```text
@test-plan/SKILL.md

帮我生成一个电商秒杀系统的测试方案。
```

AI 会输出：

**1. 测试范围**

| 类型 | 内容 |
|------|------|
| In-Scope | 秒杀活动配置、商品库存、下单流程、支付流程 |
| Out-of-Scope | 用户注册、商品评价 |

**2. 测试策略**

| 测试类型 | 策略 | 工具 |
|---------|------|------|
| 功能测试 | 场景法 + 等价类 + 边界值 | pytest / 手工 |
| 接口测试 | 契约驱动 + 自动化回归 | pytest + requests |
| 性能测试 | 基准 + 负载 + 压力 + 稳定性 | JMeter / Locust |
| 安全测试 | 权限越权 + SQL 注入 + XSS | OWASP ZAP / 手工 |
| UI 测试 | 关键路径自动化 | Playwright |

**3. 测试环境**

| 环境 | 用途 | 配置 |
|------|------|------|
| 开发环境 | 开发自测 | 本地 / Docker |
| 测试环境 | 功能测试 | 独立服务器 |
| 预发环境 | 回归验证 | 生产镜像 |

**4. 风险评估**

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 需求变更频繁 | 高 | 高 | 冻结需求基线，变更走评审 |
| 环境不稳定 | 中 | 高 | 提前搭建，每日巡检 |
| 数据准备不足 | 中 | 中 | 提前造数据，自动化生成 |

### 测试计划（Test Schedule）

```text
@test-plan/SKILL.md

帮我排一个 5 周的测试计划。
```

AI 会输出里程碑和进度安排：

| 阶段 | 开始日期 | 结束日期 | 交付物 | 退出准则 |
|------|----------|----------|--------|----------|
| 需求分析 | | | 需求分析文档 | 需求澄清完毕 |
| 测试设计 | | | 测试方案 + 用例 | 用例评审通过 |
| 测试执行 - 第一轮 | | | 测试报告 | P0/P1 用例 100% 通过 |
| 测试执行 - 第二轮 | | | 测试报告 | P0/P1/P2 用例 100% 通过 |
| 回归测试 | | | 回归报告 | 无新增缺陷 |
| 性能测试 | | | 性能报告 | 性能指标达标 |
| 验收测试 | | | 验收报告 | 产品/业务签字 |

进度安排（甘特图文字版）：

```
Week 1: [████████] 需求分析 + 测试设计
Week 2: [████████] 测试执行 - 第一轮
Week 3: [        ] 测试执行 - 第二轮
Week 4: [        ] 回归测试 + 性能测试
Week 5: [        ] 验收测试 + 上线
```

### 和 testcase-skills/规划 的区别

| 维度 | test-plan（本模块） | testcase-skills/规划 |
|------|---------------------|----------------------|
| 定位 | 完整测试方案 + 计划 | 测试范围 + 策略 + 节奏 |
| 输出 | Markdown/Excel/飞书 | Markdown |
| 粒度 | 项目级（多模块、多团队） | 模块级（单个功能） |
| 包含 | 环境、资源、风险、进度 | 范围、风险、里程碑 |
| 适用 | 大型项目、跨团队协作 | 小型迭代、单团队 |

---

## 出口闸门

测试方案/计划阶段有两个关键闸门：

| 闸门 | 规则 |
|------|------|
| 范围未明确 | **禁止**进入用例设计 |
| 策略未定义 | **禁止**开始测试执行 |
| 资源未到位 | **禁止**承诺上线日期 |
| 风险未评估 | **禁止**跳过缓解措施 |

---

## 最小工作流

```
需求文档 → requirement-modeling（拆解范围）→ test-plan（方案和排期）
                                              ↓
                                    testcase-skills/生成（写用例）
                                              ↓
                                    testcase-skills/评审（质量把关）
                                              ↓
                                    generate.sh + run_pytest.sh（执行）
```

不是每次都要跑满四段。需求很清晰时，常直接从 testcase-skills/生成 开始；大版本发布前加 test-plan 和评审。
