## 概念讲解

早上到公司，发现 Appium Server 被运维重启了。群里没人通知，监控也没告警。

我毫不知情地执行了 `pytest -n 4`：

- 1 分钟后：4 个 driver 初始化全部失败
- 5 分钟后：第一批 100 个测试用例全红
- 30 分钟后：全部 1000 个用例跑完，全红

我花了 40 分钟排查——看日志、翻代码、怀疑是不是昨晚提交的代码有问题。

最后发现：**Appium Server 端口 4723 没人监听。**

如果这 40 分钟用来写代码，我能写 200 行。结果全浪费在"服务没启动"这个屁事上。

**这个痛点不只我一个遇到。** 几乎所有做过自动化测试的人，都经历过"环境问题导致测试全红，排查半天才发现不是代码问题"。

### 健康检查解决什么问题

健康检查不是什么高科技，就是在跑测试之前先确认一件事：**环境准备好了吗？**

它做的事情很简单：

```
执行测试之前：
  Appium Server → 端口 4723 可达
  API 服务     → /health 接口返回 200
  数据库       → 端口 3306 可达
  环境变量     → API_KEY 已设置
  
所有检查通过 → 开始执行测试
任何一项失败 → 打印友好提示 → 退出，不浪费执行时间
```

### 健康检查的边界

健康检查不是测试。它不做复杂的验证，只做"服务有没有在监听"这种级别的检查。它的职责是：

- **快速**：每个检查不超过 3 秒
- **确定性**：检查没通过就不跑测试，不给 false positive 的机会
- **可跳过**：本地开发时可以跳过，CI 中必须执行

## HealthChecker 实现

### 注册检查项

```python
from self_healing.health_checker import HealthChecker

checker = HealthChecker()

# 注册自定义检查项
checker.register_check("appium_server", lambda: checker.ping_host("127.0.0.1", 4723))
checker.register_check("api_service", lambda: checker.check_url("http://localhost:8222/health"))
checker.register_check("python_env", lambda: checker.check_python_module("allure"))
checker.register_check("config_key", lambda: checker.check_env_var("API_KEY"))

# 运行所有检查
results = checker.run_all_checks()
```

### 预置的检查函数

HealthChecker 内置了 5 个常用的检查方法：

**1. ping_host(host, port)** — 检查主机端口是否可达

```python
checker.ping_host("127.0.0.1", 4723)
# 返回: (True, "127.0.0.1:4723 连接成功")
# 或: (False, "127.0.0.1:4723 连接失败: Connection refused")
```

这个最简单也最实用。底层用的 `socket.create_connection`，不依赖 HTTP 协议，所以也能检查非 HTTP 服务（如数据库、Redis）。

**2. check_url(url)** — 检查 HTTP 服务

```python
checker.check_url("http://localhost:8222/health", timeout=5.0)
# 返回: (True, "http://localhost:8222/health 响应正常 (status=200)")
```

依赖 `requests` 库。如果没装 requests，会返回友好的"requests 模块未安装"提示。

**3. check_command(cmd)** — 检查命令行工具是否可用

```python
checker.check_command("allure", "--version")
# 返回: (True, "allure 可用: 2.25.0")
# 或: (False, "allure 未安装")
```

适合检查 allure、appium、node 等命令行工具。检查失败时自动给出安装提示（如 `brew install allure`）。

**4. check_python_module(module)** — 检查 Python 模块是否可导入

```python
checker.check_python_module("allure")
# 返回: (True, "模块 allure 已安装")
# 或: (False, "模块 allure 未安装, 执行: pip install allure-pytest")
```

**5. check_env_var(name)** — 检查环境变量

```python
checker.check_env_var("API_KEY")
# 返回: (True, "环境变量 API_KEY=sk-****")
# 或: (False, "环境变量 API_KEY 未设置")
```

环境变量值会被截断显示（前 4 位 + \*\*\*\*），防止敏感信息泄露。

### 检查不通过时的处理

```python
def run_all_checks(self):
    """运行所有已注册的健康检查"""
    all_passed = True
    for name, check_fn in self._checks.items():
        passed, message = check_fn()
        if not passed:
            all_passed = False
    
    if not all_passed:
        print("环境检查未通过，测试已终止")
        print("请查看上方未通过的检查项，修复后重新运行")
        sys.exit(1)
```

**检查不通过直接退出 pytest**，不给任何继续执行的机会。防止"先跑跑看吧，说不定能行"——不可能，浪费时间。

### 友好的退出提示

看一个真实输出：

```
开始环境健康检查...
----------------------------------------
appium_server: 127.0.0.1:4723 连接成功
api_service: 127.0.0.1:8222/health 连接失败
python_env: 模块 allure 已安装
config_key: 环境变量 API_KEY=***
----------------------------------------
部分环境检查未通过

============================================================

  请查看上方未通过的检查项，修复后重新运行

```

相比直接抛 `ConnectionRefusedError` 加 50 行堆栈，这个提示友好多了。看一眼就知道哪里有问题。

## pytest_configure 集成

健康检查放在 `pytest_configure` 中执行，因为它发生在测试执行之前、用例收集之后。

```python
# conftest.py

def pytest_configure(config):
    """pytest 配置阶段：执行环境健康检查"""
    if os.getenv("SKIP_HEALTH_CHECK", "").lower() in ("1", "true", "yes"):
        logger.info("健康检查已跳过（SKIP_HEALTH_CHECK=1）")
        return

    # 如果启用了 Appium，检查 Appium Server
    if os.getenv("E2E_APP") == "1":
        checker = HealthChecker()
        checker.register_check(
            "appium_server",
            lambda: checker.ping_host("127.0.0.1", 4723),
        )
        results = checker.run_all_checks()
        if any(not r.passed for r in results):
            pytest_exit()
```

**为什么放在 pytest_configure 而不是 pytest_sessionstart？**

- `pytest_configure` 在所有 hook 中最早执行
- 环境不满就要尽早退出，不要等到用例收集完才发现服务没启动
- 而且 `pytest_configure` 在 xdist 的每个 worker 中独立执行，每个 worker 自己检查

### 跳过机制

本地开发时，你不想每次都检查环境：

```bash
# 跳过健康检查
SKIP_HEALTH_CHECK=1 pytest -v

# 跳过后即使环境有问题也继续执行
# 适合同时改代码和服务的场景
```

## 踩坑记录

### 坑 1：xdist 下重复检查

用 `-n 4` 并行时，4 个 worker 各自执行一次健康检查 = 同一个服务被检查 4 次。这不影响结果，但浪费时间。

**解决方法**：在 `pytest_configure` 中判断是主进程才检查：

```python
def pytest_configure(config):
    # 只有主进程检查，worker 不检查
    if hasattr(config, "workerinput"):
        return  # xdist worker 跳过
    # ... 执行健康检查
```

### 坑 2：检查本身太耗时

一个健康检查函数的超时时间默认 3-5 秒。如果有 5 个检查项，最坏情况是 25 秒。

**建议**：
- 每个检查设独立的超时（`check_url(url, timeout=3)`）
- 检查项控制在 5 个以内
- 如果某个服务启动很慢（如 Docker 容器），考虑用异步方式

### 坑 3：网络不通时的异常处理

`ping_host` 用 `socket.create_connection`，网络不通时可能抛多种异常（`socket.timeout`、`ConnectionRefusedError`、`OSError`）。

**解决方法**：在 `ping_host` 中统一捕获异常，全部转为 `(False, message)` 返回，不向外抛。

### 坑 4：健康检查内容不要过于严格

健康检查的目的是"快速确认环境是否可用"，不是"确认服务功能是否正常"。检查内容应该是：

```
端口可达 → 够了
HTTP 200 → 够了  
数据库里有没有测试数据 → 不归健康检查管
Redis 里有没有缓存的 session → 不归健康检查管
```

越过界的健康检查会让本地开发变得很痛苦——明明只是想跑两个用例，健康检查却要求你先启动 5 个服务。

## 总结与思考

> 健康检查本身不是测试，但它是测试的第一道防线。服务挂了就跑测试，等于蒙着眼睛开车。先确认环境再执行，一次 CI 就能省下 40 分钟。

**思考题**：你的项目中，测试全红的情况下，有多少次是环境问题导致的？如果加上健康检查，能省下多少排查时间？

## 面试题模块

### 1. 健康检查定位

**Q：健康检查属于测试吗？它的定位是什么？**

A：不属于测试。它的定位是"测试的前置条件验证"。健康检查只做快速的环境可用性确认（端口可达、服务返回 200、环境变量已设置），不做功能验证。通过就跑测试，不通过就直接退出。

### 2. 集成时机

**Q：健康检查应该在 pytest 的什么阶段执行？为什么？**

A：在 `pytest_configure` 阶段。这是 pytest 最早可用的 hook 点（fire 顺序仅次于 `pytest_load_initial_conftests`）。越早发现环境问题越节省时间。不要放在 `pytest_sessionstart` 或 fixture 中，那时候已经收集完用例了。

### 3. 跳过机制

**Q：什么场景下应该跳过快健康检查？怎么实现？**

A：开发环境跳过快检查（你正在改服务代码，服务处于不稳定状态是正常的）。CI 环境不跳过。通过环境变量 `SKIP_HEALTH_CHECK=1` 控制。CI 中不设置这个变量，开发时按需设置。

### 4. xdist 兼容

**Q：健康检查在 xdist 并行模式下要注意什么？**

A：每个 worker 都会执行 `pytest_configure`，导致同一服务被检查多次。解决方案：判断 `hasattr(config, "workerinput")`，有该属性说明是 xdist worker，跳过检查，只在主进程检查一次。
