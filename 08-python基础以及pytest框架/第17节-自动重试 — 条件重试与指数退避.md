# 17-自动重试 — 智能重试引擎

> 对应代码：`test/self_healing/retry_engine.py` + `test/conftest.py`（集成部分）
>

---

几年前我第一次用 `pytest-rerunfailures` 的时候觉得这玩意儿太香了。测试挂了自动重跑，CI 绿得发亮，领导看了直点头。

直到有一天，一个断言失败的用例——`assert response.status_code == 200`，接口返回了 500——被重试了 3 次。

每次重试都要登录、下单、付款，全套流程走一遍。3 次 × 30 秒 = 90 秒。明知道接口已经挂了，pytest 还在那儿傻乎乎地重跑。

更气人的是：重试 3 次都失败之后，报告上写着"测试失败"，跟没重试一模一样。那 90 秒纯属浪费。

**说白了，pytest-rerunfailures 是无脑重试**——只要是失败就重跑，不管你是网络抖了一下（重试能救），还是代码写错了（重试一万次也救不了）。

今天就来讲讲，怎么做一个"有脑子的重试引擎"。

---

## 概念讲解

### 为什么需要智能重试？

先说结论：**不是所有失败都值得重试。**

测试失败其实分两大类：

| 失败类型 | 例子 | 重试有用吗？ |
|---------|------|------------|
| 环境抖动 | 网络超时、连接被重置、服务暂时不可用 | 有用 |
| 代码 bug | 断言失败、空指针、类型错误、键不存在 | 没用 |

**判断标准很简单：失败是由于外部环境不稳定，还是代码逻辑本身有 bug？**

环境不稳定→重试。代码有 bug→直接报，别浪费重试的时间。

这跟考试一样：你发烧了没考好，可以补考。你压根儿没学会，补考十次也是挂。

### pytest-rerunfailures 的痛点

`pytest-rerunfailures` 是个好库，但它有几个硬伤：

1. **不分异常类型**：不管是 `AssertionError` 还是 `ConnectionError`，一律重试
2. **固定重试间隔**：每次等同样的时间，没有考虑"服务正在恢复"的场景
3. **没有统计信息**：重试到底救回了多少用例？不知道

```python
# pytest-rerunfailures 的典型用法
# pytest --reruns 3 --reruns-delay 5

# 问题：断言失败也重试，网络超时也重试，一视同仁
# 问题：每次等 5 秒，第 1 次和第 3 次一样
# 问题：救回多少用例？报表里看不到
```

干测试的都知道，**没有数据就没办法说服人**。你说重试好用，老板问"好用在哪？救了多少用例？"你答不上来，那就等于不好用。

### 条件重试的核心思想

条件重试的核心思想只有一句话：**只重试那些"再试一次可能成功"的失败。**

怎么判断"再试一次可能成功"？看异常类型：

```python
# 这些异常，重试大概率能救回来
RETRYABLE_EXCEPTIONS = (
    ConnectionError,
    TimeoutError,
    ConnectionRefusedError,
    ConnectionResetError,
    ConnectionAbortedError,
)

# 这些异常，重试也白扯
NON_RETRYABLE_EXCEPTIONS = (
    AssertionError,
    ValueError,
    TypeError,
    KeyError,
    IndexError,
    AttributeError,
    ImportError,
    SyntaxError,
    NameError,
)
```

判断逻辑很直观：

```python
def is_timeout_or_network(exc: Exception) -> bool:
    """判断异常是否属于网络/超时类（重试可能有用）"""
    return isinstance(exc, RETRYABLE_EXCEPTIONS)


def is_logic_error(exc: Exception) -> bool:
    """判断异常是否属于逻辑错误（重试也没用）"""
    return isinstance(exc, NON_RETRYABLE_EXCEPTIONS)
```

网络超时 → 重试。断言失败 → 不重试。就这么简单。

## 重试异常分类

### 可重试的异常

**什么时候重试能救命？**

**ConnectionError**：网络连接失败。可能是 VPN 断了、路由器重启、防火墙抽风。过几秒再试，大概率能连上。

**TimeoutError**：请求超时。服务端可能正在 GC、正在重启、流量高峰。等几秒再请求，可能就正常了。

**ConnectionRefusedError**：连接被拒绝。服务还没启动完，或者端口还没监听。过一会再连就好了。

**ConnectionResetError**：连接被重置。通常是代理服务器或负载均衡器把连接断了。重试一般能重新建立。

这些异常的共性是：**不是代码写错了，是环境不稳定。** 环境问题大概率会在短时间内自动恢复。

### 不可重试的异常

**什么时候重试是浪费生命？**

**AssertionError**：断言失败。`assert 200 == 500`，重试一万次 200 也不会变成 500。

**ValueError / TypeError**：值不对、类型不对。参数传错了，重试不会自动修正参数。

**KeyError**：键不存在。字典里没有这个 key，重试不会自动加上。

**AttributeError**：对象没有这个属性。代码写错了，重试也白搭。

**SyntaxError / ImportError / NameError**：代码级别的错误。这都是需要修代码的，跟网络没有半毛钱关系。

这些异常的共性是：**代码逻辑有问题。** 重试不会改代码，所以重试多少次结果都一样。

### 踩坑记录

> 踩过一次坑：有个用例报了 `requests.exceptions.ConnectionError`，但实际上是因为数据库迁移导致某个字段没了，代码里读不到这个字段才崩的。异常表面上看起来是"网络问题"，实际根因是"代码没适配新字段"。

这种情况怎么处理？两种思路：

1. **优先判断错误消息内容**：如果错误消息里包含 `"timeout"`、`"connection"` 关键词，优先归类为网络问题
2. **兜底规则**：如果一个异常既不属于可重试也不属于不可重试，默认不重试（安全优先）

实际上我把异常分类做成白名单制——只有明确知道"重试有用"的才重试，其他的默认不重试。宁可少救一个，不能多浪费一次。

## 指数退避算法

### 为什么固定延迟不够好？

假设你的服务挂了，正在重启。一般重启需要 10 秒。

固定延迟等 5 秒：第 1 次重试，服务还在重启→失败。第 2 次重试，服务启动好了→成功。运气好。

但如果服务启动需要 20 秒呢？固定延迟 5 秒，重试 3 次，全挂。

**指数退避的核心逻辑：**

- 第 1 次重试：等 2 秒（风浪不大）
- 第 2 次重试：等 4 秒（风浪变大了）
- 第 3 次重试：等 8 秒（风浪最大）

说白了，**你给服务更多的时间来恢复自己。** 第一次可能是误报，如果没恢复，那问题可能比较严重，多等等。

### RetryConfig 配置类

```python
class RetryConfig:
    """重试配置"""

    def __init__(self, max_retries: int = 3, base_delay: float = 2.0,
                 max_delay: float = 30.0, backoff_factor: float = 2.0):
        """
        参数说明：
        - max_retries: 最大重试次数（默认3次）
        - base_delay: 首次重试等待秒数（默认2秒）
        - max_delay: 最大等待秒数（默认30秒）
        - backoff_factor: 退避因子（默认2.0，即每次翻倍）
        """
        self.max_retries = max_retries
        self.base_delay = base_delay
        self.max_delay = max_delay
        self.backoff_factor = backoff_factor

    def get_delay(self, attempt: int) -> float:
        """计算第 N 次重试的等待时间（指数退避）"""
        delay = self.base_delay * (self.backoff_factor ** (attempt - 1))
        return min(delay, self.max_delay)

    def should_retry(self, exception: Exception, attempt: int) -> bool:
        """
        判断是否应该重试。
        逻辑错误不重试，只有网络/超时类异常才重试。
        """
        if is_logic_error(exception):
            logger.debug(f"逻辑错误（{type(exception).__name__}），不重试")
            return False
        if attempt >= self.max_retries:
            return False
        return True
```

**`get_delay` 的计算过程：**

| 第几次重试 | 公式 | 等待时间 |
|-----------|------|---------|
| 1 | 2.0 × 2⁰ | 2 秒 |
| 2 | 2.0 × 2¹ | 4 秒 |
| 3 | 2.0 × 2² | 8 秒 |
| 4 | 2.0 × 2³ | 16 秒 |
| 5 | 2.0 × 2⁴ | 30 秒（max_delay 兜底）|

**为什么要设置 max_delay？** 如果不设上限，第 10 次重试要等 2¹⁰ = 1024 秒 ≈ 17 分钟。测试跑一次就 forever 了。30 秒是个合理的上限——等半分钟还不够，那说明环境确实有问题，别再等了。

### 和固定延迟的对比

```python
# 固定延迟：每次等 5 秒，3 次共等 15 秒
# 指数退避：2 + 4 + 8 = 14 秒，差不多

# 但是如果需要更多重试：
# 固定延迟 5 秒 × 5 次 = 25 秒
# 指数退避 2 + 4 + 8 + 16 + 30 = 60 秒

# 指数退避在前期更激进（2秒就重试），
# 后期更保守（最长等30秒）
# 前期节省时间，后期给够恢复时间
```

## 重试跟踪器

### 为什么需要跟踪器？

重试的核心目的是**让测试更可靠**。但你怎么知道重试到底有没有用？

没有跟踪器，你只能凭感觉说"嗯，好像 CI 没那么红了"。有跟踪器，你能拿出数据说"重试引擎本周救回了 47 个用例，节省了约 23 分钟的人工排查时间"。

### RetryTracker 实现

```python
class RetryTracker:
    """
    重试跟踪器（跨 pytest 会话共享状态）。
    记录每个用例的重试次数和最终结果。
    """

    def __init__(self):
        self._retries = {}  # {nodeid: attempt_count}
        self._history = []  # [(nodeid, attempt, outcome, reason)]

    def record_attempt(self, nodeid: str, attempt: int, outcome: str,
                       reason: str = ""):
        """记录一次尝试"""
        key = f"{nodeid}#attempt{attempt}"
        self._retries[key] = outcome
        self._history.append((nodeid, attempt, outcome, reason))

    def get_attempt_count(self, nodeid: str) -> int:
        """获取某个用例已重试的次数"""
        count = 0
        for item in self._history:
            if item[0] == nodeid and item[1] > 1:
                count += 1
        return count

    def get_summary(self) -> dict:
        """获取重试统计摘要"""
        total = len(set(h[0] for h in self._history))
        retried = len(set(h[0] for h in self._history if h[1] > 1))
        failed_after_retry = len(set(
            h[0] for h in self._history
            if h[2] == "failed" and h[1] > 1
        ))
        saved_by_retry = len(set(
            h[0] for h in self._history
            if h[2] == "passed" and h[1] > 1
        ))
        return {
            "total_tests": total,
            "retried_tests": retried,
            "failed_after_retry": failed_after_retry,
            "saved_by_retry": saved_by_retry,
        }


# 全局重试跟踪器
retry_tracker = RetryTracker()
```

**`saved_by_retry` 是关键指标**：有多少用例第一次失败了，重试之后通过了。这就叫"被重试救回来的用例"。这个数字越大，说明重试引擎的价值越大。

### 在 pytest 会话结束时输出统计

```python
@pytest.hookimpl(tryfirst=True)
def pytest_sessionfinish(session, exitstatus):
    # ... 其他逻辑 ...

    summary = retry_tracker.get_summary()
    if summary["saved_by_retry"] > 0:
        logger.info("=" * 50)
        logger.info("  自愈系统摘要")
        logger.info(f"  总用例: {summary['total_tests']}")
        logger.info(f"  重试用例: {summary['retried_tests']}")
        logger.info(f"  重试救回: {summary['saved_by_retry']}")
        logger.info(f"  重试后仍失败: {summary['failed_after_retry']}")
        logger.info("=" * 50)
```

跑完测试，控制台输出这样的信息：

```
==================================================
  自愈系统摘要
  总用例: 156
  重试用例: 23
  重试救回: 18
  重试后仍失败: 5
==================================================
```

看到 18 个用例被救回来了，团队里谁还敢说重试是浪费时间？

### 踩坑记录

> 第一次写 `get_summary()` 的时候，我漏掉了 `set()` 去重。结果同一个用例重试了 3 次，就被统计成 3 个用例。报告上一看"重试救回: 54"，老板眼睛都亮了。后来发现数字不对，一查，原来是把多次重试算成多个用例了。**跟踪器一定要去重，以 nodeid 为单位统计。**

## 和现有 retry.py 的对比

项目里其实有两个重试相关的文件：

### utils/retry.py —— 装饰器模式

```python
@retry_on_failure(max_attempts=3, delay=1.0)
def test_login():
    # 测试代码
    pass
```

**特点：**
- 装饰器模式，直接装饰在函数上
- 适合重试**单个函数/操作**
- 固定延迟，不分异常类型
- 没有统计信息

**适用场景：**
- 一个函数需要保证稳定执行（如点击按钮、发送请求）
- 对重试行为没有精细控制需求
- 代码级别的重试，不涉及 pytest 用例生命周期

### self_healing/retry_engine.py —— pytest hook 集成

```python
# 在 conftest.py 中通过 hook 集成
retry_tracker.record_attempt(
    nodeid=report.nodeid,
    attempt=1,
    outcome=report.outcome,
)
```

**特点：**
- pytest hook 集成，工作在**用例级别**
- 条件重试：只重试网络/超时类异常
- 指数退避：延迟时间指数增长
- 完整的跟踪器：`get_summary()` 输出统计数据

**适用场景：**
- 整个测试套件的智能重试策略
- 需要区分"可重试"和"不可重试"的失败
- 需要量化重试效果，用数据说话

### 什么时候用哪个？

| 场景 | 用哪个？ |
|------|---------|
| 单个 API 调用需要重试 | `utils/retry.py` 的装饰器 |
| 整个用例失败了自动重试 | `retry_engine.py` + hook 集成 |
| 只需要简单重试，不想折腾 | `pytest-rerunfailures` |
| 需要一个"智能"的重试决策 | `retry_engine.py` 的 `RetryConfig` |

**说白了，两者不冲突：** `utils/retry.py` 管的是"一个函数调用失败怎么办"，`retry_engine.py` 管的是"一个测试用例失败怎么办"。粒度不同。

## 总结与思考

> 智能重试的核心不是"怎么重试"，而是"什么时候不重试"。区分"环境问题"和"代码 bug"，只重试前者，能省下大量无效的执行时间。配合指数退避和重试跟踪器，你不仅能做对决策，还能量化决策的效果。

**思考题**：你们的测试套件里，有多少失败是重试就能救回来的？用 `pytest-rerunfailures` 跑一轮，手动记录一下失败的用例类型。算一算：如果只重试网络/超时类异常，能省多少时间？

## 与第 22 节附录 B 的关系（运行时 vs 脚本自愈）

本节讲的是 **运行时自愈**：请求失败时重试、轮询、跳过，**不修改** pytest 源码。

若失败原因是 **契约变了**（字段改名、path 变更），重试无效，应：

1. 用 **第 22 节附录 A** 对比 OpenAPI 是否漂移；  
2. 更新测试脚本或断言（**脚本自愈**）。

## 面试题模块

### 1. 重试策略

**Q1：pytest-rerunfailures 有什么不足？你会怎么改进？**

A：主要不足三点：①不分异常类型，断言失败也重试，浪费执行时间；②固定重试间隔，没有考虑服务恢复时间；③没有统计信息，无法量化重试效果。改进方案：条件重试（只重试网络/超时类异常）、指数退避（2s → 4s → 8s 递增等待时间）、重试跟踪器（统计救回用例数）。

### 2. 异常分类

**Q2：怎么判断一个失败是否应该重试？**

A：看异常类型。`ConnectionError`、`TimeoutError`、`ConnectionRefusedError`、`ConnectionResetError` 这类网络/环境异常——重试。`AssertionError`、`ValueError`、`KeyError`、`AttributeError`、`SyntaxError` 这类代码逻辑异常——不重试。判断标准：重试有没有可能改变结果？环境问题可能恢复，代码 bug 不会自愈。

### 3. 指数退避

**Q3：指数退避的原理是什么？为什么比固定延迟好？**

A：指数退避让每次重试的等待时间按指数增长（如 2s → 4s → 8s → 16s）。比固定延迟好的原因是：①前期快速重试，如果问题不大能快速通过；②后期给足恢复时间，如果问题比较严重，服务需要更多时间恢复。加上 `max_delay` 限制（如 30s），防止无限增长。

### 4. 重试跟踪

**Q4：你怎么向团队证明重试引擎有价值？**

A：用数据说话。`RetryTracker.get_summary()` 输出四个指标：总用例数、重试过的用例数、重试救回的用例数（第一次失败→重试通过）、重试后仍失败的用例数。其中"重试救回"是最核心的指标。每周 CI 报告里附上这个数据，团队就能直观看到重试引擎在省时间。
