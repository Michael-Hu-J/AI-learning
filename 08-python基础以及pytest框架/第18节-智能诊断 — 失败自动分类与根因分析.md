# 18-智能诊断 — 失败分类与根因分析

> 对应代码：`test/self_healing/diagnostic.py`、`test/conftest.py`（集成部分）

---

## 概念讲解

先说个真实经历。

我之前带一个自动化测试项目，CI 跑了一整夜，第二天早上我打开报告——红了二十多个。然后呢？开始一个一个看：这个 `assert 200 == 500`，那个 `TimeoutException`，还有 `Connection refused`。看完一圈花了四十分钟。最后发现：一半是因为测试环境凌晨重启了没有恢复，另一半是新发布的代码改了接口返回值。

**四十分钟，就为了搞清楚"为什么失败"。**

这是所有自动化测试团队的通病——测试红了不可怕，可怕的是**没人知道为什么红**。你需要人工排查、翻日志、问同事，每一步都在消耗时间和精力。

智能诊断要解决的问题就是这个：**在失败发生的瞬间，自动告诉你——这是环境问题还是代码 bug？根因是什么？应该怎么修？**

说白了，就是给测试报告装上"分析脑"。

## 失败分类 — 先搞清楚"谁的问题"

### 1. 为什么要分类？

失败的原因千千万，但大部分可以归纳为几类：

| 失败类型 | 典型表现 | 该谁处理 |
|---------|---------|---------|
| 环境问题 | 服务 503、连接拒绝、数据库无法访问 | 运维 / 环境维护者 |
| 代码 Bug | 断言失败、空指针、逻辑错误 | 开发 |
| 数据问题 | 唯一性冲突、外键约束、测试数据不存在 | 测试 / 数据维护者 |
| 超时 | 元素等待超时、请求超时 | 开发（定位器/超时策略） |
| 偶发 | 有时过有时不过，原因不明 | 测试（标记 flaky 后续排查） |
| 未知 | 无法归类的新错误 | 人工排查 |

每个分类的"修复责任人"不同。自动分好类，报告就能直接告诉团队"找谁修"。

### 2. FailureCategory 枚举

用枚举而不是字符串常量，避免拼写错误：

```python
class FailureCategory:
    """失败原因分类"""
    ENVIRONMENT = "environment"       # 环境问题（服务挂了、网络不通、依赖缺失）
    CODE_BUG = "code_bug"             # 代码逻辑错误（断言失败、空指针等）
    DATA_ISSUE = "data_issue"         # 数据问题（测试数据不对、数据被污染）
    TIMEOUT = "timeout"               # 超时（元素等待超时、请求超时）
    FLAKY = "flaky"                   # 偶发性失败（概率性问题）
    UNKNOWN = "unknown"               # 无法识别
```

为什么不直接用 `Enum` 类？因为从 conftest 导入时字符串的比较更直观。枚举类也行，但这里我选了简单方案。

### 3. 关键词匹配分类器

每种失败类型都有一些"标志性关键词"：

```python
# 环境问题关键词
ENV_KEYWORDS = [
    "Connection refused",
    "Cannot connect",
    "no such host",
    "Service unavailable",
    "500 Server Error",
    "502 Bad Gateway",
    "503 Service Unavailable",
    "ModuleNotFoundError",
    ...
]

# 超时关键词
TIMEOUT_KEYWORDS = [
    "timeout", "Timed out",
    "NoSuchElementException",
    "TimeoutException",
    "Read timed out",
    ...
]

# 数据问题关键词
DATA_KEYWORDS = [
    "duplicate", "already exists",
    "Unique constraint",
    "foreign key constraint",
    "IntegrityError",
    ...
]

# 断言语义关键词（代码 bug）
ASSERT_KEYWORDS = [
    "AssertionError", "assert",
    "Expected", "not equal",
    "failed",
    ...
]
```

分类器的核心逻辑很简单——按优先级匹配关键词：

```python
def classify_failure(report) -> str:
    """分类失败原因"""
    error_text = _extract_error_text(report)
    if not error_text:
        return FailureCategory.UNKNOWN

    # 检查超时（优先级最高）
    for kw in TIMEOUT_KEYWORDS:
        if kw.lower() in error_text.lower():
            return FailureCategory.TIMEOUT

    # 检查环境问题
    for kw in ENV_KEYWORDS:
        if kw in error_text:
            return FailureCategory.ENVIRONMENT

    # 检查数据问题
    for kw in DATA_KEYWORDS:
        if kw.lower() in error_text.lower():
            return FailureCategory.DATA_ISSUE

    # 检查断言失败
    for kw in ASSERT_KEYWORDS:
        if kw in error_text:
            return FailureCategory.CODE_BUG

    return FailureCategory.UNKNOWN
```

匹配顺序有讲究：超时放在最前面，因为它关键词和"环境问题"有重叠（timeout 既是超时也是环境问题）。数据问题放在断言之前，因为某些数据错误（如 `IntegrityError`）也会触发断言。

### 4. 为什么不用机器学习的分类？

你可能会问：现在都 AI 时代了，怎么还在用关键词匹配？

**三个原因：**

1. **可解释性**：关键词匹配被问"为什么这么分"时，你可以直接说"因为错误消息里有 `Connection refused`"。ML 模型你得解释权重矩阵和决策边界。
2. **零训练成本**：规则写好了就能用，不需要标注数据、不需要训练、不需要调参。
3. **80% 场景覆盖**：测试失败的错误消息就那么几类，关键词规则已经能覆盖 80% 以上的场景。剩下 20% 归到 `UNKNOWN` 人工处理即可。

**原则：能用规则解决的问题，别上模型。**

## 根因提取 — 从 100 行 traceback 里找到关键那一行

### 1. 问题：没人想看完整的堆栈

测试失败时 pytest 会输出完整的 traceback。如果是多层调用栈，可能喷出 50-100 行。但开发者真正关心的只有一行——"到底哪一句断言失败了？"

`extract_root_cause()` 就是干这个的：

```python
def extract_root_cause(report) -> Optional[str]:
    """
    提取根因。
    从长错误信息中提取最有价值的那一行。
    """
    error_text = _extract_error_text(report)
    if not error_text:
        return None

    lines = error_text.split("\n")

    # 优先找断言失败的行
    for line in lines:
        if "AssertionError" in line or "assert " in line:
            return line.strip()

    # 其次找异常类型
    for line in lines:
        if re.match(r"^[A-Za-z_]+(\.[A-Za-z_]+)*Error", line.strip()):
            return line.strip()
        if re.match(r"^[A-Za-z_]+(\.[A-Za-z_]+)*Exception", line.strip()):
            return line.strip()

    # 最后取第一个非空非 traceback 行
    for line in lines:
        stripped = line.strip()
        if stripped and not stripped.startswith("Traceback"):
            if not stripped.startswith("  File"):
                if not stripped.startswith("    "):
                    return stripped[:200]

    return error_text[:200]
```

提取策略是"三优先"：

1. **断言行优先**：`assert 200 == 500` — 这就是根因，别废话
2. **异常类型其次**：`requests.exceptions.ConnectionError` — 明确了错误种类
3. **首个非堆栈行兜底**：取第一个看起来像"结论"的行

### 2. 实用效果

原始输出（100行）：
```

  File "/usr/lib/python3/dist-packages/urllib3/connectionpool.py", line 699, in urlopen
    httplib_response = self._make_request(...)
```

## 修复建议 — 别只说"错了"，告诉我"怎么修"

### 1. suggest_fix()

分类出来后，根据分类类型给可操作的建议：

```python
def suggest_fix(category: str, root_cause: str = "") -> str:
    """根据失败分类生成修复建议"""
    suggestions = {
        FailureCategory.ENVIRONMENT: (
            "环境问题：检查目标服务是否启动、网络是否连通、"
            "依赖服务是否正常运行。\n"
            "  建议：先执行健康检查脚本确认环境状态，再重新跑测试。"
        ),
        FailureCategory.CODE_BUG: (
            "代码逻辑错误：检查断言逻辑、数据准备和期望值是否正确。\\n"
            "  建议：本地调试复现，确认是代码 bug 还是测试数据问题。"
        ),
        FailureCategory.DATA_ISSUE: (
            "数据问题：检查测试数据是否被污染、唯一性约束、"
            "关联数据是否存在。\n"
            "  建议：重置测试数据后重试，或检查是否有并发操作覆盖了数据。"
        ),
        FailureCategory.TIMEOUT: (
            "超时失败：可能是网络延迟、服务响应慢、或元素定位失效。\\n"
            "  建议：增加等待时间、检查元素定位器是否有效。"
            "如果偶发，重试通常能解决。"
        ),
        FailureCategory.FLAKY: (
            "偶发性失败：多次执行结果不一致。\\n"
            "  建议：增加等待策略稳定性、避免共享状态、"
            "考虑标记为 flaky 后续排查。"
        ),
        FailureCategory.UNKNOWN: (
            "无法自动分类的失败原因。\\n"
            "  建议：查看完整的 Allure 报告，人工分析失败原因。"
        ),
    }
    return suggestions.get(category, suggestions[FailureCategory.UNKNOWN])
```

### 2. 为什么建议要"可操作"

最没用的修复建议就是"请检查错误"——废话文学。

好的建议必须告诉对方**具体做什么**：

| 分类 | 差建议 | 好建议 |
|------|-------|-------|
| 环境问题 | 环境可能有问题 | 检查服务是否启动、网络是否连通 |
| 超时 | 可能超时了 | 增加等待时间或检查元素定位器 |
| 代码bug | 看看代码 | 检查断言逻辑和期望值 |

## 集成到 Hook — 让诊断自动化

### 1. pytest_runtest_makereport 中的自动诊断

在 conftest.py 的 `pytest_runtest_makereport` hook 中，当测试失败时自动调用诊断模块：

```python
@pytest.hookimpl(tryfirst=True, hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    rep = outcome.get_result()
    setattr(item, f"rep_{rep.when}", rep)

    # 只在 call 阶段处理失败诊断
    if rep.when == "call" and rep.failed:
        nodeid = item.nodeid

        # 失败分类诊断
        category = classify_failure(rep)
        root_cause = extract_root_cause(rep)
        fix_suggestion = suggest_fix(category, root_cause)

        # 打印诊断信息
        logger.info(f"用例失败: {nodeid}")
        logger.info(f"   分类: {category}")
        if root_cause:
            logger.info(f"   根因: {root_cause[:150]}")
        logger.info(f"   建议: {fix_suggestion[:150]}")
```

### 2. 运行效果

当测试失败时，控制台自动输出诊断信息：

```
WARNING  conftest:conftest.py 用例失败: tests/test_api.py::test_create_order
WARNING  conftest:conftest.py    分类: code_bug
WARNING  conftest:conftest.py    根因: AssertionError: 创建订单失败: {"error": "Insufficient stock"}
WARNING  conftest:conftest.py    建议: 代码逻辑错误：检查断言逻辑...
```

不需要打开报告，不需要翻日志，失败的那一刻就知道问题在哪。

### 3. 完整的数据流

```
测试失败
  ↓
pytest_runtest_makereport(hook)
  ↓
classify_failure(report) ──────→ 分类：code_bug / timeout / environment ...
  ↓
extract_root_cause(report) ────→ 根因：AssertionError: xxx
  ↓
suggest_fix(category) ─────────→ 建议：检查断言逻辑
  ↓
打印到控制台 + 附加到 Allure
```

## 踩坑记录

### 坑1：关键词匹配的误判

`Connection reset by peer` 包含 `reset` 和 `Connection` 两个词。如果某个断言错误消息里也写了 `reset`，就可能被误分类为环境问题。

**解决**：环境问题关键词用完整短语（`Connection refused` 而非 `refused`），减少误触。

### 坑2：错误文本太长

有些框架的错误消息会序列化整个请求/响应体，长达几千字符。全部扫描关键词效率低。

**解决**：`_extract_error_text()` 只提取 `longreprtext`，必要时再截断。

### 坑3：hook 执行顺序

如果在 `pytest_runtest_makereport` 中既做诊断又做其他操作（如截图保存），要注意执行顺序。用 `tryfirst=True` 保证诊断先执行，其他后执行。

## 总结与思考

智能诊断不是什么高科技，但它是"测试工程化"中最容易见效的一环。

一套关键词 + 一个根因提取 + 一个修复建议，几十行代码就能让测试报告从"满屏红色"变成"告诉你哪里有问题、该怎么修"。

**核心原则**：

1. **分类比诊断更重要**——先搞清楚"谁的问题"，再考虑"怎么修"
2. **可操作的建议才有价值**——"请检查"是废话，"检查服务是否启动"是建议
3. **规则优先于 AI**——80% 的测试失败能用关键词规则覆盖，别为了炫技上模型

**思考题**：你的测试项目中，失败最多的是哪类问题？如果用这套分类器去分析，占比最高的会是哪个分类？你团队里最头疼的"修 bug 找人"场景是哪一种？

## 面试题模块

### 1. 失败分类

**Q1：自动化测试失败的原因一般可以分成几类？分别举一个例子。**

A：一般可以分成六类：
- **环境问题**：服务返回 503、数据库连接被拒绝
- **代码 Bug**：断言 `assert 200 == 500` 失败
- **数据问题**：插入测试数据时违反唯一性约束
- **超时**：等待元素出现时抛出 `TimeoutException`
- **偶发**：同一个测试有时过有时不过
- **未知**：无法归类的错误

分类的意义在于：不同类型的失败需要不同的人处理，分类后能直接告诉团队"该找谁"。

### 2. 分类器设计

**Q2：如果让你设计一个失败分类器，你会选择用规则匹配还是机器学习？为什么？**

A：优先选择规则匹配（关键词），原因有三：
① 测试失败的错误模式相对固定，80% 可以用关键词覆盖
② 规则匹配的可解释性强，出了问题容易排查
③ 零训练成本，无需标注数据和调参

只有剩余 20% 的未知分类才需要考虑引入 ML，而且通常是作为"辅助分析"而非主分类器。

### 3. 根因提取

**Q3：测试报告中的 traceback 非常长，你怎么从中提取关键信息？**

A：使用"三优先"策略：
1. 优先找包含 `AssertionError` 或 `assert` 的行（最直接的失败点）
2. 其次找异常类型行（如 `ConnectionError`、`TimeoutException`）
3. 最后取第一个非堆栈行的内容

目的是把 100 行的 traceback 压缩成 1-2 行关键信息，让排查者一眼看到根因。

### 4. 修复建议

**Q4：如何编写有效的修复建议？**

A：有效建议的公式是：**失败原因 + 具体操作**。

差建议："请检查错误"——没说怎么做。
好建议："环境问题：检查服务是否启动、网络是否连通。建议先执行健康检查脚本。"

好建议必须告诉对方：先做什么、后做什么、预期是什么。
