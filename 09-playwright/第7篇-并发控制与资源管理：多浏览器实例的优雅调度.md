> **代码说明**：本文中的代码示例来自完整版系统，配套代码（`配套代码/` 目录）提供了功能一致的简化版——去掉了 LLM API、LangGraph、数据库等外部依赖，替换为纯规则实现 + JSON 文件 + 内置演示应用。文章讲原理，配套代码可本地跑通，两相对照效果更好。

文中 `page.goto(url)` 等占位 URL 在本地联调时可设为 `http://127.0.0.1:5000/login`（Flask 默认端口），与 `配套代码/tests/` 下用例所选基地址无冲突；本节重点仍是执行平台侧的并发与进程模型。

100 个浏览器实例同时启动，内存直接 OOM——这是我们踩过的坑。后来加了信号量限制、进程隔离和优雅停止机制，这套并发控制方案跑了大半年，稳定支撑 3-5 个并发实例的日常测试。

## 一、为什么需要并发控制？

### 1.1 资源消耗问题

一个 Playwright 浏览器实例的资源消耗：

| 资源 | 单个实例 | 10 个实例 |
|------|---------|----------|
| CPU | 10-30% | 100-300% |
| 内存 | 200-500MB | 2-5GB |
| 文件描述符 | 50-100 | 500-1000 |
| 网络端口 | 1-3 | 10-30 |

**问题场景**：

```python
# 反模式：无限制并发
BASE = "http://127.0.0.1:5000"  # 被测系统基地址（示例默认：秒杀财务 Flask）

url = f"{BASE}/login"
for i in range(100):
    browser = playwright.chromium.launch()  #  100 个浏览器实例
    page = browser.new_page()
    page.goto(url)
```

**结果**：
- CPU 100% 占用
- 内存溢出（OOM）
- 系统崩溃

### 1.2 并发控制的目标

1. **限制并发数**：同时运行的浏览器实例不超过 N 个
2. **资源隔离**：每个实例独立，互不影响
3. **优雅停止**：支持随时停止执行
4. **结果持久化**：执行结果保存到数据库

## 二、asyncio.Semaphore 并发控制

### 2.1 Semaphore 原理

```python
import asyncio

# 创建信号量，最多 3 个并发
semaphore = asyncio.Semaphore(3)

async def run_test(exec_id):
    async with semaphore:  # 等待信号量
        # 执行测试
        await execute_test(exec_id)
    # 释放信号量

# 启动 10 个测试，但最多只有 3 个同时运行
tasks = [run_test(f"exec_{i}") for i in range(10)]
await asyncio.gather(*tasks)
```

**执行时间线**：

```
T+0s  exec_1 启动 (semaphore: 2)
T+0s  exec_2 启动 (semaphore: 1)
T+0s  exec_3 启动 (semaphore: 0)
T+0s  exec_4 等待 (semaphore: 0)
T+0s  exec_5 等待 (semaphore: 0)
...
T+10s exec_1 完成 (semaphore: 1) → exec_4 启动
T+15s exec_2 完成 (semaphore: 1) → exec_5 启动
```

### 2.2 在 UIExecutionService 中的实现

> **常见错误**：在 async 函数中使用 `subprocess.Popen` + `proc.wait()` 会阻塞事件循环，导致其他协程无法执行。正确做法是使用 `asyncio.create_subprocess_exec` + `await proc.communicate()`。

```python
# ui_execution_service.py
class UIExecutionService:
    def __init__(self, max_concurrent: int | None = None):
        from app.config import settings
        
        self._semaphore: asyncio.Semaphore | None = None
        self._max_concurrent = int(max_concurrent if max_concurrent is not None 
                                   else settings.UI_MAX_CONCURRENT_BROWSERS)
        self._processes: Dict[str, asyncio.subprocess.Process] = {}
        self._cache: Dict[str, Dict[str, Any]] = {}
    
    @property
    def semaphore(self) -> asyncio.Semaphore:
        if self._semaphore is None:
            self._semaphore = asyncio.Semaphore(self._max_concurrent)
        return self._semaphore
    
    async def _run_subprocess(self, exec_id: str) -> None:
        """在信号量保护下启动子进程（非阻塞）"""
        async with self.semaphore:  # 等待信号量
            cache = self._get_or_create_cache(exec_id)
            config = cache.get("config", {})
            
            self._push_log(exec_id, " 等待浏览器资源 (并发控制)...", "info")
            self._push_log(exec_id, f" 开始执行 UI 测试，共 {len(config.get('steps', []))} 步", "info")
            
            #  正确：使用 asyncio.create_subprocess_exec（不阻塞事件循环）
            paths = _worker_paths(exec_id)  # 生成 config/result/stop_flag 文件路径
            proc = await asyncio.create_subprocess_exec(
                sys.executable, WORKER_SCRIPT, paths["config"], paths["result"], paths["stop"],
                stdout=asyncio.subprocess.PIPE,
                stderr=asyncio.subprocess.STDOUT,
            )
            self._processes[exec_id] = proc
            
            #  正确：await proc.communicate() 不会阻塞事件循环
            try:
                stdout, stderr = await asyncio.wait_for(
                    proc.communicate(), timeout=600
                )
            except asyncio.TimeoutError:
                proc.kill()
                self._push_log(exec_id, " 子进程超时，终止执行", "error")
            
            # 读取结果
            result = json.load(open(paths["result"]))
            
            # 清理
            self._processes.pop(exec_id, None)
```

> 配套代码 `配套代码/worker/execution_service.py` 中的实现与上面一致，使用 `asyncio.create_subprocess_exec` + `await proc.communicate()`。

## 三、进程隔离设计

### 3.1 为什么不用线程？

| 维度 | 线程 | 进程 |
|------|------|------|
| GIL 限制 |  有 |  无 |
| 崩溃隔离 |  无 |  有 |
| 内存共享 |  有 |  无 |
| 资源开销 | 低 | 高 |
| 调试难度 | 中 | 低 |

**线程的问题**：

```python
# 反模式：使用线程
import threading

def run_test(config):
    with sync_playwright() as p:
        browser = p.chromium.launch()
        # ... 执行测试

threads = []
for i in range(10):
    t = threading.Thread(target=run_test, args=(config,))
    t.start()
    threads.append(t)

# 问题：
# 1. GIL 限制，无法真正并行
# 2. 一个线程崩溃，所有线程受影响
# 3. 内存泄漏，浏览器实例无法释放
```

### 3.2 进程隔离方案

```python
# 主进程
proc = subprocess.Popen(
    [sys.executable, WORKER_SCRIPT, 
     paths["config"], paths["result"], paths["stop"]],
    stdout=subprocess.PIPE,
    stderr=subprocess.STDOUT,
    text=True,
    bufsize=1,
)
self._processes[exec_id] = proc

# Worker 进程（独立进程）
def run(config_path, result_path, stop_flag_path):
    config = json.load(open(config_path))
    
    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)
        page = browser.new_page()
        
        for step in config["steps"]:
            # ... 执行测试
        
        browser.close()
    
    json.dump(result, open(result_path, "w"))
```

### 3.3 进程间通信

**方式 1：JSON 文件（配置和结果）**

```python
# 主进程写入配置
with open(paths["config"], "w") as f:
    json.dump(config, f)

# Worker 进程读取配置
config = json.load(open(config_path))

# Worker 进程写入结果
with open(result_path, "w") as f:
    json.dump(result, f)

# 主进程读取结果
result = json.load(open(result_path))
```

**方式 2：管道（实时日志）**

```python
# Worker 进程输出日志
print(f" [步骤 1] 打开页面成功")

# 主进程读取日志
def _read_output():
    for line in proc.stdout:
        self._push_log(exec_id, line.strip(), "info")

reader = threading.Thread(target=_read_output, daemon=True)
reader.start()
```

**方式 3：文件标志（停止信号）**

```python

    f.write("stop")

# Worker 进程检查停止标志
if os.path.exists(stop_flag_path):
    print(" 收到停止信号")

```

## 四、优雅停止机制

### 4.1 三级停止机制

**第一级：stop flag 文件（优雅停止）**

```python
def request_stop(self, exec_id):
    """请求停止执行"""
    cache = self._get_or_create_cache(exec_id)
    cache["stop_requested"] = True
    self._push_log(exec_id, " 已请求停止执行", "warning")
    
    # 创建 stop flag 文件
    paths = _worker_paths(exec_id)
    with open(paths["stop"], "w") as f:
        f.write("stop")
```

**第二级：子进程 terminate（强制停止）**

```python
def _kill_process(self, exec_id):
    """终止子进程"""
    proc = self._processes.get(exec_id)
    if proc and proc.poll() is None:
        try:
            proc.terminate()  # 发送 SIGTERM
            proc.wait(timeout=5)
        except Exception:
            try:
                proc.kill()  # 发送 SIGKILL
            except Exception:
                pass
```

**第三级：超时自动停止**

```python
try:
    returncode = proc.wait(timeout=600)  # 10 分钟超时
except subprocess.TimeoutExpired:
    self._push_log(exec_id, " 子进程超时，终止执行", "error")
    self._kill_process(exec_id)
    cache["status"] = "failed"
```

## 五、DB 持久化 + 内存缓存

前面的并发控制和进程隔离解决了"怎么跑"的问题，但执行结果需要持久化存储——否则服务重启后所有状态丢失，用户刷新页面看不到任何历史数据。

### 5.1 双层架构

```python
class UIExecutionService:
    def __init__(self):
        self._cache = {}  # 内存缓存
    
    def _push_log(self, exec_id, message, level="info"):
        """推送日志到内存缓存 + DB"""
        # 1. 写入内存缓存
        cache = self._get_or_create_cache(exec_id)
        cache["logs"].append({
            "time": datetime.now().strftime("%H:%M:%S"),
            "message": message,
            "level": level,
        })
        
        # 限制内存中的日志数量
        if len(cache["logs"]) > 500:
            cache["logs"] = cache["logs"][-500:]
        
        # 2. 同步到 DB
        self._update_record(exec_id, logs=cache["logs"])
    
    def _sync_cache_to_db(self, exec_id):
        """执行结束时，将完整结果同步到 DB"""
        cache = self._cache.get(exec_id)
        if not cache:
            return
        
        self._update_record(
            exec_id,
            status=cache.get("status"),
            stats=cache.get("stats"),
            logs=cache.get("logs"),
            end_time=datetime.fromisoformat(cache["end_time"]),
            result_data={
                "step_results": cache.get("step_results", []),
                "locator_resolution": cache.get("locator_resolution", []),
                "self_healing": cache.get("self_healing", {}),
            },
        )
```

### 5.2 `_update_record` 实现（JSON 文件版本）

去掉 DB 依赖后，用 JSON 文件做持久化，配套代码 `配套代码/worker/execution_service.py` 中的 `history()` / `save_history()` 就是这个思路：

```python
import json
import os
from datetime import datetime

HISTORY_FILE = "/tmp/pw_exec_history.json"

def _load_history() -> list:
    """加载执行历史"""
    if os.path.exists(HISTORY_FILE):
        try:
            with open(HISTORY_FILE, "r", encoding="utf-8") as f:
                return json.load(f)
        except (json.JSONDecodeError, IOError):
            return []
    return []

def _save_history(items: list):
    """保存执行历史"""
    os.makedirs(os.path.dirname(HISTORY_FILE) or ".", exist_ok=True)
    with open(HISTORY_FILE, "w", encoding="utf-8") as f:
        json.dump(items, f, ensure_ascii=False, indent=2)

def _update_record(exec_id: str, **kwargs):
    """更新执行记录（JSON 文件版本）"""
    history = _load_history()
    
    # 查找已有记录
    record = None
    for r in history:
        if r.get("exec_id") == exec_id:
            record = r
            break
    
    if record is None:
        record = {"exec_id": exec_id, "created_at": datetime.now().isoformat()}
        history.append(record)
    
    # 更新字段
    for key, value in kwargs.items():
        record[key] = value
    
    record["updated_at"] = datetime.now().isoformat()
    
    # 只保留最近 100 条
    _save_history(history[-100:])
```

## 六、踩坑经验

### 6.1 坑 1：asyncio.run() 在 FastAPI 中会报错

**问题**：`asyncio.run()` 会创建新的事件循环，但 FastAPI 已经有自己的事件循环，嵌套调用会报 `RuntimeError: This event loop is already running`。

**解决**：在 FastAPI 的异步路由中，直接使用 `await` 或 `asyncio.create_task()`：

```python
#  错误：在 FastAPI 路由中用 asyncio.run()
@app.post("/run")
async def run_test():
    asyncio.run(_run_execution())  # 报错！

#  正确：直接 await
@app.post("/run")
async def run_test():
    await _run_execution()

#  或者用 create_task 后台执行（不阻塞响应）
@app.post("/run")
async def run_test():
    exec_id = str(uuid.uuid4())[:8]
    task = asyncio.create_task(_run_execution(exec_id))
    return {"exec_id": exec_id}
```

> `asyncio.run()` 适用于独立脚本（如 CLI 工具、cron 任务），不适用于已有事件循环的框架（FastAPI、Django ASGI 等）。

### 6.2 坑 2：子进程 stdout 缓冲

**问题**：子进程的 stdout 默认是块缓冲，导致日志延迟。

**解决**：使用行缓冲。

```python
proc = subprocess.Popen(
    [sys.executable, WORKER_SCRIPT, ...],
    stdout=subprocess.PIPE,
    text=True,
    bufsize=1,  # 行缓冲
    env={**os.environ, "PYTHONUNBUFFERED": "1"},
)
```

### 6.3 坑 3：进程泄漏

**问题**：子进程异常退出时，PID 映射未清理。

**解决**：使用 try-finally 清理。

```python
try:
    proc = subprocess.Popen(...)
    self._processes[exec_id] = proc
    returncode = proc.wait(timeout=600)
finally:
    self._processes.pop(exec_id, None)
```

### 6.4 坑 4：内存缓存与 DB 不一致

**问题**：服务重启后，内存缓存丢失。

**解决**：启动时从 DB 恢复缓存。

```python
def _get_or_create_cache(self, exec_id):
    if exec_id not in self._cache:
        record = self._get_record(exec_id)
        if record:
            self._cache[exec_id] = {
                "status": record.status,
                "logs": record.logs or [],
                # ...
            }
    return self._cache[exec_id]
```

## 七、总结

并发控制的核心就是三件事：限制并发数（Semaphore）、隔离执行环境（进程）、随时能停下来（优雅停止）。这三件事没做好，浏览器实例多了之后系统直接崩溃，连排查日志都留不下来。

配套代码 `配套代码/worker/execution_service.py` 去掉了 DB 依赖，用 JSON 文件做持久化（`history()` / `save_history()`），子进程启动使用 `asyncio.create_subprocess_exec` + `await proc.communicate()`，与正文 2.2 节的实现一致。

并发数配置建议：

| 服务器配置 | 推荐并发数 | 原因 |
|-----------|-----------|------|
| 2 核 4GB | 1-2 | 资源有限 |
| 4 核 8GB | 2-3 | 平衡性能 |
| 8 核 16GB | 3-5 | 高并发 |
| 16 核 32GB+ | 5-10 | 超高并发 |

### 7.1 实战：我们线上是怎么配的

我们的生产环境是 8 核 16GB 的云服务器，配了 3 个并发。为什么不是 5 个？因为除了浏览器实例，服务器上还要跑 FastAPI、MySQL、Redis。3 个浏览器实例占 600-1500MB 内存，加上其他服务，总内存使用在 8-10GB，留了足够的余量。

**监控数据**：跑了半年，3 个并发下平均每个测试用例 45 秒，100 个用例约 75 分钟（串行）或 25 分钟（3 并发）。内存峰值 11GB，没有 OOM。

**遇到的唯一问题**：有一次 MySQL 连接池满了（默认 10 个连接），3 个 Worker 同时连库导致第 4 个请求等待超时。后来把连接池调到了 20，问题消失。

### 7.2 实战：进程 vs 线程的真实对比

我们在 v1.0 用的是线程方案——`threading.Thread` 启动每个浏览器。看起来简单，但问题不断：

| 问题 | 线程方案 | 进程方案 |
|------|---------|---------|
| GIL 锁 | 3 个浏览器同时跑，实际只有 1 个在跑 | 无 GIL，真正并行 |
| 崩溃传播 | 一个浏览器崩溃，整个进程挂 | 一个进程崩，其他不受影响 |
| 资源隔离 | 内存共享，一个实例泄漏影响全部 | 内存隔离，各自独立 |
| 调试难度 | 线程堆栈混在一起，日志难区分 | 每个进程独立日志，容易排查 |

**迁移成本**：从线程改到进程，代码改动量约 200 行（主要是进程间通信部分），但稳定性提升了 10 倍。这个投入产出比非常值得。

### 7.3 实战：优雅停止的实际效果

"优雅停止"听起来是个锦上添花的功能，实际上是最常用的功能之一。用户点了"停止"按钮，如果直接 `kill -9`，浏览器进程可能还在写文件，导致结果文件损坏。我们的优雅停止流程：

1. 创建 stop flag 文件
2. Worker 检测到 stop flag，完成当前步骤后退出
3. 如果 30 秒内未退出，才 `kill -9`

**实际使用频率**：大约 20% 的测试执行会被用户手动停止（要么是测试写错了，要么是等不及了）。每次停止都能正常退出，没有一次导致进程泄漏。
